# بوابة التحقق

شغّل `npm run check` من نسخة المصدر على Node.js 22.16 أو أحدث بعد تثبيت الاعتمادات. تنفّذ البوابة TypeScript وESLint (أي خطأ يُفشلها، والتحذيرات لا؛ الاستثناءات المراجَعة وأسبابها في `eslint.config.mjs`) وكل ملفات `tests/**/*.mjs` تلقائيًا، إلا الاستثناءات المحددة بسبب واضح في `check-manifest.json`. إضافة اختبار جديد لا تحتاج تعديل قائمة تشغيل. من 2026-11-05 تعمل الاختبارات **بالتوازي**: كل اختبار في عملية مستقلة، و`--jobs N` عدد العمليات في نفس الوقت (الافتراضي عدد المعالجات، 4 هنا؛ `npm run check -- --jobs 1` يشغّلها واحدًا بعد الآخر كما كانت)، وTypeScript وESLint يبدآن أولًا بجانب الاختبارات، ثم الأطول فالأقصر حسب آخر تقرير. حد الذاكرة كما هو: 512 MiB للاختبار و768 MiB لفحص الأنواع و2048 MiB لـESLint، ومهلة 120 ث للاختبار (180 ث وTypeScript و300 ث ESLint)؛ هذه ليست حدودًا لإجمالي ذاكرة نظام التشغيل. القياس على هذا الجهاز: نحو 6 دقائق متتابعة صارت نحو 3 دقائق (2 د 53 ث بـ4، و3 د 2 ث بـ3، و2 د 40 ث بـ6). لا تشغّل `npm run check` مرتين في نفس الوقت على نفس النسخة: الاثنان يكتبان `output/check/`.

النتيجة التفصيلية في `output/check/default-results.json`، وسجل مستقل لكل اختبار. أي فشل يجعل الأمر يفشل. في التشغيل المتوازي، اختبار فشل يُعاد مرة واحدة **وحده** بعد انتهاء الباقي: لو فشل ثانية يفشل الأمر، ولو نجح يُطبع `FLAKY` ويُذكر في السطر الأخير («(1 flaky: …)») وفي `flaky` و`firstTry` داخل التقرير، ولا يُحسب نجاحًا عاديًا؛ مع `--jobs 1` لا إعادة إطلاقًا. **الاختبارات التي تعمل وحدها** بعد المتوازي قائمتها في `check-manifest.json` تحت `serial` مع السبب (مكان واحد): `record-index.mjs` و`same-snapshot.mjs` (ميزانيات زمنية بالميلي ثانية) و`portable-local-mail.mjs` (يتحقق أن برنامج بريد معلّق يُقتل بمهلته 4.5 ث خلال 6 ث). باقي الاختبارات آمنة بالتوازي: فُحصت كلها بحثًا عن منافذ ثابتة ومسارات مؤقتة مشتركة وكتابة في `docs/` أو `output/` أو `public/` أو `dist/` يقرؤها غيرها وأقفال وحرّاس زمنية؛ كل مجلداتها المؤقتة `mkdtemp` (ومنها داخل `.sites-runtime`)، ولا منفذ ثابت، ولا كتابة في ملفات المستودع؛ وحارس التعليق في `visit-file-concurrency.mjs` صار 15 ث بدل 3 (حارس، لا قياس سرعة). الاختبارات تستخدم بيانات مصطنعة وقواعد مؤقتة؛ نجاحها لا يعني اختبار الهاتف أو بيانات الإنتاج أو PostgreSQL. التطبيق الحالي واختبارات الاستضافة المحمولة يستعملان SQLite، وليس PostgreSQL.

## بوابة الإصدار السريعة: `npm run gates` (2026-11-05)

طلب صاحب العمل ألا تتكرر كل الاختبارات مع كل تحديث، واختار الاثنين: تشغيل الاختبارات بالتوازي، وفي كل تحديث البوابة الافتراضية كاملة ومعها اختبارات `release-build` و`browser` الخاصة بالأجزاء التي تغيّرت فقط، والكل لما يتغيّر شيء مشترك. أمر واحد للإصدار:

```bash
export CODEX_PRIMARY_RUNTIME_NODE_MODULES=/path/to/node_modules   # فيه playwright (كما في تشغيل الإصدارات)
npm run gates -- --browser-executable /path/to/chromium          # أو YR_BROWSER_EXECUTABLE في البيئة
npm run gates -- --full                                          # كل شيء
npm run gates -- --since <commit>                                # ما تغيّر منذ commit معيّن
node scripts/gates.mjs --plan [--since X [--to Y]]               # يطبع الاختيار ولا يشغّل شيئًا
```

- **الخطوات** (`scripts/gates.mjs`): بناء نظيف (`scripts/build-independent.mjs`، يحذف `dist` أولًا؛ `--no-build` يستعمل البناء الموجود)، ثم مجمّع عمّال (`--jobs`، الافتراضي 6، و`--browser-jobs`، الافتراضي 5 متصفحات في نفس الوقت) يبدأ بالبوابة الافتراضية (`scripts/check.mjs` نفسه الذي يشغّله `npm run check`، بـ`--check-jobs 4` عمليات داخلها) في خانة من خانات المجمّع **بجانب** باقي الاختبارات (`--default-gate first` يشغّلها وحدها قبلها؛ قيس الاثنان: بجانبها أسرع، 4 د 14 ث بدل 6 د 40 ث لتعديل القوالب و11 د 18 ث بدل 13 د 3 ث للكل، دون فشل) ثم الأطول فالأقصر (من مدد آخر تشغيل في `output/gates/*/summary.json`، وإلا `typicalSeconds` في `tests/test-areas.json`). بعده الاختبارات التي يجب أن تعمل وحدها (`serial`)، ثم يُعاد كل اختبار فشل مرة واحدة **وحده**. الاختيار الافتراضي لـ`--since`: الـcommit الذي بُنيت منه الحزمة التي يسمّيها `deploy/request.json` (سطر «built from» في commit الحزمة، وإلا ما قبله)؛ لو تعذّر يطلب الأمر `--since` أو `--full`.
- **البيئة لكل اختبار كما في تشغيل الإصدارات:** متغيرات الوكيل (proxy) محذوفة لكل العمليات؛ `NODE_NO_WARNINGS=1` للبناء واختبارات `release-build`؛ `YR_BROWSER_EXECUTABLE` لاختبارات المتصفح وحدها (من `--browser-executable` أو بيئة المستدعي، لا قيمة ثابتة)، ومعها متغيرات مجلدات الصور التي تقرؤها الاختبارات (`YR_GATE_SCREENSHOT_DIR` و`YR_MOLD_SCREENSHOT_DIR` وغيرها) موجّهة إلى `output/gates/<run>/screenshots/<test>/`. لا يُضبط أي `YR_*` آخر. كل اختبار في مجموعة عمليات خاصة به (النسخة المبنية وواجهة HTTPS وChromium تموت معه)، وسجله في `output/gates/<run>/<test>.log`، ومهلته 900 ث لـ`release-build` و1200 ث للمتصفح.
- **التوازي آمن:** كل الاختبارات تأخذ منافذ عشوائية ومجلدات مؤقتة خاصة (`bootBuiltApp` ونظائره)، ولا يكتب اختباران نفس الملف. ستة تكتب في `docs/` (تقارير التحقق ولقطات `daily-report-screenshots`؛ `app-update-browser` يكتب لقطاته في مجلد التشغيل لأن متغيره مضبوط)، وقائمتها `docsWrittenByTests` في `tests/test-areas.json`: يحفظ الأمر هذه الملفات قبل التشغيل ويعيدها كما كانت في النهاية (وعند Ctrl-C)، ولا يلمس أي ملف آخر في `docs/` (قد يكون تعديل شخص أثناء التشغيل) بل يذكره في الملخص مع أي تغيير آخر تركه التشغيل في المستودع.
- **الاختيار** (`tests/test-areas.json`، الدوال في `scripts/lib/test-areas.mjs`): لكل ملف تغيّر، بالترتيب: (1) ملفات يكتبها البناء (`public/offline-app/**` و`offline-app.html` و`offline-shell-manifest.json`، و`public/sw.js` لو تغيّر سطر `BUILD_REVISION` وحده) لا تختار شيئًا؛ (2) ملف **مشترك** ← تشغيل كامل؛ (3) اختبار `release-build`/`browser` تغيّر ← يعمل هو نفسه؛ (4) ملف يقع في **منطقة** ← اختبارات المنطقة (ومنها مستندات المنطقة واختباراتها)؛ (5) `defaultGateOnly` (المستندات العامة، أندرويد، `deploy/`، إعداد ESLint، اختبارات البوابة الافتراضية) ← البوابة الافتراضية فقط؛ (6) أي ملف لا تغطيه قاعدة ← تشغيل كامل، ويُذكر الملف في الملخص. `lib/locales/en.json` مشترك، إلا لو التغيير يضيف مفاتيح فقط (لا يغيّر شاشة موجودة). البوابة الافتراضية تعمل دائمًا كاملة.
- **المناطق** (19): `mold-requests`، `design-files`، `mold-customers`، `erp`، `customer-service` (الطلبات والمساندة والشكاوى والتقارير والتقييم معًا لأن لوحاتها تستورد بعضها)، `tracking`، `visits`، `followups`، `customers`، `machines`، `map`، `targets-sales`، `competitors`، `members-regions`، `app-update-android`، `build-notice`، `offline-pwa`، `theme`، `deploy-packaging`. بُنيت من شجرة الاستيراد (`app/` و`lib/` و`portable/`) ومن المسارات والصفحات التي يفتحها كل اختبار، لا من الأسماء: مثلًا `pwa-browser` يفتح صفحة طلبات القوالب فهو في منطقتها، و`mobile-comfort-browser` يفتح العملاء والزيارات والمتابعات والأهداف والخريطة فهو في مناطقها وليس في القوالب، و`server-authorization` يمرّ على كل المسارات فهو في كل منطقة لها مسار.
- **المشترك** (قائمة `shared`): ما تستورده أغلب الصفحات أو المسارات — كل ما يصل إليه `lib/crm-server.ts` (الذي يمرّ به كل مسار: `crm` و`access` و`regions` و`request-body` و`customer-service` و`visits` و`customer-visits` و`customer-fields` و`customer-location` و`kingdom*` و`decimal-money` و`member-email` و`customer-identity*` والمصادقة)، و`app/crm-app.tsx` و`page`/`layout` والـCSS العامة والتنقّل وتسجيل الدخول، و`components/**` و`hooks/**`، و`i18n` و`client-submit` و`utils` والإملاء (`voice-field` و`native-speech`) و`upload-status`، وغلاف العمل دون اتصال (`offline-*` و`offline-entry` و`public/sw.js` و`public/offline.html`)، و`/api/crm` و`/api/auth`، و`db/` و`drizzle/`، ومسار إقلاع النسخة المبنية (`portable/app.cjs` و`upgrade` و`initialize` و`runtime` و`storage` و`local-mail` و`passenger-client`)، والبناء (`scripts/build-*`)، وأدوات الاختبار المشتركة (`scripts/lib/built-app.mjs` و`native-bridge.mjs`)، و`check-manifest.json` و`test-areas.json` نفسه، و`package.json` والقفل وإعدادات Next/Vite/TypeScript/PostCSS. ملف تستورده منطقتان أو ثلاث فقط يُكتب في كل منطقة منها بدل جعله مشتركًا.
- **الفشل والتخطي لا يُخفيان:** اختبار فشل في المجمّع يُعاد مرة وحده بعد انتهاء المجمّع: لو فشل ثانية فهو «failed»، ولو نجح فهو «flaky» (نجح عند الإعادة) ويظهر في الجدول والملخص بسجلّي المحاولتين. البوابة الافتراضية تعيد هي نفسها ما فشل فيها وحده (وتُكتب «flaky» هنا لو نجح، بأسماء البنود)، وما بقي فاشلًا تُعاد بنوده الفاشلة فقط مرة أخرى بعد المجمّع، بنفس أمر `check.mjs`. البوابتان `erp-workbook` و`erp-customers-workbook` و`tests/erp-sales-browser.mjs` (يقرأ `ERP_TEST_WORKBOOK` أو `../../upload/Reports_Invoices_14480422_094904.xlsx` كما يفعل الاختبار) تُعرض «skipped: needs the owner's ERP file» حين لا يوجد الملف، لا نجاحًا ولا فشلًا؛ وتعمل لو وُجد. الخروج 0 فقط لو لم يفشل شيء.
- **تعمل وحدها** (`serial`): `perf-budget-browser` (ميزانيات زمنية على هاتف أبطأ 4 مرات؛ حمل الاختبارات الأخرى على نفس المعالجات يُفشلها لسبب لا علاقة له بالكود) و`production-load` (حمل 60 ث لا تصف أرقامه النسخة إلا والجهاز فاضي، ويشبع المعالجات التي تعتمد عليها مهلات غيره).
- **الناتج:** جدول قصير على الشاشة و`output/gates/<run>/summary.json`: لكل اختبار البوابة والحالة والثواني وعدد الفحوص (إن طبعه) والسجل، والمجاميع، والزمن الكلي، والقاعدة التي طُبّقت وسببها (المناطق والملفات المشتركة وغير المغطاة).
- **الاختبار:** `tests/test-areas.mjs` (البوابة الافتراضية): الخريطة JSON صحيح؛ كل اختبار `release-build`/`browser` في الـmanifest داخل منطقة؛ كل glob يطابق ملفًا موجودًا؛ والاختيار على أمثلة (ملف قوالب ← اختبارات القوالب؛ `lib/access.ts` وغيره من المشترك ← الكل؛ ملف مجهول ← الكل ويُسمّى؛ مستندات عامة ← لا شيء، ومستند منطقة ← منطقته؛ ملفات مولّدة ← لا شيء).
- **عند إضافة اختبار `release-build` أو `browser`:** ضعه في منطقة (أو أكثر) في `tests/test-areas.json` وإلا يفشل `tests/test-areas.mjs`. عند إضافة ملف مصدر جديد لا تغطيه منطقة، يعمل كل شيء حتى تضيفه.
- **الحزمة والبروفة** خطوتان منفصلتان كما هما (`scripts/package-*.py` و`scripts/rehearse-update.mjs`).

- **القياس على هذا الجهاز (4 معالجات، 15 GB، 2026-11-05):** التتابع السابق نحو 55 دقيقة (البناء والبوابة الافتراضية و19 اختبار بناء و30 متصفح). `npm run gates -- --full`: 11 د 19 ث ثم 11 د 34 ث (49 ناجحًا و3 «skipped» لملفات ERP، ولا flaky)؛ بالمجمّع 4/3 كان 15 د، وبـ8/6 كان 10.5 د مع فشل إضافي تحت الحمل، فالافتراضي 6/5. تعديل القوالب وحده (`--since 2bbcbac --to 6e3316f`، 7 اختبارات): 6 د 48 ث، وأطولها كان البوابة الافتراضية نفسها؛ بعد أن صارت متوازية (`check.mjs --jobs 4` بجانب المجمّع): 4 د 13 ث، وأطولها الآن `mold-requests-browser` (نحو 3.7 د)، والتشغيل الكامل 11 د 6 ث. تشغيلات التوازي الأولى كشفت ثلاثة اختبارات تعتمد على التوقيت فأُصلحت دون تغيير ما تفحصه: `build-notice-browser` ينتظر تحميل كلمات الإنجليزية قبل قراءة التنبيه، و`offline-browser` يعطي التبويب الثاني جسر التطبيق مثل الأول (بدونه كانت بوابة التتبع تحجبه تحت الحمل)، و`visit-file-concurrency` (بوابة افتراضية) حارس التعليق فيه 15 ث بدل 3.

## إصلاحات تجهيز الاختبارات

تم تحديث توقعات قديمة فقط لتوافق سياسات المصدر الحالية: المدير يقدر يحذف الزيارة، والمندوب يعدّل بيانات العميل لكن لا يعدّل أو يحذف الزيارات؛ عدم وجود احتياج لا يملأ صنفًا افتراضيًا؛ والأدلة المحفوظة بدون شبكة لا تنتهي بعد48 ساعة. تم تصحيح تاريخ إنشاء حساب fixture قبل فترة تتبعه، والمحافظة على رفض البيانات خارج اليوم والصلاحية والترتيب.

كذلك تم استكمال mock لـ`useRef` والتخزين دون شبكة، واختيار اشتراك الشاشة بدل افتراض ترتيب effects، واختبار اختيار المنطقة بالراديو، وتحديث نصوص الواجهة وعدد migrations. اختبار migration-manifest يشغّل منطق التجميع الحقيقي مع stub لبناء الواجهة، ولا يدّعي بناء التطبيق بالكامل. هذه تعديلات بنية اختبار، ولا تُحسب كإصلاحات أمان في المنتج.

## تشغيل اختبارات المتصفح في بيئة معزولة

```bash
export CODEX_PRIMARY_RUNTIME_NODE_MODULES=/path/to/node_modules   # يحتوي playwright
export YR_BROWSER_EXECUTABLE=/path/to/chromium
env -u HTTPS_PROXY -u https_proxy NO_PROXY='*' \
  YR_COMPETITORS_SCREENSHOT_DIR=/tmp/shots YR_COMPETITORS_REPORT=/tmp/report.json \
  node tests/competitors-browser.mjs
```

- عطّل متغيرات الوكيل (proxy) وإلا تُعاد الاتصالات إلى المضيف المحلي.
- وجّه مخرجات الأدلة إلى مجلد مؤقت بمتغيرات `YR_*_SCREENSHOT_DIR` و`YR_*_REPORT`؛ بعض الاختبارات تكتب افتراضيًا فوق ملفات الأدلة داخل `docs/`.
- `tests/offline-browser.mjs` و`tests/pwa-browser.mjs` و`tests/app-browser-workflows.mjs` تحتاج متصفحًا يطبّق محاكاة انقطاع الشبكة ورفض إذن الموقع على عامل الخدمة والسياق الافتراضي (وضع المتصفح عبر CDP بمتغير `YR_BROWSER_CONTENT_SHELL=1`). في Chromium العادي عبر Playwright تتوقف عند خطوة الإقلاع البارد دون اتصال وخطوة رفض الإذن؛ هذا قيد في أداة المحاكاة وليس في التطبيق (راجع `docs/qa/REPORT-AR.md`).
- `tests/erp-sales-browser.mjs` يحتاج ملف ERP الأصلي (`ERP_TEST_WORKBOOK`).
