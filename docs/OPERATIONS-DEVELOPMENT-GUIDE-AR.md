# دليل التشغيل والتطوير والتحديث — Yourrest CRM

هذا الدليل للمطوّر ومسؤول الاستضافة. يشرح تشغيل المشروع محليًا، واختباره، وبناءه، وتحديثه على الاستضافة مع الحفاظ على البيانات والإعدادات. لا تنشر شيئًا على الموقع الفعلي إلا بعد تجربة النسخة محليًا وأخذ نسخة احتياطية.

## 1. المتطلبات

| العنصر | الإصدار |
|---|---|
| Node.js | 22.16 أو أحدث (التطبيق يستخدم `node:sqlite` المدمج) |
| pnpm | 11 (`corepack enable` ثم `pnpm --version`) |
| Chromium + Playwright | اختياري، لاختبارات المتصفح فقط |
| Python 3 و`unzip` | اختياري، لسكربتات التغليف واختبارات الحزم |

لا توجد قاعدة بيانات خارجية: التطبيق يحفظ كل شيء في ملف SQLite ومجلد مرفقات خاصين.

## 2. أول تشغيل للتطوير

```bash
pnpm install --frozen-lockfile   # تثبيت الاعتمادات المقفلة
pnpm typecheck                   # فحص الأنواع
pnpm lint                        # ESLint
pnpm check                       # الأنواع + كل الاختبارات الافتراضية (نحو 6 دقائق)
pnpm build                       # البناء إلى dist/standalone
```

ملاحظات:
- إذا رفض pnpm تثبيت إصدار حديث بسبب `minimumReleaseAge` في `pnpm-workspace.yaml`، فهذه سياسة أمان مقصودة. لا تعطّلها في المشروع؛ استخدم الإصدارات المقفلة في `pnpm-lock.yaml`.
- كل الاختبارات تستخدم بيانات اصطناعية وقواعد SQLite مؤقتة. لا تحتاج إعدادات إنتاج ولا تلمس بيانات حقيقية.
- `pnpm check` ينفّذ الأنواع ثم كل ملف في `tests/` ما عدا الاستثناءات الموثقة في `tests/check-manifest.json`. إضافة ملف اختبار `.mjs` جديد لا تحتاج تسجيله.

## 3. تجربة التطبيق محليًا

بعد `pnpm build`:

```bash
pnpm demo
```

يشغّل النسخة المبنية ببيانات اصطناعية (ستة حسابات بأدوار مختلفة وثلاثة عملاء) على عنوان مثل `https://crm.yourrest.org:8443` بشهادة موقعة ذاتيًا. رموز الدخول تظهر في الطرفية عند طلبها ولا يُرسل أي بريد حقيقي. عند الإيقاف بـ Ctrl+C تُحذف بيانات التجربة.

لأن التطبيق يشترط أصل HTTPS، افتح العنوان بإحدى طريقتين:

1. Chrome بملف تعريف مؤقت (الأنظف):
   ```bash
   chrome --user-data-dir=/tmp/yr-demo --ignore-certificate-errors \
     --host-resolver-rules="MAP crm.yourrest.org 127.0.0.1" https://crm.yourrest.org:8443
   ```
2. أو إضافة السطر `127.0.0.1 crm.yourrest.org` إلى ملف hosts أثناء التجربة فقط، وحذفه بعدها.

لتغيير المنفذ: `DEMO_PORT=9443 pnpm demo`. الحسابات: `owner` و`admin` و`manager` و`supervisor` و`rep.east` و`rep.west` و`service` بنطاق `@yourrest.org`.

لتجربة الهاتف: في أدوات المطور اختر شاشة 390 بكسل أو جهازًا محمولًا. الوضع الليلي من المفتاح في الشريط العلوي.

## 4. الإعدادات والأسرار

- الإعدادات الحقيقية في ملف `settings.cjs` **خارج** مجلد الإصدار وخارج `public_html`، بصلاحية خاصة (600).
- `node setup.cjs` عند أول تثبيت على الاستضافة ينشئ `settings.cjs` بسرّ عشوائي جديد ومجلدات البيانات الخاصة. لا تشغّله على تثبيت قائم.
- القالب الخالي من الأسرار: `settings.example.cjs`. ومتغيرات البيئة النموذجية: `.env.example`.
- المفاتيح: `YR_APP_ORIGIN` و`YR_AUTH_SECRET` (64 خانة سداسية عشرية أو أكثر) و`YR_DATABASE_PATH` و`YR_OBJECTS_PATH` و`YR_MAIL_TRANSPORT` و`YR_MAIL_FROM` و`YR_SENDMAIL_PATH`، واختياريًا `YR_NATIONAL_ADDRESS_API_KEY`.
- تغيير `YR_AUTH_SECRET` يسجّل خروج كل المستخدمين. لا تضع السر في المستودع أو في السجلات.
- عند وجود `settings.cjs` يرفض التطبيق أي قيمة `YR_*` مختلفة في متغيرات البيئة.
- مفتاح توقيع أندرويد يُسلّم منفصلًا ولا يُنشر ولا يدخل المستودع.

## 5. بنية المشروع

| المسار | المحتوى |
|---|---|
| `app/` | الصفحات والمكونات ومسارات API (`app/api/*`) |
| `lib/` | القواعد الأساسية: الصلاحيات (`access.ts`)، المستهدفات (`targets.ts`)، أوزان التقييم (`kpis.ts`)، المبيعات، استيراد ERP، المزامنة دون شبكة |
| `db/` و`drizzle/` | المخطط وترحيلات SQL التراكمية (16 ملفًا؛ آخرها `0015_member_devices.sql`) |
| `portable/` | طبقة الاستضافة: التشغيل والإعداد والنسخ الاحتياطي والاسترجاع والترقية |
| `scripts/` | البناء والتغليف والتجربة المحلية؛ `scripts/lib/built-app.mjs` يشغّل النسخة المبنية للاختبارات |
| `tests/` | اختبارات الانحدار والأمان والمتصفح والإصدار |
| `mobile/android` | مصدر أندرويد (لا يُبنى هنا) |

## 6. قواعد التطوير الآمن

1. **الصلاحيات على الخادم دائمًا.** إخفاء زر في الواجهة ليس حماية. أي مسار جديد في `app/api` يتحقق من الجلسة ثم الدور ثم نطاق السجل، ويُضاف إلى `tests/server-authorization.mjs`.
2. **لا تعدّل المعادلات** (أوزان التقييم، تجميع المشرف ومدير المبيعات، المستهدفات الممتدة بالتواريخ) إلا بقرار أعمال، ومع اختبارات تثبّت الأرقام.
3. **الترحيلات تراكمية فقط.** لا تعدّل ملفًا في `drizzle/` طُبّق من قبل؛ أضف ملفًا جديدًا. التثبيت القائم يأخذ نسخة من المخطط قبل أي ترحيل.
4. **التواريخ بتوقيت الرياض.** استخدم `today()` من `lib/crm.ts` ولا تستخدم تاريخ جهاز المستخدم أو `toISOString()` على اللحظة الحالية.
5. **أنواع دقيقة بلا `any`** ولا `eslint-disable`. فحص ESLint صفر أخطاء وجزء من `npm run check`: أي خطأ جديد يُفشل البوابة. الاستثناءات المراجَعة (قواعد React Compiler الذي لا يستعمله المشروع كتحذيرات، سكربتا ما قبل الرسم في `app/layout.tsx`، و`any` في `Row.data` والمستهدفات ومسار CRM) مكتوبة بأسبابها في `eslint.config.mjs`، لا في تعليقات متفرقة.
6. **استيراد جديد بين الوحدات** قد يكسر اختبارات تحقن التبعيات بأسماء محددة (مثل `tests/journey-ui.mjs`). استخدم `import type` للأنواع، وحدّث الاختبار إذا أضفت استيرادًا فعليًا.
7. **ملفات يولّدها البناء** (`public/offline-app/**` و`public/sw.js` و`public/offline-shell-manifest.json`) تتغير عند تغيير كود الواجهة. شغّل `pnpm build` وثبّتها في commit منفصل.
8. اختبارات المتصفح تكتب أدلة في `docs/`؛ وجّه مخرجاتها إلى مجلد مؤقت بمتغيرات `YR_*_SCREENSHOT_DIR` و`YR_*_REPORT` كي لا تتغير الأدلة المحفوظة.

## 7. الاختبارات

| البوابة | الأمر | تحتاج |
|---|---|---|
| الافتراضية | `pnpm check` | لا شيء إضافي |
| بعد البناء | `node tests/server-authorization.mjs` و`node tests/sales-date-boundaries.mjs` و`node tests/namecheap-http.mjs` و`node tests/app-update-release.mjs` | `pnpm build` |
| المتصفح | `node tests/<name>-browser.mjs` | `pnpm build`، Playwright، Chromium |
| ملف ERP الأصلي | `ERP_TEST_WORKBOOK=/path/file.xlsx pnpm check:erp` | ملف التقرير الأصلي |
| حزم الإصدار | اختبارات `tests/*-update-package.py` | حزمة إصدار مصدّرة |
| أندرويد | `mobile/android` | JDK وAndroid SDK والتوقيع |

لتشغيل اختبارات المتصفح في بيئة معزولة:

```bash
export CODEX_PRIMARY_RUNTIME_NODE_MODULES=/path/to/node_modules   # يحتوي playwright
export YR_BROWSER_EXECUTABLE=/path/to/chromium
env -u HTTPS_PROXY -u https_proxy NO_PROXY='*' node tests/competitors-browser.mjs
```

إذا كانت بيئتك خلف وكيل (proxy)، عطّله لهذه الاختبارات وإلا يُعاد الاتصال بالمضيف المحلي. جزء من اختبارات الوضع دون اتصال وPWA يعتمد على محاكاة انقطاع الشبكة في Chromium؛ راجع حدودها في تقرير المراجعة.

## 8. البناء والتغليف

```bash
pnpm build        # ينشئ dist/standalone (التطبيق + مجلد operations + الترحيلات + manifest)
```

حزمة الاستضافة التراكمية تُنشأ بسكربتات `scripts/package-*.py` (مثل `package-namecheap.py`)، وهي تنسخ `dist/standalone` ومعها التعليمات والأدلة. هذه السكربتات تاريخية ومرتبطة باختبارات `tests/*-update-package.py`؛ لا تحذفها قبل توحيدها بقرار منفصل.

## 9. التحديث على الاستضافة مع الحفاظ على البيانات

البيانات والإعدادات خارج مجلد الإصدار، لذلك استبدال `release` لا يمسها. اتّبع الترتيب بدقة:

1. **نسخة احتياطية قبل أي تحديث** (يمكن أخذها والتطبيق يعمل):
   ```bash
   node /home/ACCOUNT/yourrest-crm/release/operations/backup-scheduled.mjs /home/ACCOUNT/yourrest-crm-backups 14
   ```
   تأكد أن الناتج `ok:true` وأن `status.json` يظهر `state: ok`. التفاصيل واستعادة نسخة: `docs/PRODUCTION-BACKUP-AR.md`.
2. من cPanel > **Setup Node.js App** اختر التطبيق ثم **Stop App**.
3. فكّ الحزمة داخل مجلد التطبيق مع **استبدال `release` فقط**. لا تستبدل `settings.cjs`، ولا مجلد البيانات `yourrest-crm-data`، ولا ملف قاعدة البيانات.
4. **لا تشغّل** `setup.cjs` ولا `npm install` على تثبيت قائم.
5. **Start App.** عند الإقلاع يطبّق التطبيق الترحيلات الجديدة فقط على قاعدة معروفة، بعد نسخة خاصة من المخطط. إذا توقف الإقلاع فراجع سجل التطبيق ولا تحذف قاعدة البيانات.
6. افتح الموقع وسجّل الدخول وتحقق من: الدخول، قائمة العملاء، تسجيل زيارة، صفحة المستهدفات. افتح التطبيق مرة أثناء الاتصال ثم أغلقه وافتحه لتفعيل واجهة الوضع دون اتصال.
7. تطبيق أندرويد لا يتحدث تلقائيًا برفع السيرفر؛ ثبّت APK الجديد (نفس التوقيع) فوق القديم دون حذفه إذا تغيّر إصدار الأندرويد.

**التراجع:** أوقف التطبيق وأعد `release` السابق. إذا لزم استرجاع البيانات فاستعدها إلى **مجلد خاص جديد** (الأداة ترفض الكتابة فوق مجلد قائم):

```bash
node /home/ACCOUNT/yourrest-crm/release/operations/restore.mjs verify  /home/ACCOUNT/yourrest-crm-backups/BACKUP_NAME
node /home/ACCOUNT/yourrest-crm/release/operations/restore.mjs restore /home/ACCOUNT/yourrest-crm-backups/BACKUP_NAME /home/ACCOUNT/yourrest-crm-restored
```

ثم وجّه `YR_DATABASE_PATH` و`YR_OBJECTS_PATH` في `settings.cjs` إلى المجلد المسترجع وشغّل التطبيق. لا تحذف قاعدة البيانات الأصلية قبل التأكد من سلامة المسترجعة.

## 9-ب. بناء حزمة التحديث وبروفتها قبل الرفع

حزمة الاستضافة التي تُرفع على cPanel تُبنى من `dist/standalone` بسكربت التغليف الذي يثبّت بصمة كل ملف داخل مُفعِّل مستقل. لا تُرفع حزمة السورس نفسها.

```bash
pnpm install --frozen-lockfile && pnpm build
python3 scripts/package-ui-refresh-update.py \
  --release dist/standalone --output /مسار/خارج/المستودع/Yourrest-CRM-Update-YYYYMMDD.zip \
  --release-name update --release-date YYYYMMDD \
  --stage-name yourrest-crm-update-YYYYMMDD --helper-name yourrest-activate-update.cjs \
  --guide docs/UPDATE-YYYYMMDD-AR.txt
```

الدليل يجب أن يذكر اسم مجلد الرفع واسم المُفعِّل وإلا يرفض السكربت.

**قائمة أسماء التحديثات السابقة:** المُفعِّل يعيد استعمال نسخة اليوم الاحتياطية لو أخذها مُفعِّل تحديث سابق في اليوم نفسه، ولا يقبل إلا مجلدات نُسخ باسم معروف: `BACKUP_TRANSACTION` في `portable/activate-ui-refresh-update.cjs` (الأسماء الثابتة، ثم اسم الحزمة نفسها تلقائيًا). **كلما سُلِّمت حزمة بهوية جديدة أضف اسم نشاط حزمتها (`yourrest-<release-name>-activation-<date>`) إلى هذه القائمة قبل أن تُبنى الحزمة التي بعدها**، وإلا رفضها المُفعِّل بـ`STOP: INVALID_DAILY_BACKUP_INDEX` حين يكون التحديث الثاني في اليوم نفسه (حدث هذا لحزمة مسار المساندة بعد حزمة رسالة العميل؛ والاختبار `tests/baseline-update-activation.mjs` يغطي الآن حزم 17 و18 أكتوبر).

**ترحيل جديد داخل الحزمة:** القاعدة الحية يجب أن تكون على الخط الأساسي. الأساسي الافتراضي 15 ترحيلًا (إصدار 2026-10-11)، ومن بنى فوق إصدار فيه ترحيلات أكثر يعلنه بـ`--schema-baseline N` (يُقبل من 15 إلى 99)، فمثلًا بعد تفعيل إصدار 2026-10-12 (16 ترحيلًا) تُغلَّف الحزمة التالية بلا ترحيل جديد بالأمر `--schema-baseline 16`. أي ترحيل بعده تُعلنه صراحة عند التغليف، وتشترط الحزمة أن يحمل البناء الترحيلات الأساسية + المعلنة بالضبط وإلا ترفض:

```bash
python3 scripts/package-ui-refresh-update.py ... \
  --new-migration 0015_member_devices.sql --verify-route /api/device-status=401
```

- `--new-migration` (يتكرر): اسم الترحيل بالضبط كما في `drizzle/`.
- `--schema-baseline N`: عدد الترحيلات في القاعدة الحية قبل هذه الحزمة. تشترط الحزمة أن يحمل البناء N ترحيلًا + المعلنة بالضبط، ويشترط المُفعِّل ذلك على القاعدة الحية عند `apply` (لا عند `--check`، فالتطبيق يعمل أثناءه). وهو يقبل نسخة اليوم الكاملة التي أخذها مُفعِّل سابق في اليوم نفسه بتوقيت الرياض ولو كانت عند ترحيلات أقل، فلا تُنسخ البيانات مرة ثانية.
- `--verify-route PATH=STATUS` (يتكرر): مسار جديد يفحصه `--verify` بلا جلسة (المتوقع هنا 401).
- المُفعِّل لا يكتب في القاعدة ولا يشغّل الترحيل. `--check` يعلن التغيير، والتطبيق يطبّقه عند أول Start بعد نسخة خاصة في `yourrest-crm-data/schema-backups`، و`--verify` يرفض بسبب واضح (`MIGRATION_NOT_APPLIED_START_APP_FIRST`) إن لم يبدأ التطبيق، ثم يتأكد من 16 ترحيلًا ومن بقاء كل معرفات السجلات.
- **لا رجعة بسيطة بعد الترحيل:** الإصدار القديم يرفض قاعدة فيها ترحيل أحدث. التراجع بعد نجاح الترحيل = استعادة نسخة `schema-backups` + إعادة `old-release` (دليل التحديث يشرحه، وأي بيانات بعد التشغيل تضيع). قبل الترحيل لا خسارة.
- اختبار حزمة بلا ترحيل فوق قاعدة مرحَّلة (16→16) وإعادة نسخة اليوم: `node tests/baseline-update-activation.mjs`.
- اختبار هذا المسار كاملًا: `node tests/schema-update-activation.mjs` (الحزمة الحقيقية والمُفعِّل الحقيقي وروتين الإقلاع الحقيقي على SQLite).

**بروفة كاملة قبل الرفع** (ببيانات اصطناعية، دون أي اتصال بالاستضافة): ابنِ الإصدار المثبّت حاليًا في مجلد منفصل ثم نفّذ بحساب غير مميز كما على الاستضافة:

```bash
node scripts/rehearse-update.mjs --old-release /مسار/dist/standalone-القديم --package /مسار/Yourrest-CRM-Update-YYYYMMDD.zip --out report.json
```

تُنشئ البروفة موقعًا مثبّتًا كالاستضافة، وتشغّل الإصدار القديم وتنشئ بيانات عبر واجهته، ثم تتبع خطوات الدليل: `--check` والتطبيق يعمل، رفض التبديل ما دام برنامج غير خادم Node.js يمسك مجلد التطبيق (`sleep` حقيقي)، ثم تشغيل التطبيق كما يفعل المضيف بعد Stop App وإيقاف المُفعِّل له بنفسه ومتابعته، الإيقاف والتبديل، التشغيل و`--verify`، ثم تثبت أن كل جدول ومرفق والإعدادات والواجهات لكل دور متطابقة، وأن حزمة معطوبة تُرفض دون لمس شيء. المُفعِّل يشترط أصل الموقع `https://crm.yourrest.org` تمامًا، لذلك تحتاج البروفة المنفذ 443 (صلاحية ربط المنافذ المنخفضة فقط).

عند إعلان ترحيل جديد تجرّب البروفة أيضًا طريقي التراجع بالخطوات نفسها المكتوبة في دليل التحديث: (أ) العودة قبل أول تشغيل للإصدار الجديد بإعادة `old-release`، و(ب) العودة بعد الترحيل. في (ب) تثبت أن الإصدار القديم يرفض القاعدة المرحَّلة، وأن استعادة نسخة `schema-backups` مع المجلد القديم تعيد كل جدول وكل واجهة إلى حالتها قبل التحديث. **ملفا `database.sqlite-wal` و`database.sqlite-shm` يبقيان بعد إيقاف التطبيق** ويجب إزاحتهما مع `database.sqlite` قبل نسخ النسخة الخاصة، وإلا اختلطا بالقاعدة المستعادة.

## 9-ج. إلزام تتبع المسار وحالة هاتف المندوب

## 9-هـ. مساندة خدمة العملاء والزيارات المفقودة وتأخر الاعتماد

**القاعدة:** مساندة خدمة العملاء (ما يفتحه المندوب وما يتولاه الممثل من الزيارات المفقودة) سجل مستقل من النوع `support` يسير المسار نفسه الذي تسير عليه الشكاوى: الممثل يتواصل ويرفع، مدير الخدمة يعتمد أو يعيد، مدير المبيعات يكلّف، المشرف يفوّض، المندوب يسجّل تواصله بقناته، ثم يغلق الممثل أو يعيد إلى المندوب. الوصف الكامل في `docs/CUSTOMER-SERVICE-WORKFLOW-AR.md` (القسم 9) والخطة في `docs/qa/PLAN-SUPPORT-CHAIN-AR.md`.

| الملف | الدور |
|---|---|
| `lib/support.ts` | المنطق الخالص: من يطلب ومن يقرأ ومن يتصرف (`canRequestSupport` و`canReadSupport` و`supportPermissions`)، والمرحلة والتقدم (`supportStage` و`supportProgress` و`supportOwner`)، وسير الطلب (`supportEvents` يركّب سيرًا للصفوف القديمة)، والمرشحون للإحالة والتكليف والتفويض (`supportCandidates`)، وما ينتظر القارئ (`supportAwaiting`)، توجيه الطلب لممثل المنطقة (`supportStaff`)، قائمة الطلبات (`supportQueue`) والمفقودة (`missedVisits`) والعدّاد (`supportBadge`) وأقسام اللوحة (`supportGroups`)، وروابط الاتصال (`contactLinks`). الثوابت المسماة وحدها: `SUPPORT_TARGET_HOURS=4` و`SUPPORT_STAGE_HOURS` (مراجعة 4، تكليف 4، تفويض 4، أول تواصل 24، إغلاق 24) و`MISSED_VISIT_GRACE_DAYS=2` و`MISSED_VISIT_WINDOW_DAYS=30` و`SUPPORT_HISTORY_DAYS=30` و`SUPPORT_LIST_LIMIT=300` (حدّ العرض لا العدّ: `GET` يحسب القائمة كاملة ويقصّ العرض ويعيد الأعداد الكلية في `counts` والتولّي يبحث في الكاملة). اختباره `tests/support.mjs` |
| `app/api/support/route.ts` | `GET` (ما يراه القارئ) و`POST` بإجراءات `request` و`take` و`assign` و`submit` (رفع نتيجة الممثل؛ أول رفع هو ما يقيسه التقييم) و`forward` و`return` و`allocate` و`delegate` و`reassign` و`resolve` و`reject` و`close` و`cancel` و`seen`، بإيصالات `support-receipt` وفحص النسخة وإعادة فحص الأعضاء عند الحفظ. اختباره `tests/support-http.mjs` |
| `app/support-panel.tsx` و`app/support-panel.css` | الزر `SupportButton`، واللوحة `SupportPanel`، ونموذج الطلب `SupportRequestDialog`، ونافذة الطلب `SupportSheet`، وخطاف التحميل `useSupport` (يحمّل بعد لقطة الصفحة وبحد أقصى مرة كل 15 ثانية لإعادات الصفحة نفسها، وكل 10 دقائق، وفورًا بعد أي تغيير يجريه صاحب الحساب). اختباره `tests/support-ui.mjs` و`tests/support-browser.mjs` |
| `app/visits-table.tsx` و`app/customer-visits.tsx` و`app/customer-followup-list.tsx` | موضع الزر: آخر زيارة لكل عميل في الجدول، ورأس سجل زيارات العميل، وخطة العميل في المتابعات |
| `lib/service-queue.ts` | لمدير خدمة العملاء: طلبات الاعتماد التي تنتظره فقط (مرحلة `approval` وصلاحية `approve`) بالساعة نفسها وعلامة التأخر والعدّاد |

**التخزين بلا ترحيل:** كل طلب سجل في `crm_records` من النوع `support` بلا أب (`parent_id` فارغ)، وكل ما يخصه في `data` (الحالة `open|submitted|returned|pending_assignment|assigned|resolved|done|cancelled`، والعميل والطالب والمسؤول والمتولّي ومدير الخدمة ومدير المبيعات والمشرف والمندوب المكلَّف، ونتيجة الممثل `result` ونتيجة المندوب `resolution` والإغلاق `closure` وسير الطلب `events`؛ كلها اختيارية فتبقى الصفوف القديمة صالحة). لذلك لا تراه قواعد الزيارات ولا الطلبات ولا حذف العميل، ويتجاهله الإصدار القديم، ويستبعده `scopeRecords` من سجلات مدير النظام. التراجع = إعادة مجلد `release` القديم فقط دون استعادة القاعدة. حذف عميل له طلبات يمرّ، وتبقى طلباته مخفية. لا تخزّن طلبًا بنوع `activity` أبدًا: سيُحسب زيارة ويصير خطة العميل الأخيرة.

**الزيارة المفقودة مشتقة عند القراءة** من خطة العميل الأخيرة (`customerPlanSource`) على كل السجلات لا على نطاق القارئ، فلا جدول ولا مهمة مجدولة. لا يُكتب شيء حتى يتولاها أحد، وحينها يُنشأ السجل بمعرّف ثابت `support-missed-<معرّف الزيارة>` فلا يتولاها اثنان. لا يرى ممثل الخدمة من الزيارة إلا الخطة (الإجراء والموعد والنتيجة) واسم المندوب.

**الصلاحيات:** المندوب والمشرف والمدير يطلبون لعملاء فريقهم أو لعميل زاروه، وخدمة العملاء لا تطلب. التولّي والتواصل والرفع والإغلاق لممثل الخدمة ضمن فرع العميل ومنطقته، والاعتماد لمدير الخدمة الذي يتبعه الممثل، والتكليف لمدير المبيعات المربوط به المدير (`salesManagerId`) وحده وإن رأى كل مدير مبيعات فريق الطلب، والتفويض للمشرف المكلَّف. الإلغاء قبل التكليف لصاحب الطلب ومن فوقه ولمدير الخدمة (للمفقودة ولما يراجعه)، ولمدير النظام في أي مرحلة مفتوحة. حارس الطلب المفتوح الواحد لكل عميل (`OPEN_CUSTOMER`) يمتد على المسار كله. أي مسار جديد بعد هذا يمرّ على `tests/server-authorization.mjs`.

الأرقام للمتابعة: لا تدخل في حركة ولا زيارة ولا مستهدف ولا تقييم المناديب؛ وتقرؤها «تقييم خدمة العملاء» (القسم 9-ط) لتقييم ممثلي الخدمة ومديريها. لا تجعل مهلة تمنع إجراءً أو تغيّر صلاحية.

## 9-و. موقع العميل الجديد: موقع الجهاز أو موقع آخر

**القاعدة:** موقع العميل الجديد يُلتقط من الجهاز افتراضيًا كما كان. «موقع آخر» اختيار صريح من العضو: يكتب الإحداثيات أو يلصق رابط خرائط كاملًا فيه الإحداثيات، أو يضغط المكان على الخريطة ويسحب الدبوس ثم يؤكد. لا يتغير موقع عميل قائم عند فتحه، ولا موقع الزيارة (يبقى من الجهاز)، ولا شيء مما يستند إلى الموقع بعد الحفظ (خريطة المصانع والاتجاهات وفحص الوصول).

| الملف | الدور |
|---|---|
| `app/customer-entry-fields.tsx` | `CustomerLocationFields`: اختيار المصدر بأزرار اختيار حقيقية (`customer-choice`)، التقاط الجهاز، كتابة المكان، `applyPoint` للمكان المكتوب أو المختار، `lookup` للعنوان الوطني. يستعمله نموذج العميل في `app/crm-app.tsx` و«إضافة عميل» في `app/visit-customer-picker.tsx` |
| `app/location-picker.tsx` و`app/location-picker.css` | نافذة الخريطة (Leaflet وبلاطات OpenStreetMap كخريطة المصانع): نقرة تضع الدبوس، سحب يعدّله، و«وضع الدبوس في وسط الخريطة» دون لمس. تبدأ على المكان المكتوب ثم منطقة العميل ثم المملكة. لا يتغير شيء قبل «تأكيد الموقع». ملاحظة ظاهرة إن تعذر تحميل الخريطة أو البلاطات (دون إنترنت) |
| `lib/customer-location.ts` | `coordinatesFromText`: ما يُقرأ إحداثيات (زوج بفاصلة عادية أو عربية، `@lat,lng`، `?q=` و`query=`)، ولا شيء غير ذلك: لا اسم مدينة ولا رابط مختصر. و`tidyLocationText`: رابط يحمل إحداثيات يصير الزوج الذي يشير إليه (الحقل 250 حرفًا والروابط أطول) |
| `lib/customer-fields.ts` | `prepareCustomerLocation` قواعد الخادم، و`customerLocationProblem` يطبقها على نسخة في النموذج قبل الحفظ أو الوضع في طابور الجهاز دون الحكم على ساعة الهاتف |

**ما يُخزَّن:** المكان اليدوي رقمان `latitude` و`longitude` يحسبهما الخادم من النص، بلا `locationSource` ولا `locationCapturedAt` ولا `locationAccuracy`: لا يُسمّى التقاطًا. ادعاء التقاط لا يطابق النص يُرفض ولا يُعاد وسمه. الخادم لم يتغير في هذا الإصدار.

**الفحص قبل الحفظ:** نص ليس إحداثيات يُشرح فور كتابته ويُرفض في النموذج قبل أي طلب، حتى دون اتصال، لأن العميل المحفوظ على الجهاز لا يفحصه الخادم إلا عند المزامنة وقد فات تصحيحه. لا يحكم الفحص على وقت الالتقاط بساعة الهاتف: وقت الموقع قد يأتي من نظام التحديد ويختلف عن ساعة الجهاز، فالحكم عليه للخادم وحده.

**العنوان الوطني:** يُجلب بعد المكان المكتوب عند مغادرة الحقل ولا يحجز الحفظ (الضغط على «حفظ» هو نفسه ما يغادر الحقل فلا يُضيَّع)، وبعد المكان المختار على الخريطة ويحجز الحفظ حتى يصل أو تنتهي مهلته (12 ثانية)، كالمكان الملتقط. يملأ الحقول الفارغة فقط، ويُمسح ما مُلئ تلقائيًا لمكان سابق إن لم يغيّره العضو، ولا يستبدل جواب متأخر ما كُتب بعده. دون اتصال يُتجاوز. المزوّد غير مفعّل على الاستضافة، فتظهر عبارة «غير متاح» فقط.

**الهاتف الذي لا يجيب:** اختيار «موقع آخر» ينهي انتظار الالتقاط ويفتح الحفظ فورًا، ورسالة خطأ التحديد تدل عليه.

**الحدود:** لا بحث باسم مكان أو عنوان (لا ترميز جغرافي)، ولا فك للروابط المختصرة (`maps.app.goo.gl` لا تحمل إحداثيات؛ يُلصق الرابط الكامل). عنوان وطني بالعكس (من العنوان إلى الموقع) غير مبني. البلاطات من خوادم OpenStreetMap العامة وتحتاج إنترنت؛ دونه يبقى وضع الدبوس وكتابة الإحداثيات.

**الاختبارات:** `tests/customer-entry-fields-ui.mjs` (الواجهة)، `tests/customer-location-rules.mjs` (القواعد)، `tests/rep-customer-create.mjs` (الخادم)، `tests/location-picker-browser.mjs` (Chromium على النسخة المبنية، بوابة `browser`).

## 9-ز. شكاوى العملاء: من خدمة العملاء إلى المندوب حتى الإغلاق

**القاعدة:** الشكوى سجل مستقل من النوع `complaint` في `crm_records` بلا أب، بلا ترحيل، كالمساندة. يسجّلها ممثل خدمة العملاء، يراجعها مديره ويحيلها إلى مدير المبيعات المرتبط به، فيكلّف مندوبًا أو مشرفًا في فرع العميل يغطي منطقته (المندوب الحالي للعميل مقترح أولًا)، يسجّل المندوب تواصلاته داخل الشكوى ثم الحل، وتتأكد خدمة العملاء من العميل وتغلقها أو تعيدها. الوصف الكامل في `docs/CUSTOMER-SERVICE-WORKFLOW-AR.md` (القسم 10).

**من يرى:** مدير النظام الكل. ممثل الخدمة شكاوى فرعه في المناطق التي يغطيها. مدير الخدمة ما سجّله فريقه وما أحاله، وما لا مدير له. مدير المبيعات ما أُحيل إليه وما يحمله أي مندوب أو مشرف (نطاق مدير المبيعات في `salesScopeMemberIds` يشمل كل المناديب والمشرفين، كما في الطلبات). المشرف ما يحمله هو أو مندوبوه. المندوب ما يحمله.

**من يُسأل (`awaiting`):** مدير الخدمة المراجعة؛ الممثل التعديل بعد الإعادة وتأكيد الإغلاق بعد الحل؛ مدير المبيعات التكليف؛ المشرف التفويض؛ المندوب أول تواصل ثم الحل. مدير النظام لا يُسأل إلا حين لا يوجد من يُسأل (مسجِّل بلا مدير، أو مسجِّل لم يعد نشطًا عند الإغلاق). العدّاد هو عدد ما يُسأل عنه القارئ.

**ما يُخزَّن:** كل شيء في `data` (الحالة من `submitted` إلى `closed` أو `cancelled`، الأطراف، التقرير، أختام كل انتقال، `resolution` و`closure`، `updates` و`notes` و`events` لسير الشكوى، `previousAssignees`). الأرقام للعرض فقط.

**الحدود:** لا مرفقات ولا إشعار هاتف. العمل متصلًا فقط. لا يُحتسب تواصل المندوب زيارة. التقرير الشهري يقرأ كل صفوف الشكاوى عند فتحه (أعدادها صغيرة؛ لا حد) ولا يُحدَّث تلقائيًا؛ إن كثرت الشكاوى على مدى سنوات فحدّه بالأشهر الأخيرة.

**الاختبارات:** `tests/complaints.mjs` و`tests/complaints-ui.mjs` و`tests/complaint-report.mjs` و`tests/complaint-report-ui.mjs` (البوابة الافتراضية)، `tests/complaints-http.mjs` و`tests/complaint-report-http.mjs` (بوابة البناء)، `tests/complaints-browser.mjs` (بوابة المتصفح)، و`tests/role-ui.mjs` و`tests/mobile-navigation-ui.mjs` و`tests/server-authorization.mjs` و`tests/baseline-update-activation.mjs` محدَّثة.

## 9-ح. الإصدار الإجباري لتطبيق أندرويد ومناطق متعددة للعضو

**الإصدار الإجباري:** الإصدار الذي يقدمه الموقع (`lib/app-update-release.json`، الآن 1.0.10) هو الإصدار المطلوب من كل من يفتح تطبيق أندرويد أيًّا كان دوره. قرار الحجب في `trackingGateDecision` (`lib/tracking-gate.ts`) بمدخل `requiredVersion`: تطبيق يبلّغ عن إصدار أقدم يُحجب بالسبب `upgrade` قبل أي فحص للتتبع، وإصدار غير معروف لا يُحكم عليه بالإصدار بل بقدراته كما كان. الشاشة في `app/tracking-gate.tsx` تذكر الإصدارين وتعرض تدفق التحديث داخل التطبيق لمن لديه بروتوكول التحديث (1.0.10 فأعلى) أو ملف APK المقدَّم لمن أقدم؛ مسار الملف يُشتق من `apkUrl` في ملف الإصدار لا من ثابت. صفحة الفريق تكتب «إصدار قديم؛ المطلوب كذا» لهاتف آخر تقريره أقدم من المقدَّم (`phoneBrief` في `lib/tracking-coverage-text.ts`). لا تغيير في APK. نشر إصدار جديد (تحديث `lib/app-update-release.json` والملف في `public/downloads`) يحجب كل من لم يحدّث في اللحظة نفسها، فانشره في وقت مناسب. الاختبارات: `tests/tracking-gate.mjs` و`tests/tracking-gate-ui.mjs` و`tests/tracking-coverage.mjs` و`tests/tracking-gate-browser.mjs`.

**المناطق المتعددة:** نطاق العضو `region_scope` نص واحد في العمود نفسه بلا ترحيل: `all`، أو معرّف منطقة، أو عدة معرّفات بترتيب القائمة مفصولة بفاصلة (`central,eastern`). `canonicalRegionScope` في `lib/regions.ts` توحّد ما يرسله النموذج (مصفوفة أو نص) ومسار الأعضاء يرفض ما لا يحوي منطقة معروفة. `memberCanAccessRegion` تقبل عميلًا في أي منطقة من مناطق العضو، `regionScopesOverlap` تحدد من يرى من (`regionMembers`، أعضاء التتبع)، و`regionScopeSql` تبني شرطًا يقبل صفوف `crm_erp_sales` التي تتقاطع منطقتها مع القارئ (مبيعات ERP، التقييم، أدلة الأداء) بدل المطابقة التامة. حراس الكتابة التي تقارن `region_scope=?` تبقى مطابقة تامة للنص الموحّد نفسه. النموذج `MemberRegionField` مربعات اختيار، و`CustomerRegionField` يحصر منطقة العميل الجديد في مناطق العضو ويثبّتها حين تكون واحدة. التراجع إلى إصدار أقدم يترك صاحب المناطق المتعددة بلا عملاء مرئيين حتى يُعاد ضبطه لأن الإصدار الأقدم يطابق النص تمامًا. الاختبارات: `tests/regions.mjs` و`tests/crm-regression.mjs` و`tests/member-regions-browser.mjs`.

## 9-ط. تقييم أداء خدمة العملاء

**القاعدة:** درجة شهرية من 100 لكل ممثل خدمة ولكل مدير خدمة، تُحسب عند الطلب من بيانات موجودة (أحداث الشكاوى `events`، المساندة، طلبات الخدمة) ومن سجلين جديدين: تدقيق المدير وتقييم العميل. بلا ترحيل: القاعدة تبقى على 16 ترحيلًا والتراجع إعادة مجلد release القديم. أصل الفكرة ملف التقييم الذي قدّمه المالك؛ والقواعد النهائية في دليل سير العمل (القسم 10.9).

**التخزين:** ثلاثة أنواع في `crm_records` بلا أب: `service_audit` (`service-audit-<requestId>`: الممثل والشهر والمرجع والدرجات والمجموع والنتيجة وتحقق الاتصال والملاحظة والمدقق، ويُحذف بوسم `deleted` لا بمسح السطر)، `service_kpi_month` (`service-kpi-month-<managerId|none>-<YYYY-MM>`: شهادة الإقفال بالفريق والإعدادات والدرجات، وإعادة الفتح بوسم `reopened` ثم يُستبدل السطر عند إعادة الإقفال)، `service_kpi_settings` (`service-kpi-settings`، بنسخة السطر للتعارض). أبقِ هذه الصفوف صغيرة: سياق مدير النظام يحمّل كل `crm_records`. ولا تسمِّ في بياناتها `performedBy` أو `recordedByEmail` أو `responsibleId` فهي حقول يقرأ منها مسار المبيعات المؤلف.

**قواعد لمن يعدّل المنطق:**
1. يُنسب كل رقم إلى الشهر الذي وقع فيه حدثه، لا إلى حالة الشكوى الحالية: ولهذا يبقى جواب شهر منتهٍ ثابتًا. لا تقرأ `status` ولا `closedAt` ولا `submittedAt` (يُعاد ضبطه عند إعادة الإرسال) في حساب شهر ماضٍ؛ اقرأ الأحداث.
2. لا يُحاسَب ممثل على ما لا يملكه: عدم رضا العميل لا يُحسب ضده.
3. مؤشر دون أقل حالاته يُخرَج من الدرجة ويُوزَّع وزنه، لا يُحتسب كاملًا ولا صفرًا.
   وكذلك «لا مفتوح» في ضبط المتراكم (`emptyIsFull`): يُحتسب كاملًا بجانب مؤشر مقيس آخر فقط، وإن كان وحده فالبطاقة بلا درجة؛ يضبط ذلك `scorecard`.
4. مجموع أوزان كل بطاقة 100 ومجموع درجات التدقيق 100، يتحقق منه `settingsProblem` على الخادم والواجهة معًا.
5. بعد الإقفال تُقرأ الإعدادات والفريق من الشهادة لا من الحال. وأي حقل جديد في الشهادة يكتب مع `monthCertificate` ويُقرأ بقيمة افتراضية.
6. الأرقام لتقييم خدمة العملاء وحدها: لا تدخل في حركة ولا زيارة ولا مستهدف ولا تقييم المناديب، ولا تمنع مهلة إجراءً.
7. الاتجاه ووسيط الفريق (`trend` في جواب `serviceKpiView`): آخر ثلاثة أشهر لكل بطاقة مرئية، ووسيط الفريق لمدير الخدمة ومدير النظام فقط، يحسبهما `serviceKpiMonth` ثلاث مرات في الطلب نفسه بلا حفظ شيء. لا يكلّفان سطرًا في القاعدة؛ وتكلفتهما ثلاثة أمثال حساب الشهر في الذاكرة. إن أبطأت الصفحة مع كبر البيانات فاقصر القراءة على سنتين كما في «الحدود». والواجهة لا تعرض سطر الاتجاه إلا إذا كان لأحد الشهرين السابقين درجة.

**الحدود:** لا مكالمات ولا واتساب ولا دوام. طلبات الخدمة في «دقة التسجيل» ومراجعة المدير فقط. `GET` يقرأ كل الشكاوى والمساندة وطلبات الخدمة عند الفتح ويحسب الشهر وشهرين قبله. القياس على بيانات اصطناعية تعادل عامين لـ16 ممثلًا (6000 شكوى و12000 طلب مساندة و2000 طلب خدمة و500 تدقيق، على النسخة المبنية وجهاز الاختبار): نحو 0.2 ثانية حساب الشهر الواحد في الذاكرة، و1.2 إلى 1.7 ثانية للطلب كاملًا بما فيه قراءة الصفوف، لأي دور. أعداد اليوم أقل بكثير. إن بلغ الطلب ثانيتين على الاستضافة فاقصر قراءة الصفوف على سنتين (`lib/service-kpi-rows.ts`) أو احفظ جواب الأشهر المنتهية. لا إشعار هاتف ولا تغيير في أندرويد.

**الاختبارات:** `tests/service-kpi.mjs` و`tests/service-kpi-ui.mjs` (البوابة الافتراضية)، `tests/service-kpi-http.mjs` (بوابة البناء)، `tests/service-kpi-browser.mjs` (بوابة المتصفح)، وتحديث `tests/server-authorization.mjs` و`tests/mobile-navigation-ui.mjs`. التفاصيل في `tests/CHECKS.md`.

## 9-ي. الزيارة لا تُسجَّل إلا في مكان العميل

**القاعدة:** زيارة المندوب الميدانية (النوع «زيارة»، لا الاتصال ولا البريد ولا الرسالة) تُحفظ فقط إن كان موقع جهازه ضمن **300 متر** من موقع العميل، ويتسع الحد بدقة الجهاز نفسه حتى **100 متر** إضافية. قياس دقته أسوأ من **300 متر** لا يقبل ولا يرفض (رسالة «غير مؤكد» ويُطلب تحديث الموقع) إلا إن كان بعيدًا عن العميل رغم هامش خطئه. وصول أكده تتبع المسار (محطة خط السير بوصول ولم تُغادر) يحسم القبول أيًّا كان القياس. عميل بلا موقع مسجَّل لا يُبعَد عن شيء: تُقبل أول زيارة ويصير موقعها موقع العميل مع ملاحظة «من زيارة فلان بتاريخ كذا» في ورقته (`_locationFromVisit`). **المحجوب المندوب فقط**؛ المشرف والمدير ومدير النظام تُحفظ زيارتهم وتُوسم «خارج موقع العميل» (`placeOutside`) ويظهر ذلك لمن يقرأها. تعديل زيارة محفوظة لا يُحكم عليه من جديد. بلا ترحيل.

## 9-س. تنبيه «يوجد تحديث للتطبيق، أعد التحميل»

**المشكلة:** صفحة مفتوحة قبل النشر تبقى تشغّل الكود القديم حتى تُغلق وتُفتح، فلا يرى المندوب الأزرار الجديدة. **الحل:** تكتشف الصفحة أن إصدارًا أحدث منشور وتخبر المستخدم، ولا تعيد التحميل وحدها أبدًا.

| الموضع | ما فيه |
|---|---|
| `lib/build-freshness.ts` | `runningScripts` (سكربتات الصفحة المجزّأة تحت `/_next/static/` أو `/offline-app/assets/`)، و`judge` (الحكم: 404/410 = `stale`، 2xx = `current`، غير ذلك أو فشل شبكة = `unknown` ولا شريط)، و`createBuildFreshness` (المتحكّم بالبيئة المحقونة: فحص عند الاشتراك وكل `FRESHNESS_INTERVAL_MS`=10 دقائق وعند العودة بعد `FRESHNESS_RESUME_GAP_MS`=60 ثانية، لا دون اتصال ولا والصفحة مخفية، طلب واحد لكل جولة، حد `FRESHNESS_HEAD_LIMIT`=6)، و`buildFreshness()` المتحكّم الفعلي |
| `app/build-notice.tsx` و`.css` | الشريط (يُعرض إن كان الحكم `stale` فقط) وزر «أعد التحميل» بارتفاع 44px؛ في `workspace-notices` بجانب شريط تحديث أندرويد |
| `public/sw.js` | مستمع `message`: `skipWaiting()` **فقط** عند رسالة `yourrest-activate-update` الصريحة من الصفحة. لا `skipWaiting` في `install` ولا `activate` (يفحصه `tests/offline-shell.mjs`) |

- **ما يفحصه:** `HEAD` بـ`cache:'no-store'` لكل سكربت (الأطول مرة واحدة)؛ المختفي = إصدار أحدث لأن كل نشر يغيّر أسماء الملفات (يتغير `index-*.js` بتغير أي جزء). نسخة الشغل بدون نت تُقارن بـ`/offline-shell-manifest.json`.
- **حالة «أحدث» لا تُمحى** بجواب لاحق فاشل أو سليم؛ تُمحى بإعادة التحميل وحدها.
- **الإعادة:** `reload()` تطلب من العامل المنتظر أن يتولى (بحد 3 ثوانٍ للبحث وثانية ونصف للتولّي)، ثم `location.reload()` ولو فشل العامل.
- **تبويب «الماكينات» لغير مندوب العميل:** `app/crm-app.tsx` يعرض «لا توجد ماكينات لهذا العميل / تُضاف ماكينات العميل من مندوبه المسؤول عنه.» حين لا يكون `canAddMachineTo` (كانت الرسالة السابقة تشير إلى أزرار لا توجد)؛ يغطيه `tests/machines-browser.mjs`.
- **لا يعمل على الصفحات المفتوحة قبل هذا الإصدار** (لا تحمل الكود)؛ تحتاج مرة إغلاقًا وفتحًا.
- **اختباراتها:** `tests/build-freshness.mjs` (68، بوابة افتراضية)، `tests/build-notice-browser.mjs` (16، متصفح حقيقي بمحاكاة 404 و503 على الطلب الخفيف)، `tests/offline-shell.mjs`.

## 9-ع. المُفعِّل يوقف عمليات التطبيق التي أعاد المضيف تشغيلها

**المشكلة:** استضافة Node.js في cPanel تُعيد تشغيل التطبيق عند وصول أي طلب (تتبع المناديب يرسل طلبات طوال النهار)، فيعود `lsnode` بعد **Stop App** ويمنع المُفعِّل بـ`STOP: APP_OR_DATA_STILL_IN_USE`. كان الحل اليدوي أمر `kill` ثم المُفعِّل فورًا (حدث في تفعيل 21 أكتوبر 2026).

**الحل (في `portable/activate-ui-refresh-update.cjs`، يدخل أول حزمة تُبنى بعده):**

| الدالة | ما تفعله |
|---|---|
| `appServerProcesses(p, procRoot)` | عمليات الحساب التي هي **خادم Node.js نفسه** (`lsnode` أو `node`) وتمسك مجلد التطبيق أو البيانات (مجلد العمل، أو سطر الأمر، أو ملف مفتوح في البيانات). لا تعيد المُفعِّل نفسه ولا سلسلة آبائه (الطرفية التي شغّلته)، ولا عملية انتهت وتنتظر الجمع (`Z`)، ولا أي برنامج غير Node.js كصدفة `bash` جالسة في المجلد. |
| `terminateApp(p, options)` | `SIGTERM` أولًا وانتظار حتى 15 ثانية، ثم `SIGKILL` لمن لم يخرج وانتظار 5 ثوانٍ، وتعيد الفحص وتكرر حتى 3 جولات إن أعاد المضيف تشغيله. تطبع «APP STILL RUNNING … STOPPING IT NOW» ثم «APP PROCESSES STOPPED: n». |
| `run()` | تستدعيها **مرة واحدة** قبل أول `stopped(p)`، أي قبل أي قفل أو نقطة حفظ، ولا تستدعيها في `--check` ولا `--verify`. **الفحوص اللاحقة** (قبل النسخ وبعده وقبل التبديل) تبقى صارمة وتفشل ولا توقف شيئًا. تعمل فقط حين يكون `stopped` هو الافتراضي `ensureStopped`؛ الاختبارات التي تحقن `stopped` لا تلمس عمليات الجهاز. |

- **ما لا يتغير:** `ensureStopped` كما هو، فإن بقي شيء غير خادم Node.js يمسك المجلد (صدفة، سكربت فحص) يظهر `APP_OR_DATA_STILL_IN_USE` كالسابق. وخطوة **Stop App** في cPanel تبقى الخطوة الأولى في الدليل؛ المُفعِّل يلتقط ما أعاده المضيف فقط.
- **حدّه:** إن أعاد المضيف تشغيل التطبيق **بعد** الفحص الأول وأثناء النسخ فالفحص اللاحق يفشل كما قبل، ولا شيء يتغير في الإنتاج قبل التبديل. هذا نادر لأن الإيقاف والفحص الأول يسبقان النسخ بثوانٍ.
- **اختبارها:** `tests/activate-auto-stop.mjs` (31 فحصًا، بوابة افتراضية): شجرات `/proc` وهمية (lsnode و node بمجلد العمل أو الأمر أو ملف مفتوح في البيانات، وإبقاء `bash` و`sleep` و`nodemon` وعملية Node.js في مشروع آخر، وحماية المُفعِّل وآبائه، و`SIGTERM` يكفي، و`SIGTERM` المُتجاهَل يلحقه `SIGKILL`، والزومبي لا يُنتظر ولا يُقتل، وإعادة تشغيل بين جولتين، ومضيف لا يترك التطبيق متوقفًا فيُنهى بثلاث جولات ثم الرفض الصارم، وفشل الإرسال `EPERM` يُسجَّل ولا يُرمى) ثم عمليات حقيقية على `/proc` الحقيقي: خادم Node.js في مجلد التطبيق يُوقَف و`sleep` في المجلد نفسه لا يُمس. ويثبّت أن الاستدعاء داخل `run()` واحد وقبل `stopped(p)`.

### 9-ف-2. فتح التطبيق على نسخة الجهاز (2026-10-29)

**القياس قبل:** على موبايل أبطأ 4 مرات و4G بطيء، المندوب يفتح التطبيق المعتاد (والنسخة محفوظة على جهازه) في نحو 1.85 ثانية، و3.25 ثانية إن كان زمن الوصول للسيرفر 600 مللي ثانية؛ لأن التطبيق كان ينتظر رد `/api/crm` ثم الحفظ على الجهاز ثم يرسم، ويطلب المساندة والشكاوى بعدها لا معها. وكان يعيد تنزيل 112 كيلو من سكربتاته مع **كل** فتح.

| ماذا | أين | القاعدة |
|---|---|---|
| عرض نسخة الجهاز فورًا | `load()` في `app/crm-app.tsx` | أول تحميل في الصفحة يعرض نسخة الجهاز لنفس الحساب المفتوح (`refreshLocal`) ويُظهر «يتم تحديث البيانات…» (`.refresh-notice`) ثم يطلب السيرفر؛ الرد يحل محلها. النسخة لا تُقرأ إلا لحساب مفتوح على الجهاز في نفس الجلسة (`unlockedOfflineOwner`)، وصفحة الدخول تقفلها، و401/403 يقفلها ويمسح الشاشة: حساب آخر على نفس الجهاز لا يرى نسخة غيره. |

| الطلبات معًا | `useSupport` و`useComplaints` | مع نسخة الجهاز يُعرف الحساب فورًا فتبدأ طلبات المساندة والشكاوى مع `/api/crm` لا بعده. |

| صفحة العملاء | `app/customer-machines.tsx` | تُرسم الكروت أو الجدول حسب الشاشة (`(max-width: 1023px)` نفس نقطة التنسيق) لا الاثنان؛ عناصر الصفحة من 4853 إلى 2841. بلا `matchMedia` (السيرفر، اختبار) يُرسم الاثنان كما كان. |

**بعد، نفس الظروف:** الفتح المعتاد 1.2 ثانية بدل 1.85، و1.4 بدل 3.25 مع 600 مللي ثانية للسيرفر (البيانات تظهر قبل رد السيرفر)، ولا سكربت يُنزَّل في الفتح المعتاد بدل 112 كيلو. أول فتح على جهاز جديد بلا تغيير (المرحلة 3).

- **القاعدة لأي كود جديد:** لا تؤخر العرض على كتابة IndexedDB؛ لا تطلب بـHEAD (أو بأي طريقة غير GET) عنوانًا محفوظًا في ذاكرة المتصفح؛ ما يُضاف إلى `OfflineSnapshot` تقارنه `sameSnapshot` تلقائيًا (كل المفاتيح).

### 9-ف-3. حجم أول فتح (2026-10-29)

أول فتح بعد كل إصدار (أو على جهاز جديد) ينزّل سكربتات التطبيق: نحو 442 كيلو مضغوطة، منها 279 لملف `crm-app` و41 لملف تسجيل الدخول.

- **قاموس الإنجليزي عند الطلب فقط:** كان `lib/locales/en.json` (نحو 94 كيلو خام، 31 مضغوطة) داخل ملف تسجيل الدخول فيُنزَّل مع كل فتح ولو بالعربي. الآن `lib/i18n.ts` يستورده بـ`import()` عند اختيار الإنجليزي (`loadEnglish`)، والصفحة تبقى بالعربي لحظة حتى يصل ثم تتحول مرة واحدة؛ الاختيار المحفوظ يبدأ التنزيل مع تحميل الوحدة؛ آخر اختيار يفوز؛ والاختبارات تسلّم القاموس مباشرة بـ`installEnglish`. ملف الصدفة دون اتصال يضم الملف الجديد تلقائيًا (كل ما يُخرجه Vite يدخل `offline-shell-manifest.json`). **النتيجة:** أول فتح 411 كيلو بدل 442 (−7%)، و4.25 ثانية بدل 4.38، و5.8 بدل 6.1 مع 600 مللي ثانية للسيرفر. الفتح المعتاد لا يتأثر (السكربتات من الذاكرة).
- **ما جُرِّب ولم يُعتمد:** تحميل الصفحات النادرة (المبيعات والمستهدفات مع استيراد ERP، تقرير اليوم، المنافسون، تقييم الخدمة) بـ`React.lazy`. Rolldown (Vite 8) لا يضع الوحدات المشتركة بين الصفحة والتطبيق في ملف التطبيق بل يقسمها إلى ملفات صغيرة (أيقونات `lucide` منفصلة، و`visit-customer-picker` 252 كيلو خام)، فصار أول فتح 20 ملفًا بدل 8: الحجم نقص 11% لكن الوقت لم يتحسن (4.47 ثانية) وساء مع زمن وصول عالٍ (6.8 بدل 6.1). لا تُضف `lazy` لصفحة قبل ضبط تجميع الوحدات المشتركة (`advancedChunks` لبيئة العميل فقط) وقياس أول فتح بزمن وصول 600 مللي ثانية. التعديل محفوظ في سجل التطوير لا في الكود.
- **ما يبقى في ملف التطبيق ولا يُفصل بسهولة:** مكتبات الواجهة (`@base-ui/react` نحو 90 كيلو خام، `sonner`، `tailwind-merge`، `@radix-ui/react-select`) و`zod` (57 كيلو، مشترك مع تحقق البيانات في `lib/crm.ts` و`lib/customer-service.ts`)، والقوائم والنماذج التي يستعملها المندوب كل يوم.
- **الاختبار:** `tests/i18n-lazy.mjs` (افتراضي): لا تنزيل بالعربي، الإنجليزي ينتظر القاموس ثم يتحول، تنزيل واحد مهما تكرر التبديل، آخر اختيار يفوز، الاختيار المحفوظ يبدأ التنزيل مبكرًا، و`installEnglish` فوري.

## 9-ص. الرفع إلى الاستضافة من GitHub بتوكن cPanel (كما في سديم)

بدل تنفيذ خطوات دليل التحديث يدويًا في Terminal cPanel، ينفّذها GitHub نفسه بنفس المُفعِّل وبنفس الترتيب، بطريقة نظام سديم: توكن API من cPanel، بلا مفتاح SSH. الملفات: `.github/workflows/deploy.yml` و`scripts/deploy-cpanel.mjs` و`scripts/hosting-cron.sh` و`scripts/hosting-deploy.sh`.

- **الإعداد مرة واحدة (المالك):** cPanel ← Security ← Manage API Tokens ← Create، ثم في GitHub: Settings ← Secrets and variables ← Actions ← New repository secret باسم `CPANEL_API_TOKEN`. هذا هو السر الوحيد اللازم؛ `CPANEL_HOST` و`CPANEL_USER` اختياريان (الافتراضي `premium137.web-hosting.com` و`youriedx`). القيمة تُنظَّف من المسافات وعلامات الاتجاه التي يجلبها النسخ من رسالة عربية، والتوكن لا يُطبع أبدًا.
- **الحزمة:** تُبنى وتُجرَّب البروفة الكاملة هنا كالمعتاد، ثم تُلتزم الحزمة نفسها (نفس SHA256 المسلَّم) في `deploy/packages/`، فما يُرفع هو ما جُرِّب بالبايت. احذف الحزمة السابقة من المجلد عند إضافة الجديدة.
- **التشغيل:** دفع `deploy/request.json` إلى `main` أو فرع `claude/**`، أو يدويًا من تبويب Actions بعد وصول الـworkflow إلى `main` (GitHub لا يعرض التشغيل اليدوي إلا لما في الفرع الافتراضي؛ الوضع المختار هناك يحل محل وضع الملف):
  `{"mode": "check", "package": "deploy/packages/Yourrest-CRM-Update-Speed-20261029.zip", "sha256": "c03d…", "stage": "yourrest-crm-update-speed-20261029", "helper": "yourrest-activate-update-speed.cjs"}`.
  الخطوة الأولى تتحقق من الطلب: SHA256 الحزمة الملتزمة يطابق الطلب، وفيها `release/` و`RELEASE-SHA256SUMS.txt` والمُفعِّل في جذرها، والأسماء كما في دليل التحديث.
- **كيف يُنفَّذ على الاستضافة:** واجهة cPanel تنقل الملفات لكنها لا تنفّذ أوامر. لذلك `deploy-cpanel.mjs`: يتأكد أن التوكن يفتح الحساب وأن `yourrest-crm` موجود؛ يرفع الحزمة إلى مجلد البيت (كما في الدليل) والسكربتين إلى `~/yourrest-deploy`؛ يكتب ملف الطلب؛ ثم يضيف **سطر cron مؤقتًا** كل دقيقة يشغّل `hosting-cron.sh`، الذي يأخذ الطلب مرة واحدة (`mv` ذري) ويشغّل `hosting-deploy.sh` ويكتب الناتج في `log-<run>` ورمز الخروج في `done-<run>`. الـworkflow يقرأ الناتج أولًا بأول ويعرضه، ثم **يحذف سطر cron** في كل الأحوال، ويحذف أي طلب لم يُؤخذ، فلا يعمل طلب لاحقًا وحده. علامة `running-<run>` تمنع تشغيلين معًا (تُتجاهل إن زاد عمرها عن ساعتين).
- **الأوضاع (`hosting-deploy.sh`):**
  - `check`: فكّ الحزمة في مجلدها و`--check`، والتطبيق يعمل؛ ويطبع هل `cloudlinux-selector` متاح وحالة التطبيق فيه (دون متغيرات البيئة).
  - `deploy`: `--check`، إيقاف التطبيق بـ`cloudlinux-selector stop` إن وُجد (وإلا يوقفه المُفعِّل بنفسه)، المُفعِّل (النسخة الاحتياطية والتبديل)، التشغيل بـ`cloudlinux-selector start`، ثم `--verify` حتى ست محاولات. إن توقف المُفعِّل **قبل** التبديل يُعاد تشغيل التطبيق القديم كما هو ويفشل التشغيل بمخرجات المُفعِّل. دون `cloudlinux-selector` يشغّل المضيف التطبيق مع أول طلب؛ إن لم يُجب ينتهي برمز 4: Start App يدويًا ثم `mode=verify`.
  - `verify`: `--verify` فقط، ولا تُرفع حزمة.
  - `diagnose`: فحص للقراءة فقط على البيانات الحية دون حزمة ولا إيقاف: `{"mode": "diagnose", "script": "scripts/diagnose/<name>.cjs"}`. يُرفع السكربت باسم `yourrest-deploy/diagnose.cjs` ويُشغَّل بـNode الحساب، ويظهر ناتجه في سجل الـjob. القاعدة: سكربت `scripts/diagnose/` يفتح القاعدة `readOnly` ولا يكتب شيئًا، ويطبع أعدادًا ومعرّفات سجلات فقط (لا أسماء ولا هواتف ولا أرقام فواتير)، وله اختبار على قاعدة اصطناعية. ثاني سكربت: `backups.cjs` (هل في نسخ احتياطية يومية: سطر cron، آخر نجاح، عدد النسخ، نقاط التفعيل، المساحة). أول سكربت: `arabic-digits.cjs` (هل الأرقام العربية في أرقام الفواتير وأكواد العملاء تفصل سجلًا عن توأمه في ERP). نتيجة 2026-10-31: لا أرقام عربية في البيانات الحية. بعدها صار مفتاح الفاتورة ومفتاح كود العميل يحوّلان ٠-٩ و۰-۹ إلى أرقام إنجليزية، فـ«INV-١٠٢٣» و«INV-1023» فاتورة واحدة؛ أعد هذا الفحص قبل رفع أول حزمة تحمل هذا التعديل، فإن ظهرت أرقام عربية فلا تُرفع الحزمة قبل مراجعة مفاتيحها المخزنة.
- **الموافقة:** Claude لا يدفع طلب `deploy` إلا بعد موافقة المالك في المحادثة. الـjob يعمل في بيئة `production`؛ إضافة Required reviewers لها تجعل كل تشغيل ينتظر ضغطة Approve إن أراد المالك ذلك.
- **القراءة:** ناتج الاستضافة كاملًا في سجل الـjob وفي ملخص التشغيل، وأهم أسطره في annotation واحدة (`hosting said`)، والخطوات في annotations (`deploy`).
- **الحدود:** لا يُحذف شيء ولا يُسترجع: أي `STOP` من المُفعِّل يُنهي التشغيل بمخرجاته. لا يمس السكربت مجلدات حزم سابقة؛ مجلد الحزمة نفسها يُعاد استعماله إن كان بنفس `RELEASE-SHA256SUMS.txt` ويُرفض إن اختلف. يلزم أن يسمح الحساب بـcron (cPanel ← Cron Jobs)؛ إن لم يبدأ السطر خلال 6 دقائق يتوقف الـworkflow ويحذف الطلب والسطر.
- **الاختبار:** `node tests/deploy-cpanel.mjs` (البوابة الافتراضية) يشغّل السكربتات الحقيقية على cPanel وهمي في مجلد مؤقت بـcron يشغّل bash فعلًا. وباليد: `HOME=<مجلد مؤقت> YR_HOSTING_NODE=$(command -v node) bash scripts/hosting-deploy.sh check <zip> <stage> <helper> <sha256>`.

## 10-ب. مندوب محجوب أو بلا بيانات تتبع

1. افتح «الفريق والصلاحيات» ← عمود «التتبع»، أو «تقرير يوم المندوب» ← اختر المندوب: اللوحة تقول هل لم يُفعَّل التتبع قط، أم لم تصل نقاط اليوم، وما آخر ما أبلغ به الهاتف.
2. «لم يصل أي تقرير من الهاتف»: لم يفتح النظام بعد التحديث. اطلب منه فتح تطبيق أندرويد.
3. «متصفح»: يستخدم المتصفح؛ لا حل إلا تطبيق أندرويد.
4. «أذونات ناقصة»: يفتح إعدادات الهاتف ← التطبيقات ← يورست ← الأذونات ← الموقع: «السماح طوال الوقت» مع الموقع الدقيق، والإشعارات.
5. «يوم العمل مرتبط بجهاز آخر»: بدّل هاتفه في منتصف اليوم؛ يُحل في اليوم التالي.
