# دليل التشغيل والتطوير والتحديث — Yourrest CRM

هذا الدليل للمطوّر ومسؤول الاستضافة. يشرح تشغيل المشروع محليًا، واختباره، وبناءه، وتحديثه على الاستضافة مع الحفاظ على البيانات والإعدادات. لا تنشر شيئًا على الموقع الفعلي إلا بعد تجربة النسخة محليًا وأخذ نسخة احتياطية.

## 1. المتطلبات

| العنصر | الإصدار |
|---|---|
| Node.js | 22.16 أو أحدث (التطبيق يستخدم `node:sqlite` المدمج) |
| pnpm | 11 (`corepack enable` ثم `pnpm --version`) |
| Chromium + Playwright | اختياري، لاختبارات المتصفح فقط |
| Python 3 و`unzip` | اختياري، لسكربتات التغليف واختبارات الحزم |

لا توجد قاعدة بيانات خارجية: التطبيق يحفظ كل شيء في ملف SQLite ومجلد مرفقات خاصين.

## 2. أول تشغيل للتطوير

```bash
pnpm install --frozen-lockfile   # تثبيت الاعتمادات المقفلة
pnpm typecheck                   # فحص الأنواع
pnpm lint                        # ESLint
pnpm check                       # الأنواع + كل الاختبارات الافتراضية (نحو 6 دقائق)
pnpm build                       # البناء إلى dist/standalone
```

ملاحظات:
- إذا رفض pnpm تثبيت إصدار حديث بسبب `minimumReleaseAge` في `pnpm-workspace.yaml`، فهذه سياسة أمان مقصودة. لا تعطّلها في المشروع؛ استخدم الإصدارات المقفلة في `pnpm-lock.yaml`.
- كل الاختبارات تستخدم بيانات اصطناعية وقواعد SQLite مؤقتة. لا تحتاج إعدادات إنتاج ولا تلمس بيانات حقيقية.
- `pnpm check` ينفّذ الأنواع ثم كل ملف في `tests/` ما عدا الاستثناءات الموثقة في `tests/check-manifest.json`. إضافة ملف اختبار `.mjs` جديد لا تحتاج تسجيله.

## 3. تجربة التطبيق محليًا

بعد `pnpm build`:

```bash
pnpm demo
```

يشغّل النسخة المبنية ببيانات اصطناعية (ستة حسابات بأدوار مختلفة وثلاثة عملاء) على عنوان مثل `https://crm.yourrest.org:8443` بشهادة موقعة ذاتيًا. رموز الدخول تظهر في الطرفية عند طلبها ولا يُرسل أي بريد حقيقي. عند الإيقاف بـ Ctrl+C تُحذف بيانات التجربة.

لأن التطبيق يشترط أصل HTTPS، افتح العنوان بإحدى طريقتين:

1. Chrome بملف تعريف مؤقت (الأنظف):
   ```bash
   chrome --user-data-dir=/tmp/yr-demo --ignore-certificate-errors \
     --host-resolver-rules="MAP crm.yourrest.org 127.0.0.1" https://crm.yourrest.org:8443
   ```
2. أو إضافة السطر `127.0.0.1 crm.yourrest.org` إلى ملف hosts أثناء التجربة فقط، وحذفه بعدها.

لتغيير المنفذ: `DEMO_PORT=9443 pnpm demo`. الحسابات: `owner` و`admin` و`manager` و`supervisor` و`rep.east` و`rep.west` و`service` بنطاق `@yourrest.org`.

لتجربة الهاتف: في أدوات المطور اختر شاشة 390 بكسل أو جهازًا محمولًا. الوضع الليلي من المفتاح في الشريط العلوي.

## 4. الإعدادات والأسرار

- الإعدادات الحقيقية في ملف `settings.cjs` **خارج** مجلد الإصدار وخارج `public_html`، بصلاحية خاصة (600).
- `node setup.cjs --owner-email=name@yourrest.org` عند أول تثبيت على الاستضافة ينشئ `settings.cjs` بسرّ عشوائي جديد ومجلدات البيانات الخاصة، وقاعدة بيانات **فارغة** فيها حساب المالك وحده (أدمن كل المناطق، والاسم اختياري بـ`--owner-name=...`، وإلا «مدير النظام»). يدخل المالك ببريده ثم يضيف الفريق والعملاء من التطبيق. لا تشغّله على تثبيت قائم (ويرفض `--owner-email` إن وُجدت القاعدة دون أن يغيّر شيئًا).
- **لا توجد بيانات عملاء في المستودع ولا في الحزمة** (أُزيلت لقطة التبدئة `migration/initial.json` في 2026-11-16 بموافقة المالك). لبدء تثبيت جديد من بيانات قائمة: الأفضل استرجاع نسخة احتياطية (`docs/PRODUCTION-BACKUP-AR.md`). أو ضع ملف بيانات أولية بصيغة `yourrest-namecheap-export-v1` يدويًا في `migration/initial.json` داخل مجلد التطبيق على الخادم مع بصمته SHA-256 في `migration/initial.sha256`، ثم شغّل `node setup.cjs` بلا خيارات: تُفحص البصمة قبل أي تحميل، ويُرفض الملف مع `--owner-email` معًا. لا ترفع هذا الملف إلى المستودع (`.gitignore` يمنعه).
- القالب الخالي من الأسرار: `settings.example.cjs`. ومتغيرات البيئة النموذجية: `.env.example`.
- المفاتيح: `YR_APP_ORIGIN` و`YR_AUTH_SECRET` (64 خانة سداسية عشرية أو أكثر) و`YR_DATABASE_PATH` و`YR_OBJECTS_PATH` و`YR_MAIL_TRANSPORT` و`YR_MAIL_FROM` و`YR_SENDMAIL_PATH`، واختياريًا `YR_NATIONAL_ADDRESS_API_KEY`.
- تغيير `YR_AUTH_SECRET` يسجّل خروج كل المستخدمين. لا تضع السر في المستودع أو في السجلات.
- عند وجود `settings.cjs` يرفض التطبيق أي قيمة `YR_*` مختلفة في متغيرات البيئة.
- مفتاح توقيع أندرويد يُسلّم منفصلًا ولا يُنشر ولا يدخل المستودع.

## 5. بنية المشروع

| المسار | المحتوى |
|---|---|
| `app/` | الصفحات والمكونات ومسارات API (`app/api/*`) |
| `lib/` | القواعد الأساسية: الصلاحيات (`access.ts`)، المستهدفات (`targets.ts`)، أوزان التقييم (`kpis.ts`)، المبيعات، استيراد ERP، المزامنة دون شبكة |
| `db/` و`drizzle/` | المخطط وترحيلات SQL التراكمية (16 ملفًا؛ آخرها `0015_member_devices.sql`) |
| `portable/` | طبقة الاستضافة: التشغيل والإعداد والنسخ الاحتياطي والاسترجاع والترقية |
| `scripts/` | البناء والتغليف والتجربة المحلية؛ `scripts/lib/built-app.mjs` يشغّل النسخة المبنية للاختبارات |
| `tests/` | اختبارات الانحدار والأمان والمتصفح والإصدار |
| `mobile/android` | مصدر أندرويد (لا يُبنى هنا) |

## 6. قواعد التطوير الآمن

1. **الصلاحيات على الخادم دائمًا.** إخفاء زر في الواجهة ليس حماية. أي مسار جديد في `app/api` يتحقق من الجلسة ثم الدور ثم نطاق السجل، ويُضاف إلى `tests/server-authorization.mjs`.
2. **لا تعدّل المعادلات** (أوزان التقييم، تجميع المشرف ومدير المبيعات، المستهدفات الممتدة بالتواريخ) إلا بقرار أعمال، ومع اختبارات تثبّت الأرقام.
3. **الترحيلات تراكمية فقط.** لا تعدّل ملفًا في `drizzle/` طُبّق من قبل؛ أضف ملفًا جديدًا. التثبيت القائم يأخذ نسخة من المخطط قبل أي ترحيل.
4. **التواريخ بتوقيت الرياض.** استخدم `today()` من `lib/crm.ts` ولا تستخدم تاريخ جهاز المستخدم أو `toISOString()` على اللحظة الحالية.
5. **أنواع دقيقة بلا `any`** ولا `eslint-disable`. فحص ESLint صفر أخطاء وجزء من `npm run check`: أي خطأ جديد يُفشل البوابة. الاستثناءات المراجَعة (قواعد React Compiler الذي لا يستعمله المشروع كتحذيرات، سكربتا ما قبل الرسم في `app/layout.tsx`، و`any` في `Row.data` والمستهدفات ومسار CRM) مكتوبة بأسبابها في `eslint.config.mjs`، لا في تعليقات متفرقة.
6. **استيراد جديد بين الوحدات** قد يكسر اختبارات تحقن التبعيات بأسماء محددة (مثل `tests/journey-ui.mjs`). استخدم `import type` للأنواع، وحدّث الاختبار إذا أضفت استيرادًا فعليًا.
7. **ملفات يولّدها البناء** (`public/offline-app/**` و`public/sw.js` و`public/offline-shell-manifest.json`) تتغير عند تغيير كود الواجهة. شغّل `pnpm build` وثبّتها في commit منفصل.
8. اختبارات المتصفح تكتب أدلة في `docs/`؛ وجّه مخرجاتها إلى مجلد مؤقت بمتغيرات `YR_*_SCREENSHOT_DIR` و`YR_*_REPORT` كي لا تتغير الأدلة المحفوظة.

## 7. الاختبارات

| البوابة | الأمر | تحتاج |
|---|---|---|
| الافتراضية | `pnpm check` | لا شيء إضافي |
| بعد البناء | `node tests/server-authorization.mjs` و`node tests/sales-date-boundaries.mjs` و`node tests/namecheap-http.mjs` و`node tests/app-update-release.mjs` | `pnpm build` |
| المتصفح | `node tests/<name>-browser.mjs` | `pnpm build`، Playwright، Chromium |
| ملف ERP الأصلي | `ERP_TEST_WORKBOOK=/path/file.xlsx pnpm check:erp` | ملف التقرير الأصلي |
| حزم الإصدار | اختبارات `tests/*-update-package.py` | حزمة إصدار مصدّرة |
| أندرويد | `mobile/android` | JDK وAndroid SDK والتوقيع |

**الإصدار: أمر واحد `npm run gates` (من 2026-11-05).** يبني نسخة نظيفة ثم يشغّل البوابة الافتراضية كاملة (كل اختبارات الوحدة) ومعها اختبارات النسخة المبنية والمتصفح **بالتوازي** (6 عمليات، حتى 5 متصفحات على هذا الجهاز ذي الأربعة معالجات)، و**يختار** منها ما يخص الأجزاء التي تغيّرت منذ آخر حزمة (`deploy/request.json`)، والكل لو تغيّر ملف مشترك (صلاحيات، مناطق، الصفحة الرئيسية، قاعدة البيانات، البناء…) أو ملف لا تعرفه الخريطة `tests/test-areas.json`. القياس على هذا الجهاز: تشغيل كامل نحو 11 دقيقة ونصف (البناء نصف دقيقة) بدل نحو 55 دقيقة متتابعة؛ تعديل في طلبات القوالب وحدها نحو 4 دقائق (7 اختبارات من 49، وكانت نحو 7 قبل أن تصير البوابة الافتراضية متوازية). البوابة الافتراضية نفسها (`npm run check`) صارت تشغّل اختباراتها بالتوازي أيضًا: نحو 3 دقائق بدل 6 ونصف، و`npm run check -- --jobs 1` يعيد التشغيل المتتابع القديم؛ وتعمل داخل `npm run gates` بجانب باقي الاختبارات لا قبلها (أسرع، قيس الاثنان). أي اختبار يفشل يُعاد مرة وحده: إن نجح يُكتب «flaky» وإن فشل ثانية «failed» ولا يمرّ الإصدار؛ واختبارات ملف ERP الخاص بصاحب العمل تُكتب «skipped» لأن الملف ليس على الجهاز. `node scripts/gates.mjs --plan` يعرض ما سيعمل دون تشغيل، و`--full` يشغّل الكل. التفاصيل في `tests/CHECKS.md` («بوابة الإصدار السريعة»). الحزمة والبروفة خطوتان منفصلتان كما هما.

لتشغيل اختبارات المتصفح في بيئة معزولة:

```bash
export CODEX_PRIMARY_RUNTIME_NODE_MODULES=/path/to/node_modules   # يحتوي playwright
export YR_BROWSER_EXECUTABLE=/path/to/chromium
env -u HTTPS_PROXY -u https_proxy NO_PROXY='*' node tests/competitors-browser.mjs
```

إذا كانت بيئتك خلف وكيل (proxy)، عطّله لهذه الاختبارات وإلا يُعاد الاتصال بالمضيف المحلي. جزء من اختبارات الوضع دون اتصال وPWA يعتمد على محاكاة انقطاع الشبكة في Chromium؛ راجع حدودها في تقرير المراجعة.

## 8. البناء والتغليف

```bash
pnpm build        # ينشئ dist/standalone (التطبيق + مجلد operations + الترحيلات + manifest)
```

حزمة الاستضافة التراكمية تُنشأ بسكربتات `scripts/package-*.py` (مثل `package-namecheap.py`)، وهي تنسخ `dist/standalone` ومعها التعليمات والأدلة. هذه السكربتات تاريخية ومرتبطة باختبارات `tests/*-update-package.py`؛ لا تحذفها قبل توحيدها بقرار منفصل.

## 9. التحديث على الاستضافة مع الحفاظ على البيانات

البيانات والإعدادات خارج مجلد الإصدار، لذلك استبدال `release` لا يمسها. اتّبع الترتيب بدقة:

1. **نسخة احتياطية قبل أي تحديث** (يمكن أخذها والتطبيق يعمل):
   ```bash
   node /home/ACCOUNT/yourrest-crm/release/operations/backup-scheduled.mjs /home/ACCOUNT/yourrest-crm-backups 14
   ```
   تأكد أن الناتج `ok:true` وأن `status.json` يظهر `state: ok`. التفاصيل واستعادة نسخة: `docs/PRODUCTION-BACKUP-AR.md`.
2. من cPanel > **Setup Node.js App** اختر التطبيق ثم **Stop App**.
3. فكّ الحزمة داخل مجلد التطبيق مع **استبدال `release` فقط**. لا تستبدل `settings.cjs`، ولا مجلد البيانات `yourrest-crm-data`، ولا ملف قاعدة البيانات.
4. **لا تشغّل** `setup.cjs` ولا `npm install` على تثبيت قائم.
5. **Start App.** عند الإقلاع يطبّق التطبيق الترحيلات الجديدة فقط على قاعدة معروفة، بعد نسخة خاصة من المخطط. إذا توقف الإقلاع فراجع سجل التطبيق ولا تحذف قاعدة البيانات.
6. افتح الموقع وسجّل الدخول وتحقق من: الدخول، قائمة العملاء، تسجيل زيارة، صفحة المستهدفات. افتح التطبيق مرة أثناء الاتصال ثم أغلقه وافتحه لتفعيل واجهة الوضع دون اتصال.
7. تطبيق أندرويد لا يتحدث تلقائيًا برفع السيرفر؛ ثبّت APK الجديد (نفس التوقيع) فوق القديم دون حذفه إذا تغيّر إصدار الأندرويد.

**التراجع:** أوقف التطبيق وأعد `release` السابق. إذا لزم استرجاع البيانات فاستعدها إلى **مجلد خاص جديد** (الأداة ترفض الكتابة فوق مجلد قائم):

```bash
node /home/ACCOUNT/yourrest-crm/release/operations/restore.mjs verify  /home/ACCOUNT/yourrest-crm-backups/BACKUP_NAME
node /home/ACCOUNT/yourrest-crm/release/operations/restore.mjs restore /home/ACCOUNT/yourrest-crm-backups/BACKUP_NAME /home/ACCOUNT/yourrest-crm-restored
```

ثم وجّه `YR_DATABASE_PATH` و`YR_OBJECTS_PATH` في `settings.cjs` إلى المجلد المسترجع وشغّل التطبيق. لا تحذف قاعدة البيانات الأصلية قبل التأكد من سلامة المسترجعة.

## 9-ب. بناء حزمة التحديث وبروفتها قبل الرفع

حزمة الاستضافة التي تُرفع على cPanel تُبنى من `dist/standalone` بسكربت التغليف الذي يثبّت بصمة كل ملف داخل مُفعِّل مستقل. لا تُرفع حزمة السورس نفسها.

```bash
pnpm install --frozen-lockfile && pnpm build
python3 scripts/package-ui-refresh-update.py \
  --release dist/standalone --output /مسار/خارج/المستودع/Yourrest-CRM-Update-YYYYMMDD.zip \
  --release-name update --release-date YYYYMMDD \
  --stage-name yourrest-crm-update-YYYYMMDD --helper-name yourrest-activate-update.cjs \
  --guide docs/UPDATE-YYYYMMDD-AR.txt
```

الدليل يجب أن يذكر اسم مجلد الرفع واسم المُفعِّل وإلا يرفض السكربت.

**قائمة أسماء التحديثات السابقة:** المُفعِّل يعيد استعمال نسخة اليوم الاحتياطية لو أخذها مُفعِّل تحديث سابق في اليوم نفسه، ولا يقبل إلا مجلدات نُسخ باسم معروف: `BACKUP_TRANSACTION` في `portable/activate-ui-refresh-update.cjs` (الأسماء الثابتة، ثم اسم الحزمة نفسها تلقائيًا). **كلما سُلِّمت حزمة بهوية جديدة أضف اسم نشاط حزمتها (`yourrest-<release-name>-activation-<date>`) إلى هذه القائمة قبل أن تُبنى الحزمة التي بعدها**، وإلا رفضها المُفعِّل بـ`STOP: INVALID_DAILY_BACKUP_INDEX` حين يكون التحديث الثاني في اليوم نفسه (حدث هذا لحزمة مسار المساندة بعد حزمة رسالة العميل، ثم كاد يحدث لحزمة ERP والقوالب بعد حزمة update-fallback في 3 نوفمبر؛ والاختبار `tests/baseline-update-activation.mjs` يغطي الآن حزم 17 و18 أكتوبر ومن 1 إلى 3 نوفمبر). والبروفة (`scripts/rehearse-update.mjs`) تشغّل في موقع منفصل مُفعِّلًا باسم الحزمة المنشورة قبلها (`--after-package`، وافتراضيًا الحزمة التي يسمّيها `deploy/request.json`) يأخذ نسخة اليوم أولًا، ثم مُفعِّل الحزمة الجديدة، فتفشل إن نقص الاسم.

**ترحيل جديد داخل الحزمة:** القاعدة الحية يجب أن تكون على الخط الأساسي. الأساسي الافتراضي 15 ترحيلًا (إصدار 2026-10-11)، ومن بنى فوق إصدار فيه ترحيلات أكثر يعلنه بـ`--schema-baseline N` (يُقبل من 15 إلى 99)، فمثلًا بعد تفعيل إصدار 2026-10-12 (16 ترحيلًا) تُغلَّف الحزمة التالية بلا ترحيل جديد بالأمر `--schema-baseline 16`. أي ترحيل بعده تُعلنه صراحة عند التغليف، وتشترط الحزمة أن يحمل البناء الترحيلات الأساسية + المعلنة بالضبط وإلا ترفض:

```bash
python3 scripts/package-ui-refresh-update.py ... \
  --new-migration 0015_member_devices.sql --verify-route /api/device-status=401
```

- `--new-migration` (يتكرر): اسم الترحيل بالضبط كما في `drizzle/`.
- `--schema-baseline N`: عدد الترحيلات في القاعدة الحية قبل هذه الحزمة. تشترط الحزمة أن يحمل البناء N ترحيلًا + المعلنة بالضبط، ويشترط المُفعِّل ذلك على القاعدة الحية عند `apply` (لا عند `--check`، فالتطبيق يعمل أثناءه). وهو يقبل نسخة اليوم الكاملة التي أخذها مُفعِّل سابق في اليوم نفسه بتوقيت الرياض ولو كانت عند ترحيلات أقل، فلا تُنسخ البيانات مرة ثانية.
- `--verify-route PATH=STATUS` (يتكرر): مسار جديد يفحصه `--verify` بلا جلسة (المتوقع هنا 401).
- المُفعِّل لا يكتب في القاعدة ولا يشغّل الترحيل. `--check` يعلن التغيير، والتطبيق يطبّقه عند أول Start بعد نسخة خاصة في `yourrest-crm-data/schema-backups`، و`--verify` يرفض بسبب واضح (`MIGRATION_NOT_APPLIED_START_APP_FIRST`) إن لم يبدأ التطبيق، ثم يتأكد من 16 ترحيلًا ومن بقاء كل معرفات السجلات.
- **لا رجعة بسيطة بعد الترحيل:** الإصدار القديم يرفض قاعدة فيها ترحيل أحدث. التراجع بعد نجاح الترحيل = استعادة نسخة `schema-backups` + إعادة `old-release` (دليل التحديث يشرحه، وأي بيانات بعد التشغيل تضيع). قبل الترحيل لا خسارة.
- اختبار حزمة بلا ترحيل فوق قاعدة مرحَّلة (16→16) وإعادة نسخة اليوم: `node tests/baseline-update-activation.mjs`.
- اختبار هذا المسار كاملًا: `node tests/schema-update-activation.mjs` (الحزمة الحقيقية والمُفعِّل الحقيقي وروتين الإقلاع الحقيقي على SQLite).

**بروفة كاملة قبل الرفع** (ببيانات اصطناعية، دون أي اتصال بالاستضافة): ابنِ الإصدار المثبّت حاليًا في مجلد منفصل ثم نفّذ بحساب غير مميز كما على الاستضافة:

```bash
node scripts/rehearse-update.mjs --old-release /مسار/dist/standalone-القديم --package /مسار/Yourrest-CRM-Update-YYYYMMDD.zip --out report.json
```

تُنشئ البروفة موقعًا مثبّتًا كالاستضافة، وتشغّل الإصدار القديم وتنشئ بيانات عبر واجهته، ثم تتبع خطوات الدليل: `--check` والتطبيق يعمل، رفض التبديل ما دام برنامج غير خادم Node.js يمسك مجلد التطبيق (`sleep` حقيقي)، ثم تشغيل التطبيق كما يفعل المضيف بعد Stop App وإيقاف المُفعِّل له بنفسه ومتابعته، الإيقاف والتبديل، التشغيل و`--verify`، ثم تثبت أن كل جدول ومرفق والإعدادات والواجهات لكل دور متطابقة، وأن حزمة معطوبة تُرفض دون لمس شيء. المُفعِّل يشترط أصل الموقع `https://crm.yourrest.org` تمامًا، لذلك تحتاج البروفة المنفذ 443 (صلاحية ربط المنافذ المنخفضة فقط).

عند إعلان ترحيل جديد تجرّب البروفة أيضًا طريقي التراجع بالخطوات نفسها المكتوبة في دليل التحديث: (أ) العودة قبل أول تشغيل للإصدار الجديد بإعادة `old-release`، و(ب) العودة بعد الترحيل. في (ب) تثبت أن الإصدار القديم يرفض القاعدة المرحَّلة، وأن استعادة نسخة `schema-backups` مع المجلد القديم تعيد كل جدول وكل واجهة إلى حالتها قبل التحديث. **ملفا `database.sqlite-wal` و`database.sqlite-shm` يبقيان بعد إيقاف التطبيق** ويجب إزاحتهما مع `database.sqlite` قبل نسخ النسخة الخاصة، وإلا اختلطا بالقاعدة المستعادة.

## 9-هـ. مساندة خدمة العملاء والزيارات المفقودة وتأخر الاعتماد

**القاعدة:** مساندة خدمة العملاء (ما يفتحه المندوب وما يتولاه الممثل من الزيارات المفقودة) سجل مستقل من النوع `support` يسير المسار نفسه الذي تسير عليه الشكاوى: الممثل يتواصل ويرفع، مدير الخدمة يعتمد أو يعيد، مدير المبيعات يكلّف، المشرف يفوّض، المندوب يسجّل تواصله بقناته، ثم يغلق الممثل أو يعيد إلى المندوب. الوصف الكامل في `docs/CUSTOMER-SERVICE-WORKFLOW-AR.md` (القسم 9) والخطة في `docs/qa/PLAN-SUPPORT-CHAIN-AR.md`.

| الملف | الدور |
|---|---|
| `lib/support.ts` | المنطق الخالص: من يطلب ومن يقرأ ومن يتصرف (`canRequestSupport` و`canReadSupport` و`supportPermissions`)، والمرحلة والتقدم (`supportStage` و`supportProgress` و`supportOwner`)، وسير الطلب (`supportEvents` يركّب سيرًا للصفوف القديمة)، والمرشحون للإحالة والتكليف والتفويض (`supportCandidates`)، وما ينتظر القارئ (`supportAwaiting`)، توجيه الطلب لممثل المنطقة (`supportStaff`)، قائمة الطلبات (`supportQueue`) والمفقودة (`missedVisits`) والعدّاد (`supportBadge`) وأقسام اللوحة (`supportGroups`)، وروابط الاتصال (`contactLinks`). الثوابت المسماة وحدها: `SUPPORT_TARGET_HOURS=4` و`SUPPORT_STAGE_HOURS` (مراجعة 4، تكليف 4، تفويض 4، أول تواصل 24، إغلاق 24) و`MISSED_VISIT_GRACE_DAYS=2` و`MISSED_VISIT_WINDOW_DAYS=30` و`SUPPORT_HISTORY_DAYS=30` و`SUPPORT_LIST_LIMIT=300` (حدّ العرض لا العدّ: `GET` يحسب القائمة كاملة ويقصّ العرض ويعيد الأعداد الكلية في `counts` والتولّي يبحث في الكاملة). اختباره `tests/support.mjs` |
| `app/api/support/route.ts` | `GET` (ما يراه القارئ) و`POST` بإجراءات `request` و`take` و`assign` و`submit` (رفع نتيجة الممثل؛ أول رفع هو ما يقيسه التقييم) و`forward` و`return` و`allocate` و`delegate` و`reassign` و`resolve` و`reject` و`close` و`cancel` و`seen`، بإيصالات `support-receipt` وفحص النسخة وإعادة فحص الأعضاء عند الحفظ. اختباره `tests/support-http.mjs` |

| `lib/service-queue.ts` | لمدير خدمة العملاء: طلبات الاعتماد التي تنتظره فقط (مرحلة `approval` وصلاحية `approve`) بالساعة نفسها وعلامة التأخر والعدّاد |

**التخزين بلا ترحيل:** كل طلب سجل في `crm_records` من النوع `support` بلا أب (`parent_id` فارغ)، وكل ما يخصه في `data` (الحالة `open|submitted|returned|pending_assignment|assigned|resolved|done|cancelled`، والعميل والطالب والمسؤول والمتولّي ومدير الخدمة ومدير المبيعات والمشرف والمندوب المكلَّف، ونتيجة الممثل `result` ونتيجة المندوب `resolution` والإغلاق `closure` وسير الطلب `events`؛ كلها اختيارية فتبقى الصفوف القديمة صالحة). لذلك لا تراه قواعد الزيارات ولا الطلبات ولا حذف العميل، ويتجاهله الإصدار القديم، ويستبعده `scopeRecords` من سجلات مدير النظام. التراجع = إعادة مجلد `release` القديم فقط دون استعادة القاعدة. حذف عميل له طلبات يمرّ، وتبقى طلباته مخفية. لا تخزّن طلبًا بنوع `activity` أبدًا: سيُحسب زيارة ويصير خطة العميل الأخيرة.

**الزيارة المفقودة مشتقة عند القراءة** من خطة العميل الأخيرة (`customerPlanSource`) على كل السجلات لا على نطاق القارئ، فلا جدول ولا مهمة مجدولة. لا يُكتب شيء حتى يتولاها أحد، وحينها يُنشأ السجل بمعرّف ثابت `support-missed-<معرّف الزيارة>` فلا يتولاها اثنان. لا يرى ممثل الخدمة من الزيارة إلا الخطة (الإجراء والموعد والنتيجة) واسم المندوب.

**الصلاحيات:** المندوب والمشرف والمدير يطلبون لعملاء فريقهم أو لعميل زاروه، وخدمة العملاء لا تطلب. التولّي والتواصل والرفع والإغلاق لممثل الخدمة ضمن فرع العميل ومنطقته، والاعتماد لمدير الخدمة الذي يتبعه الممثل، والتكليف لمدير المبيعات المربوط به المدير (`salesManagerId`) وحده وإن رأى كل مدير مبيعات فريق الطلب، والتفويض للمشرف المكلَّف. الإلغاء قبل التكليف لصاحب الطلب ومن فوقه ولمدير الخدمة (للمفقودة ولما يراجعه)، ولمدير النظام في أي مرحلة مفتوحة. حارس الطلب المفتوح الواحد لكل عميل (`OPEN_CUSTOMER`) يمتد على المسار كله. أي مسار جديد بعد هذا يمرّ على `tests/server-authorization.mjs`.

الأرقام للمتابعة: لا تدخل في حركة ولا زيارة ولا مستهدف ولا تقييم المناديب؛ وتقرؤها «تقييم خدمة العملاء» (القسم 9-ط) لتقييم ممثلي الخدمة ومديريها. لا تجعل مهلة تمنع إجراءً أو تغيّر صلاحية.

## 9-و. موقع العميل الجديد: موقع الجهاز أو موقع آخر

**القاعدة:** موقع العميل الجديد يُلتقط من الجهاز افتراضيًا كما كان. «موقع آخر» اختيار صريح من العضو: يكتب الإحداثيات أو يلصق رابط خرائط كاملًا فيه الإحداثيات، أو يضغط المكان على الخريطة ويسحب الدبوس ثم يؤكد. لا يتغير موقع عميل قائم عند فتحه، ولا موقع الزيارة (يبقى من الجهاز)، ولا شيء مما يستند إلى الموقع بعد الحفظ (خريطة المصانع والاتجاهات وفحص الوصول).

| الملف | الدور |
|---|---|
| `app/customer-entry-fields.tsx` | `CustomerLocationFields`: اختيار المصدر بأزرار اختيار حقيقية (`customer-choice`)، التقاط الجهاز، كتابة المكان، `applyPoint` للمكان المكتوب أو المختار، `lookup` للعنوان الوطني. يستعمله نموذج العميل في `app/crm-app.tsx` و«إضافة عميل» في `app/visit-customer-picker.tsx` |

| `lib/customer-location.ts` | `coordinatesFromText`: ما يُقرأ إحداثيات (زوج بفاصلة عادية أو عربية، `@lat,lng`، `?q=` و`query=`)، ولا شيء غير ذلك: لا اسم مدينة ولا رابط مختصر. و`tidyLocationText`: رابط يحمل إحداثيات يصير الزوج الذي يشير إليه (الحقل 250 حرفًا والروابط أطول) |
| `lib/customer-fields.ts` | `prepareCustomerLocation` قواعد الخادم، و`customerLocationProblem` يطبقها على نسخة في النموذج قبل الحفظ أو الوضع في طابور الجهاز دون الحكم على ساعة الهاتف |

**ما يُخزَّن:** المكان اليدوي رقمان `latitude` و`longitude` يحسبهما الخادم من النص، بلا `locationSource` ولا `locationCapturedAt` ولا `locationAccuracy`: لا يُسمّى التقاطًا. ادعاء التقاط لا يطابق النص يُرفض ولا يُعاد وسمه. الخادم لم يتغير في هذا الإصدار.

**الفحص قبل الحفظ:** نص ليس إحداثيات يُشرح فور كتابته ويُرفض في النموذج قبل أي طلب، حتى دون اتصال، لأن العميل المحفوظ على الجهاز لا يفحصه الخادم إلا عند المزامنة وقد فات تصحيحه. لا يحكم الفحص على وقت الالتقاط بساعة الهاتف: وقت الموقع قد يأتي من نظام التحديد ويختلف عن ساعة الجهاز، فالحكم عليه للخادم وحده.

**العنوان الوطني:** يُجلب بعد المكان المكتوب عند مغادرة الحقل ولا يحجز الحفظ (الضغط على «حفظ» هو نفسه ما يغادر الحقل فلا يُضيَّع)، وبعد المكان المختار على الخريطة ويحجز الحفظ حتى يصل أو تنتهي مهلته (12 ثانية)، كالمكان الملتقط. يملأ الحقول الفارغة فقط، ويُمسح ما مُلئ تلقائيًا لمكان سابق إن لم يغيّره العضو، ولا يستبدل جواب متأخر ما كُتب بعده. دون اتصال يُتجاوز. المزوّد غير مفعّل على الاستضافة، فتظهر عبارة «غير متاح» فقط.

**الهاتف الذي لا يجيب:** اختيار «موقع آخر» ينهي انتظار الالتقاط ويفتح الحفظ فورًا، ورسالة خطأ التحديد تدل عليه.

**الحدود:** لا بحث باسم مكان أو عنوان (لا ترميز جغرافي)، ولا فك للروابط المختصرة (`maps.app.goo.gl` لا تحمل إحداثيات؛ يُلصق الرابط الكامل). عنوان وطني بالعكس (من العنوان إلى الموقع) غير مبني. البلاطات من خوادم OpenStreetMap العامة وتحتاج إنترنت؛ دونه يبقى وضع الدبوس وكتابة الإحداثيات.

**الاختبارات:** `tests/customer-entry-fields-ui.mjs` (الواجهة)، `tests/customer-location-rules.mjs` (القواعد)، `tests/rep-customer-create.mjs` (الخادم)، `tests/location-picker-browser.mjs` (Chromium على النسخة المبنية، بوابة `browser`).

## 9-ز. شكاوى العملاء: من خدمة العملاء إلى المندوب حتى الإغلاق

**القاعدة:** الشكوى سجل مستقل من النوع `complaint` في `crm_records` بلا أب، بلا ترحيل، كالمساندة. يسجّلها ممثل خدمة العملاء، يراجعها مديره ويحيلها إلى مدير المبيعات المرتبط به، فيكلّف مندوبًا أو مشرفًا في فرع العميل يغطي منطقته (المندوب الحالي للعميل مقترح أولًا)، يسجّل المندوب تواصلاته داخل الشكوى ثم الحل، وتتأكد خدمة العملاء من العميل وتغلقها أو تعيدها. الوصف الكامل في `docs/CUSTOMER-SERVICE-WORKFLOW-AR.md` (القسم 10).

**من يرى:** مدير النظام الكل. ممثل الخدمة شكاوى فرعه في المناطق التي يغطيها. مدير الخدمة ما سجّله فريقه وما أحاله، وما لا مدير له. مدير المبيعات ما أُحيل إليه وما يحمله أي مندوب أو مشرف (نطاق مدير المبيعات في `salesScopeMemberIds` يشمل كل المناديب والمشرفين، كما في الطلبات). المشرف ما يحمله هو أو مندوبوه. المندوب ما يحمله.

**من يُسأل (`awaiting`):** مدير الخدمة المراجعة؛ الممثل التعديل بعد الإعادة وتأكيد الإغلاق بعد الحل؛ مدير المبيعات التكليف؛ المشرف التفويض؛ المندوب أول تواصل ثم الحل. مدير النظام لا يُسأل إلا حين لا يوجد من يُسأل (مسجِّل بلا مدير، أو مسجِّل لم يعد نشطًا عند الإغلاق). العدّاد هو عدد ما يُسأل عنه القارئ.

**ما يُخزَّن:** كل شيء في `data` (الحالة من `submitted` إلى `closed` أو `cancelled`، الأطراف، التقرير، أختام كل انتقال، `resolution` و`closure`، `updates` و`notes` و`events` لسير الشكوى، `previousAssignees`). الأرقام للعرض فقط.

**الحدود:** لا مرفقات ولا إشعار هاتف. العمل متصلًا فقط. لا يُحتسب تواصل المندوب زيارة. التقرير الشهري يقرأ كل صفوف الشكاوى عند فتحه (أعدادها صغيرة؛ لا حد) ولا يُحدَّث تلقائيًا؛ إن كثرت الشكاوى على مدى سنوات فحدّه بالأشهر الأخيرة.

**الاختبارات:** `tests/complaints.mjs` و`tests/complaints-ui.mjs` و`tests/complaint-report.mjs` و`tests/complaint-report-ui.mjs` (البوابة الافتراضية)، `tests/complaints-http.mjs` و`tests/complaint-report-http.mjs` (بوابة البناء)، `tests/complaints-browser.mjs` (بوابة المتصفح)، و`tests/role-ui.mjs` و`tests/mobile-navigation-ui.mjs` و`tests/server-authorization.mjs` و`tests/baseline-update-activation.mjs` محدَّثة.

## 9-ح. الإصدار الإجباري لتطبيق أندرويد ومناطق متعددة للعضو

**الإصدار الإجباري (منذ 2026-11-15 بقاعدة المالك في GSCO من 2026-10-31: «مفيش حاجة اسمها تحديث اختياري»):** كل إصدار ينشره الموقع من تطبيق أندرويد إلزامي لكل من يفتح التطبيق أيًّا كان دوره (المندوب والمشرف والمدير والإدارة وخدمة العملاء ومديرها)، ولا يوجد زر «متابعة» أو «لاحقًا» ولا عبارة «يمكنك متابعة عملك». أقل إصدار مسموح هو دائمًا أحدث إصدار منشور: `minimumVersionCode` في `lib/app-update-release.json` يساوي `versionCode` (يكتبه `scripts/publish-android-release.mjs` كذلك، ويقرؤه `parseAppRelease` في `lib/app-update.ts` مساويًا لـ`versionCode` مهما كُتب فيه، ويتحقق `tests/app-update-release.mjs` منه في الملف المقدَّم). القرار في `appUpdateRequired` (`lib/app-update.ts`): الموقع يقرأ إعلانه `GET /api/app-update` عند فتح التطبيق وعند العودة إليه وعند عودة الشبكة وكل 15 دقيقة، ويسأل عن ملف APK نفسه بطلب `HEAD`؛ إن كان الإصدار المثبت أقدم (برقم الإصدار الدقيق من جسر التحديث في 1.0.10 فأعلى، أو باسم الإصدار من التطبيقات الأقدم أو من خدمة التتبع) ظهرت شاشة «حدّث تطبيق يورست للمتابعة» في `app/tracking-gate.tsx` قبل أي فحص للتتبع: تذكر الإصدارين وما الجديد في الإصدار المطلوب، وفيها لوحة التحديث (التنزيل والتثبيت داخل التطبيق، «إعادة المحاولة» عند فشل التنزيل، «ثبّت عن طريق المتصفح»، أو رابط الملف للتطبيقات الأقدم) وتسجيل الخروج. **لا تُحجب أحدًا حين لا يمكن التحديث لسبب خارج يده** (كما في GSCO): بلا شبكة، أو تعذرت قراءة الإعلان، أو لم يُجب ملف APK على الموقع (404 أو خطأ خادم)، أو الإصدار المثبت غير معروف؛ عندها تبقى مساحة العمل وشريط التحديث يقول لماذا ينتظر التحديث. المتصفح على الحاسوب أو الهاتف لا يُحجب أبدًا، ولا التطبيق المساوي للإصدار المنشور أو الأحدث منه. **البيانات:** تحت الشاشة تبقى مساحة العمل مركّبة ومخفية (لا يُعاد تركيبها)، فالنماذج المفتوحة باقية، والإدخالات المحفوظة على الهاتف تُرفع كما كانت (عند التحميل وكل 30 ثانية وعند عودة الشبكة)؛ الشاشة تعدّها («إدخالات محفوظة على الهاتف بانتظار الرفع») وفيها «رفع الآن»، والتحديث فوق التطبيق لا يحذفها. إن كان في مساحة العمل نافذة مفتوحة (نموذج زيارة أو عميل…) تنتظر الشاشة حتى تُحفظ أو تُغلق، وبعد ظهور الشاشة لا ترفعها نافذة تُفتح تحتها (طلب من إشعار مثلًا) وتبقى أزرارها قابلة للضغط. لا يُفرض شيء على الخادم: لا يحمل أي طلب من التطبيق رقم إصداره (وكيل المستخدم `YourrestCRM-Android/1` ثابت)، ورفض طلبات التطبيق القديم كان سيوقف رفع نقاط خط السير والإدخالات المحفوظة. نشر إصدار جديد (تحديث `lib/app-update-release.json` و`public/app-update.json` والملف في `public/downloads`) يحجب كل من لم يحدّث فور قراءة الإعلان، فانشره في وقت مناسب. صفحة الفريق تكتب «إصدار قديم؛ المطلوب كذا» لهاتف آخر تقريره أقدم من المقدَّم (`phoneBrief` في `lib/tracking-coverage-text.ts`). الاختبارات: `tests/app-update-ui.mjs` و`tests/tracking-gate.mjs` و`tests/tracking-gate-ui.mjs` (البوابة الافتراضية)، `tests/app-update-release.mjs` (بوابة البناء)، `tests/app-update-browser.mjs` و`tests/tracking-gate-browser.mjs` (بوابة المتصفح، على محاكي تطبيق أندرويد)، و`tests/tracking-coverage.mjs`.

**المناطق المتعددة:** نطاق العضو `region_scope` نص واحد في العمود نفسه بلا ترحيل: `all`، أو معرّف منطقة، أو عدة معرّفات بترتيب القائمة مفصولة بفاصلة (`central,eastern`). `canonicalRegionScope` في `lib/regions.ts` توحّد ما يرسله النموذج (مصفوفة أو نص) ومسار الأعضاء يرفض ما لا يحوي منطقة معروفة. `memberCanAccessRegion` تقبل عميلًا في أي منطقة من مناطق العضو، `regionScopesOverlap` تحدد من يرى من (`regionMembers`، أعضاء التتبع)، و`regionScopeSql` تبني شرطًا يقبل صفوف `crm_erp_sales` التي تتقاطع منطقتها مع القارئ (مبيعات ERP، التقييم، أدلة الأداء) بدل المطابقة التامة. حراس الكتابة التي تقارن `region_scope=?` تبقى مطابقة تامة للنص الموحّد نفسه. النموذج `MemberRegionField` مربعات اختيار، و`CustomerRegionField` يحصر منطقة العميل الجديد في مناطق العضو ويثبّتها حين تكون واحدة. التراجع إلى إصدار أقدم يترك صاحب المناطق المتعددة بلا عملاء مرئيين حتى يُعاد ضبطه لأن الإصدار الأقدم يطابق النص تمامًا. الاختبارات: `tests/regions.mjs` و`tests/crm-regression.mjs` و`tests/member-regions-browser.mjs`.

**التخزين:** ثلاثة أنواع في `crm_records` بلا أب: `service_audit` (`service-audit-<requestId>`: الممثل والشهر والمرجع والدرجات والمجموع والنتيجة وتحقق الاتصال والملاحظة والمدقق، ويُحذف بوسم `deleted` لا بمسح السطر)، `service_kpi_month` (`service-kpi-month-<managerId|none>-<YYYY-MM>`: شهادة الإقفال بالفريق والإعدادات والدرجات، وإعادة الفتح بوسم `reopened` ثم يُستبدل السطر عند إعادة الإقفال)، `service_kpi_settings` (`service-kpi-settings`، بنسخة السطر للتعارض). أبقِ هذه الصفوف صغيرة: سياق مدير النظام يحمّل كل `crm_records`. ولا تسمِّ في بياناتها `performedBy` أو `recordedByEmail` أو `responsibleId` فهي حقول يقرأ منها مسار المبيعات المؤلف.

**قواعد لمن يعدّل المنطق:**
1. يُنسب كل رقم إلى الشهر الذي وقع فيه حدثه، لا إلى حالة الشكوى الحالية: ولهذا يبقى جواب شهر منتهٍ ثابتًا. لا تقرأ `status` ولا `closedAt` ولا `submittedAt` (يُعاد ضبطه عند إعادة الإرسال) في حساب شهر ماضٍ؛ اقرأ الأحداث.
2. لا يُحاسَب ممثل على ما لا يملكه: عدم رضا العميل لا يُحسب ضده.
3. مؤشر دون أقل حالاته يُخرَج من الدرجة ويُوزَّع وزنه، لا يُحتسب كاملًا ولا صفرًا.
   وكذلك «لا مفتوح» في ضبط المتراكم (`emptyIsFull`): يُحتسب كاملًا بجانب مؤشر مقيس آخر فقط، وإن كان وحده فالبطاقة بلا درجة؛ يضبط ذلك `scorecard`.
4. مجموع أوزان كل بطاقة 100 ومجموع درجات التدقيق 100، يتحقق منه `settingsProblem` على الخادم والواجهة معًا.
5. بعد الإقفال تُقرأ الإعدادات والفريق من الشهادة لا من الحال. وأي حقل جديد في الشهادة يكتب مع `monthCertificate` ويُقرأ بقيمة افتراضية.
6. الأرقام لتقييم خدمة العملاء وحدها: لا تدخل في حركة ولا زيارة ولا مستهدف ولا تقييم المناديب، ولا تمنع مهلة إجراءً.
7. الاتجاه ووسيط الفريق (`trend` في جواب `serviceKpiView`): آخر ثلاثة أشهر لكل بطاقة مرئية، ووسيط الفريق لمدير الخدمة ومدير النظام فقط، يحسبهما `serviceKpiMonth` ثلاث مرات في الطلب نفسه بلا حفظ شيء. لا يكلّفان سطرًا في القاعدة؛ وتكلفتهما ثلاثة أمثال حساب الشهر في الذاكرة. إن أبطأت الصفحة مع كبر البيانات فاقصر القراءة على سنتين كما في «الحدود». والواجهة لا تعرض سطر الاتجاه إلا إذا كان لأحد الشهرين السابقين درجة.

**الحدود:** لا مكالمات ولا واتساب ولا دوام. طلبات الخدمة في «دقة التسجيل» ومراجعة المدير فقط. `GET` يقرأ كل الشكاوى والمساندة وطلبات الخدمة عند الفتح ويحسب الشهر وشهرين قبله. القياس على بيانات اصطناعية تعادل عامين لـ16 ممثلًا (6000 شكوى و12000 طلب مساندة و2000 طلب خدمة و500 تدقيق، على النسخة المبنية وجهاز الاختبار): نحو 0.2 ثانية حساب الشهر الواحد في الذاكرة، و1.2 إلى 1.7 ثانية للطلب كاملًا بما فيه قراءة الصفوف، لأي دور. أعداد اليوم أقل بكثير. إن بلغ الطلب ثانيتين على الاستضافة فاقصر قراءة الصفوف على سنتين (`lib/service-kpi-rows.ts`) أو احفظ جواب الأشهر المنتهية. لا إشعار هاتف ولا تغيير في أندرويد.

## 9-ي. الزيارة لا تُسجَّل إلا في مكان العميل

**القاعدة:** زيارة المندوب الميدانية (النوع «زيارة»، لا الاتصال ولا البريد ولا الرسالة) تُحفظ فقط إن كان موقع جهازه ضمن **300 متر** من موقع العميل، ويتسع الحد بدقة الجهاز نفسه حتى **100 متر** إضافية. قياس دقته أسوأ من **300 متر** لا يقبل ولا يرفض (رسالة «غير مؤكد» ويُطلب تحديث الموقع) إلا إن كان بعيدًا عن العميل رغم هامش خطئه. وصول أكده تتبع المسار (محطة خط السير بوصول ولم تُغادر) يحسم القبول أيًّا كان القياس. عميل بلا موقع مسجَّل لا يُبعَد عن شيء: تُقبل أول زيارة ويصير موقعها موقع العميل مع ملاحظة «من زيارة فلان بتاريخ كذا» في ورقته (`_locationFromVisit`). **المحجوب المندوب فقط**؛ المشرف والمدير ومدير النظام تُحفظ زيارتهم وتُوسم «خارج موقع العميل» (`placeOutside`) ويظهر ذلك لمن يقرأها. تعديل زيارة محفوظة لا يُحكم عليه من جديد. بلا ترحيل.

## 9-س. تنبيه «يوجد تحديث للتطبيق، أعد التحميل»

**المشكلة:** صفحة مفتوحة قبل النشر تبقى تشغّل الكود القديم حتى تُغلق وتُفتح، فلا يرى المندوب الأزرار الجديدة. **الحل:** تكتشف الصفحة أن إصدارًا أحدث منشور وتخبر المستخدم، ولا تعيد التحميل وحدها أبدًا.

| الموضع | ما فيه |
|---|---|
| `lib/build-freshness.ts` | `runningScripts` (سكربتات الصفحة المجزّأة تحت `/_next/static/` أو `/offline-app/assets/`)، و`judge` (الحكم: 404/410 = `stale`، 2xx = `current`، غير ذلك أو فشل شبكة = `unknown` ولا شريط)، و`createBuildFreshness` (المتحكّم بالبيئة المحقونة: فحص عند الاشتراك وكل `FRESHNESS_INTERVAL_MS`=10 دقائق وعند العودة بعد `FRESHNESS_RESUME_GAP_MS`=60 ثانية، لا دون اتصال ولا والصفحة مخفية، طلب واحد لكل جولة، حد `FRESHNESS_HEAD_LIMIT`=6)، و`buildFreshness()` المتحكّم الفعلي |
| `app/build-notice.tsx` و`.css` | الشريط (يُعرض إن كان الحكم `stale` فقط) وزر «أعد التحميل» بارتفاع 44px؛ في `workspace-notices` بجانب شريط تحديث أندرويد |
| `public/sw.js` | مستمع `message`: `skipWaiting()` **فقط** عند رسالة `yourrest-activate-update` الصريحة من الصفحة. لا `skipWaiting` في `install` ولا `activate` (يفحصه `tests/offline-shell.mjs`) |

- **ما يفحصه:** `HEAD` بـ`cache:'no-store'` لكل سكربت (الأطول مرة واحدة)؛ المختفي = إصدار أحدث لأن كل نشر يغيّر أسماء الملفات (يتغير `index-*.js` بتغير أي جزء). نسخة الشغل بدون نت تُقارن بـ`/offline-shell-manifest.json`.

- **لا يعمل على الصفحات المفتوحة قبل هذا الإصدار** (لا تحمل الكود)؛ تحتاج مرة إغلاقًا وفتحًا.

## 9-ع. المُفعِّل يوقف عمليات التطبيق التي أعاد المضيف تشغيلها

**المشكلة:** استضافة Node.js في cPanel تُعيد تشغيل التطبيق عند وصول أي طلب (تتبع المناديب يرسل طلبات طوال النهار)، فيعود `lsnode` بعد **Stop App** ويمنع المُفعِّل بـ`STOP: APP_OR_DATA_STILL_IN_USE`. كان الحل اليدوي أمر `kill` ثم المُفعِّل فورًا (حدث في تفعيل 21 أكتوبر 2026).

**الحل (في `portable/activate-ui-refresh-update.cjs`، يدخل أول حزمة تُبنى بعده):**

| الدالة | ما تفعله |
|---|---|
| `appServerProcesses(p, procRoot)` | عمليات الحساب التي هي **خادم Node.js نفسه** (`lsnode` أو `node`) وتمسك مجلد التطبيق أو البيانات (مجلد العمل، أو سطر الأمر، أو ملف مفتوح في البيانات). لا تعيد المُفعِّل نفسه ولا سلسلة آبائه (الطرفية التي شغّلته)، ولا عملية انتهت وتنتظر الجمع (`Z`)، ولا أي برنامج غير Node.js كصدفة `bash` جالسة في المجلد. |
| `terminateApp(p, options)` | `SIGTERM` أولًا وانتظار حتى 15 ثانية، ثم `SIGKILL` لمن لم يخرج وانتظار 5 ثوانٍ، وتعيد الفحص وتكرر حتى 3 جولات إن أعاد المضيف تشغيله. تطبع «APP STILL RUNNING … STOPPING IT NOW» ثم «APP PROCESSES STOPPED: n». |
| `run()` | تستدعيها **مرة واحدة** قبل أول `stopped(p)`، أي قبل أي قفل أو نقطة حفظ، ولا تستدعيها في `--check` ولا `--verify`. **الفحوص اللاحقة** (قبل النسخ وبعده وقبل التبديل) تبقى صارمة وتفشل ولا توقف شيئًا. تعمل فقط حين يكون `stopped` هو الافتراضي `ensureStopped`؛ الاختبارات التي تحقن `stopped` لا تلمس عمليات الجهاز. |

- **ما لا يتغير:** `ensureStopped` كما هو، فإن بقي شيء غير خادم Node.js يمسك المجلد (صدفة، سكربت فحص) يظهر `APP_OR_DATA_STILL_IN_USE` كالسابق. وخطوة **Stop App** في cPanel تبقى الخطوة الأولى في الدليل؛ المُفعِّل يلتقط ما أعاده المضيف فقط.
- **حدّه:** إن أعاد المضيف تشغيل التطبيق **بعد** الفحص الأول وأثناء النسخ فالفحص اللاحق يفشل كما قبل، ولا شيء يتغير في الإنتاج قبل التبديل. هذا نادر لأن الإيقاف والفحص الأول يسبقان النسخ بثوانٍ.
- **اختبارها:** `tests/activate-auto-stop.mjs` (31 فحصًا، بوابة افتراضية): شجرات `/proc` وهمية (lsnode و node بمجلد العمل أو الأمر أو ملف مفتوح في البيانات، وإبقاء `bash` و`sleep` و`nodemon` وعملية Node.js في مشروع آخر، وحماية المُفعِّل وآبائه، و`SIGTERM` يكفي، و`SIGTERM` المُتجاهَل يلحقه `SIGKILL`، والزومبي لا يُنتظر ولا يُقتل، وإعادة تشغيل بين جولتين، ومضيف لا يترك التطبيق متوقفًا فيُنهى بثلاث جولات ثم الرفض الصارم، وفشل الإرسال `EPERM` يُسجَّل ولا يُرمى) ثم عمليات حقيقية على `/proc` الحقيقي: خادم Node.js في مجلد التطبيق يُوقَف و`sleep` في المجلد نفسه لا يُمس. ويثبّت أن الاستدعاء داخل `run()` واحد وقبل `stopped(p)`.

### 9-ف-2. فتح التطبيق على نسخة الجهاز (2026-10-29)

**القياس قبل:** على موبايل أبطأ 4 مرات و4G بطيء، المندوب يفتح التطبيق المعتاد (والنسخة محفوظة على جهازه) في نحو 1.85 ثانية، و3.25 ثانية إن كان زمن الوصول للسيرفر 600 مللي ثانية؛ لأن التطبيق كان ينتظر رد `/api/crm` ثم الحفظ على الجهاز ثم يرسم، ويطلب المساندة والشكاوى بعدها لا معها. وكان يعيد تنزيل 112 كيلو من سكربتاته مع **كل** فتح.

| ماذا | أين | القاعدة |

**بعد، نفس الظروف:** الفتح المعتاد 1.2 ثانية بدل 1.85، و1.4 بدل 3.25 مع 600 مللي ثانية للسيرفر (البيانات تظهر قبل رد السيرفر)، ولا سكربت يُنزَّل في الفتح المعتاد بدل 112 كيلو. أول فتح على جهاز جديد بلا تغيير (المرحلة 3).

- **الاختبارات:** `tests/same-snapshot.mjs` (افتراضي)؛ `tests/open-cached-browser.mjs` (متصفح بعد `pnpm build`): رد السيرفر يُمسك عمدًا فيُرى كل شيء بترتيبه: أول فتح ينتظر، الفتح التالي يعرض النسخة مع السطر ثم الرد يحل محلها، سيرفر لا يُصل إليه يترك النسخة دون خطأ، حساب آخر على نفس الجهاز لا يرى النسخة، وجلسة أُنهيت في السيرفر لا تبقى نسختها وتُقفل؛ `tests/build-notice-browser.mjs` يتأكد من `?release-check` ومن أن الفتح التالي يأخذ كل السكربتات من الذاكرة.

## 9-ص. الرفع إلى الاستضافة من GitHub بتوكن cPanel (كما في سديم)

بدل تنفيذ خطوات دليل التحديث يدويًا في Terminal cPanel، ينفّذها GitHub نفسه بنفس المُفعِّل وبنفس الترتيب، بطريقة نظام سديم: توكن API من cPanel، بلا مفتاح SSH. الملفات: `.github/workflows/deploy.yml` و`scripts/deploy-cpanel.mjs` و`scripts/hosting-cron.sh` و`scripts/hosting-deploy.sh`.

- **الإعداد مرة واحدة (المالك):** cPanel ← Security ← Manage API Tokens ← Create، ثم في GitHub: Settings ← Secrets and variables ← Actions ← New repository secret باسم `CPANEL_API_TOKEN`. هذا هو السر الوحيد اللازم؛ `CPANEL_HOST` و`CPANEL_USER` اختياريان (الافتراضي `premium137.web-hosting.com` و`youriedx`). القيمة تُنظَّف من المسافات وعلامات الاتجاه التي يجلبها النسخ من رسالة عربية، والتوكن لا يُطبع أبدًا.
- **الحزمة:** تُبنى وتُجرَّب البروفة الكاملة هنا كالمعتاد، ثم تُلتزم الحزمة نفسها (نفس SHA256 المسلَّم) في `deploy/packages/`، فما يُرفع هو ما جُرِّب بالبايت. احذف الحزمة السابقة من المجلد عند إضافة الجديدة.
- **التشغيل:** دفع `deploy/request.json` إلى `main` أو فرع `claude/**`، أو يدويًا من تبويب Actions بعد وصول الـworkflow إلى `main` (GitHub لا يعرض التشغيل اليدوي إلا لما في الفرع الافتراضي؛ الوضع المختار هناك يحل محل وضع الملف):
  `{"mode": "check", "package": "deploy/packages/Yourrest-CRM-Update-Speed-20261029.zip", "sha256": "c03d…", "stage": "yourrest-crm-update-speed-20261029", "helper": "yourrest-activate-update-speed.cjs"}`.
  الخطوة الأولى تتحقق من الطلب: SHA256 الحزمة الملتزمة يطابق الطلب، وفيها `release/` و`RELEASE-SHA256SUMS.txt` والمُفعِّل في جذرها، والأسماء كما في دليل التحديث.
- **كيف يُنفَّذ على الاستضافة:** واجهة cPanel تنقل الملفات لكنها لا تنفّذ أوامر. لذلك `deploy-cpanel.mjs`: يتأكد أن التوكن يفتح الحساب وأن `yourrest-crm` موجود؛ يرفع الحزمة إلى مجلد البيت (كما في الدليل) والسكربتين إلى `~/yourrest-deploy`؛ يكتب ملف الطلب؛ ثم يضيف **سطر cron مؤقتًا** كل دقيقة يشغّل `hosting-cron.sh`، الذي يأخذ الطلب مرة واحدة (`mv` ذري) ويشغّل `hosting-deploy.sh` ويكتب الناتج في `log-<run>` ورمز الخروج في `done-<run>`. الـworkflow يقرأ الناتج أولًا بأول ويعرضه، ثم **يحذف سطر cron** في كل الأحوال، ويحذف أي طلب لم يُؤخذ، فلا يعمل طلب لاحقًا وحده. علامة `running-<run>` تمنع تشغيلين معًا (تُتجاهل إن زاد عمرها عن ساعتين).
- **الأوضاع (`hosting-deploy.sh`):**
  - `check`: فكّ الحزمة في مجلدها و`--check`، والتطبيق يعمل؛ ويطبع هل `cloudlinux-selector` متاح وحالة التطبيق فيه (دون متغيرات البيئة).
  - `deploy`: `--check`، إيقاف التطبيق بـ`cloudlinux-selector stop` إن وُجد (وإلا يوقفه المُفعِّل بنفسه)، المُفعِّل (النسخة الاحتياطية والتبديل)، التشغيل بـ`cloudlinux-selector start`، ثم `--verify` حتى ست محاولات. إن توقف المُفعِّل **قبل** التبديل يُعاد تشغيل التطبيق القديم كما هو ويفشل التشغيل بمخرجات المُفعِّل. دون `cloudlinux-selector` يشغّل المضيف التطبيق مع أول طلب؛ إن لم يُجب ينتهي برمز 4: Start App يدويًا ثم `mode=verify`.
  - `verify`: `--verify` فقط، ولا تُرفع حزمة.
  - `backup`: `{"mode": "backup"}`: نسخة احتياطية الآن بأدوات الإصدار الحي (`release/operations/backup-scheduled.mjs` إلى `~/yourrest-crm-backups` مع الاحتفاظ بـ14)، ثم `restore.mjs verify` عليها، ثم سطر cron يومي بالأمر الذي يطبعه `backup-cron.mjs` الساعة 03:15 بتوقيت السعودية محسوبة من فرق توقيت الخادم. السطر يُضاف مرة واحدة فقط (لا يُكرَّر إن وُجد) وبعد نسخة سليمة فقط. التطبيق يعمل طوال الوقت.
  - `diagnose`: فحص للقراءة فقط على البيانات الحية دون حزمة ولا إيقاف: `{"mode": "diagnose", "script": "scripts/diagnose/<name>.cjs"}`. يُرفع السكربت باسم `yourrest-deploy/diagnose.cjs` ويُشغَّل بـNode الحساب، ويظهر ناتجه في سجل الـjob. القاعدة: سكربت `scripts/diagnose/` يفتح القاعدة `readOnly` ولا يكتب شيئًا، ويطبع أعدادًا ومعرّفات سجلات فقط (لا أسماء ولا هواتف ولا أرقام فواتير)، وله اختبار على قاعدة اصطناعية. ثاني سكربت: `backups.cjs` (هل في نسخ احتياطية يومية: سطر cron، آخر نجاح، عدد النسخ، نقاط التفعيل، المساحة). أول سكربت: `arabic-digits.cjs` (هل الأرقام العربية في أرقام الفواتير وأكواد العملاء تفصل سجلًا عن توأمه في ERP). نتيجة 2026-10-31: لا أرقام عربية في البيانات الحية. بعدها صار مفتاح الفاتورة ومفتاح كود العميل يحوّلان ٠-٩ و۰-۹ إلى أرقام إنجليزية، فـ«INV-١٠٢٣» و«INV-1023» فاتورة واحدة؛ أعد هذا الفحص قبل رفع أول حزمة تحمل هذا التعديل، فإن ظهرت أرقام عربية فلا تُرفع الحزمة قبل مراجعة مفاتيحها المخزنة.
  - `prune`: تفضية المساحة من النسخ القديمة: `{"mode": "prune", "dryRun": true, "remove": ["<اسم في مجلد الحساب>", ...]}`. يُرفع `scripts/prune/old-copies.cjs` باسم `yourrest-deploy/prune.cjs` والقائمة بجانبه، ويفحص القائمة كلها قبل مسح أي شيء: نسخ قديمة لنا فقط (يبدأ اسمها بـ`yourrest-` أو حزمة `Yourrest-CRM-…zip`)، ليست التطبيق ولا البيانات ولا النسخ الليلية ولا الفهرس اليومي ولا مجلد الرفع، لم يتغيّر فيها شيء في آخر 48 ساعة، ليست نقطة نسخة اليوم الأحدث، لا يشير إليها رابط في التطبيق ولا سطر cron، لا تحديث ولا نسخة تعمل، ونسخة الليلة الأخيرة ناجحة من أقل من 30 ساعة وتتحقق بـ`restore.mjs verify`. أي رفض لا يمسح شيئًا (`PRUNE STOP <السبب>`). يُشغَّل أولًا بـ`dryRun: true` (يقول ما سيُمسح وكم سيوفّر)، ثم بـ`false` بعد موافقة المالك على القائمة. فحص المساحة للقراءة فقط: `scripts/diagnose/space.cjs`.
  - `mold-link`: ربط طلبات القوالب القديمة (التي استوردها تطبيق المنتجات بأرقامها) بطلبات CRM بما أكّده المالك: `{"mode": "mold-link", "dryRun": true}`. يُرفع `scripts/mold-link/legacy-link.cjs` باسم `yourrest-deploy/mold-link.cjs` والطلب بجانبه، ويشغّل أداة الإصدار الحي `release/operations/mold-import.mjs --key yourrest` على نسخة خاصة مؤقتة من ملف الطلبات القديمة: كل مندوب في القائمة المؤكَّدة داخل الأداة (`CONFIRMED`: رقم أول طلب له ← معرّف عضو CRM) يُكتب باسمه في الـCRM، وطلبات «المركز الرئيسي» (`LEFT_OUT`) تُترك بلا ربط. يتوقف قبل أي نداء للإنتاج إن ظهر اسم مندوب غير مؤكَّد، أو لم يعد العضو المؤكَّد مندوبًا نشطًا، أو تغيّر اسمه في الـCRM فلم يعد يحمل كلمات اسم الشيت (`MOLD LINK STOP <السبب>`). `dryRun: true` يفتح القاعدة للقراءة فقط ولا ينادي أحدًا ويقول هل مفتاح الإنتاج مضبوط؛ `false` يربط كل طلب في الإنتاج أولًا ثم يحفظه في الـCRM، وإعادة التشغيل لا تكرر شيئًا. يطبع أرقام الطلبات والأعداد والأسباب فقط. يسبقه `backup`، ويُشغَّل بـ`false` بعد موافقة المالك على نتيجة التجربة. سبب عدم المطابقة يُقرأ بـ`scripts/diagnose/mold-reps.cjs`.
- **الموافقة:** Claude لا يدفع طلب `deploy` إلا بعد موافقة المالك في المحادثة. الـjob يعمل في بيئة `production`؛ إضافة Required reviewers لها تجعل كل تشغيل ينتظر ضغطة Approve إن أراد المالك ذلك.
- **القراءة:** ناتج الاستضافة كاملًا في سجل الـjob وفي ملخص التشغيل، وأهم أسطره في annotation واحدة (`hosting said`)، والخطوات في annotations (`deploy`).
- **الحدود:** لا يُحذف شيء ولا يُسترجع: أي `STOP` من المُفعِّل يُنهي التشغيل بمخرجاته. لا يمس السكربت مجلدات حزم سابقة؛ مجلد الحزمة نفسها يُعاد استعماله إن كان بنفس `RELEASE-SHA256SUMS.txt` ويُرفض إن اختلف. يلزم أن يسمح الحساب بـcron (cPanel ← Cron Jobs)؛ إن لم يبدأ السطر خلال 6 دقائق يتوقف الـworkflow ويحذف الطلب والسطر.

## 9-ق. تعديل بيانات العميل يحتاج موافقة (2026-11-15)

**القاعدة:** مدير النظام ومدير المبيعات يعدّلان بيانات العميل مباشرة، ويبتّان في الطلبات. المندوب والمشرف وخدمة العملاء ومديرها يرسلون طلب تعديل: يمر الحفظ بكل فحوص التعديل المباشر باسم المرسل، ثم يُحفظ طلبًا ولا يتغير العميل. طلب المندوب الذي له مشرف نشط (من `supervisor_id` في حسابه، ودوره «مشرف») يصل إلى المشرف أولًا ثم إلى مدير المبيعات؛ وغيره يصل إلى مدير المبيعات مباشرة. المرحلة تُقرأ لحظيًا: إيقاف المشرف أو فك ربطه ينقل الطلب إلى مدير المبيعات دون أي مهمة مجدولة. الرفض يحتاج سببًا يقرؤه المرسل، والمرسل وحده يلغي طلبه في أي مرحلة. كود ERP والمسؤول والفرع لا تدخل الطلب أبدًا.

## 9-ر. الإجازة والانقطاع في التقييم (2026-11-15)

**القاعدة (GSCO 2.13.50 و2.13.51، طلب المالك «الإجازات تتحسب في التقييم: الأيام اللي المندوب كان فيها في إجازة ما تتحسبش ضده»):** لا يُسجَّل أي إجازة؛ تُقرأ من البيانات.

- **الشهر المشتغل:** شهر فيه للشخص نشاط (زيارة أو اتصال أو متابعة أو أي تواصل)، أو عميل أضافه يدويًا في التطبيق (بيوم سجله بتوقيت الرياض، لا ما أضافه ملف أو استيراد عملاء ERP)، أو مستند مبيعات مؤكد (بيع أو مرتجع، من الـCRM أو ERP). خط السير وحده لا يكفي.
- **«بلا نشاط في هذا الشهر – خارج التقييم»** (منذ 2026-11-14): للمندوب فقط، في شهر مغلق، مبيعاته مكتملة (رفع ERP كامل أو تأكيد «بيانات المؤشرات»)، بلا عمل فيه. لا درجة ولا نقاط، وآخر جدول المقارنة. المشرف ومدير المبيعات لا يُعلَّمان، والشهر الجاري لا يُعلَّم. **المندوب يرى العلامة في «أهدافي»** (نعم أو لا فقط).
- **«الحفاظ على العملاء الحاليين» و«العملاء المستردون»:** يُقارنان بآخر ثلاثة أشهر **اشتغلها** الشخص، حتى 12 شهرًا للخلف. الشهر المغطى بمبيعات كاملة بلا عمل يُتخطى ويظهر تحت «العملاء والسوق» في «أشهر بلا نشاط لم تُحتسب» وفي سبب المؤشر وفي «تصدير التقييم». الشهر غير المغطى يبقى نقص بيانات ويُسمّى؛ وإذا تجاوزت الإجازة الأشهر الثلاثة التي يؤكدها «بيانات المؤشرات» فلا يكملها إلا رفع ERP كامل.
- **المندوب الجديد (2.13.51):** الشهر المغطى قبل أول شهر اشتغله شهر عادي بلا مشتريات، فيُحسب «الحفاظ» من شهره الثاني، و«المستردون» «لا ينطبق» حتى يمر أربعة أشهر على أول شهر اشتغله. أقل من ثلاثة أشهر مشتغلة في الاثني عشر: المؤشران «لا ينطبق» بسببهما.
- **إجازة جزء من الشهر:** لا تخفيض للمستهدف (اختيار «أ» في GSCO). **مستهدف فريق المشرف** ما زال يجمع مستهدف مندوب في إجازة شهر كامل: قرار مؤجَّل للمالك كما في GSCO.

## 9-ش. إخفاء تبويبات صفحة المستهدفات لكل حساب (2026-11-16)

**القاعدة (البند السادس من قائمة GSCO، طلب المالك «إخفاء تبويبات صفحة المستهدفات لكل حساب لوحده (النتائج، التحصيل، العروض)، زي مفاتيح إخفاء الأقسام في GSCO»، كما في GSCO 2.13.58):** في «الفريق والصلاحيات» ← تعديل المستخدم ← «الصلاحيات»، تحت صف «المستهدفات وتقييم الأداء» أربعة صفوف: «تبويب «نتائج الأداء»» و«تبويب «التحصيل»» و«تبويب «عروض الأسعار»» و«تبويب «المستهدفات والأوزان»»، لكل منها خانة «استعراض» وحدها. إزالة العلامة تخفي التبويب عن هذا الحساب وحده.

- **لمن:** مدير المبيعات والمشرف فقط (الدوران اللذان صفحة المستهدفات عندهما صفحة تبويبات). مدير النظام لا يُخفى عنه شيء («—»). المندوب («أهدافي» بلا تبويبات) وخدمة العملاء (بلا صفحة مستهدفات) بلا صفوف.
- **«رفع المبيعات»** بلا مفتاح خاص: يتبع «استعراض» في «المبيعات» كما كان، وكما في GSCO.
- **إخفاء فقط:** لا يضيف المفتاح شيئًا للدور، ولا يُخفى شيء افتراضيًا، والحساب لا يتغير حتى يحفظ مدير النظام. «الكل» في صف الشاشة يشمل التبويبات، وإخفاء الشاشة نفسها يعطّل خانات تبويباتها (تُحفظ قيمها).
- **الصفحة:** التبويب المخفي لا يُرسم. إذا طلبه العنوان (`?tab=`) أو تذكّره المتصفح فُتح أول تبويب ظاهر وصُحّح العنوان. التقييم لا يُطلب إذا أُخفيت «نتائج الأداء» و«التحصيل» و«عروض الأسعار» معًا.
- **الخادم:** طلبات التبويب المخفي وحده ترد 404 «هذا الجزء غير متاح لحسابك. راجع مدير النظام.» (لا 401 ولا 403 حتى لا تُقفل جلسة العمل دون اتصال):
  - «نتائج الأداء»: `POST /api/kpis`.
  - «التحصيل»: `GET` و`POST /api/kpi-evidence/import`.
  - «عروض الأسعار»: `GET` و`POST /api/erp-quotes`.
  - «المستهدفات والأوزان»: `POST /api/targets` و`GET /api/targets/history`.
  - المشترك يبقى مفتوحًا ما دام أحد تبويباته ظاهرًا: `/api/kpi-evidence` يُغلق إذا أُخفيت تبويبات التقييم الثلاثة، و`GET /api/sales` يبقى 200 ويُرسل `kpis: null` عند إخفاء الثلاثة.
- **كل التبويبات مخفية:** تبقى الصفحة بتبويب «رفع المبيعات» ما دام ظاهرًا؛ وإلا تُخفى الصفحة كلها كأن «استعراض» فيها مغلق (لا تظهر في القوائم، والرابط القديم يفتح أول شاشة متاحة، وطلباتها 404 ومنها `/api/sales`).
- **النسخ والسجل:** «انسخ الصلاحيات من» ينسخ التبويبات المخفية للمشرف أو مدير المبيعات، ويذكر ما لم يُنسخ لغيرهما. كل حفظ قيد «صلاحيات» بقبل وبعد.

## 9-ت. تنبيه المصانع القريبة في تطبيق أندرويد 1.0.13 (2026-11-16)

**القاعدة (البند السابع من قائمة GSCO، طلب المالك «تنبيه بالمصانع القريبة اللي محتاجة زيارة، على طريقة تنبيه المشاريع القريبة المجمّع في GSCO (أندرويد 1.4.8)»، والموافقة «تمام كمل كل البنود وارفع لما الفحص يخلص»):** للمندوب وحده وفي تطبيق أندرويد وحده: إشعار واحد مجمّع عندما يكون الهاتف على بعد **كيلومتر** أو أقل من عملاء **مسؤول عنهم** المندوب، **لم تُسجَّل لهم زيارة منذ 60 يومًا أو أكثر**، و**لهم موقع محفوظ على الخريطة**. **المصنع نفسه لا يُنبَّه عنه أكثر من مرة في اليوم.**

- **من يدخل القائمة (الخادم، `GET /api/nearby-customers`):** عملاء المندوب المسند إليهم (`assigned_to`) في مناطقه، بموقع محفوظ تقرؤه «خريطة المصانع» (`customerCoordinates`)، وآخر زيارة لهم (سجل في «الزيارات» نوعه «زيارة»، **من أي عضو**، تحت العميل مباشرة أو تحت فرصته أو ماكينته) قبل 60 يومًا أو أكثر بتوقيت الرياض، أو لم يُزاروا قط. 60 يومًا بالضبط تدخل و59 لا. الاتصال والواتساب والبريد ليست زيارات. العميل المحذوف والزيارة المحذوفة في «المحذوفات» فلا يُقرآن. لا يوجد في يورست دمج عملاء.
- **ليست قاعدة «عملاء واقفين»:** تلك «لم يشترِ منذ 60 يومًا» (`lib/customer-last-purchase.ts`: المشتريات، والحالة «نشط»، و60 يومًا ما زالت حديثة). لم تكن في يورست قاعدة للزيارات، فهذه قاعدة جديدة بأرقام المالك المعتمدة.
- **ما يخرج للتطبيق:** المعرّف والاسم والإحداثيات وعدد الأيام منذ آخر زيارة (`null` لمن لم يُزر)، مع هوية الحساب ومناطقه، وصلاحية عشر دقائق (`expiresAt`) وإعادة الطلب كل خمس (`refreshAfterSeconds`). لا جوال ولا بريد ولا مسؤول ولا رقم ولا عنوان. الحد 2000 عميل؛ أكثر من ذلك يُرفض كاملًا (503 «تعذّر تحديث قائمة المصانع القريبة كاملة. حاول لاحقًا.») ولا يُقص.
- **الأبواب:** بلا جلسة 401؛ أي دور غير المندوب 403 «تنبيه المصانع القريبة متاح لحساب المندوب فقط.»؛ مندوب أُخفيت عنه «العملاء» 404 «هذا الجزء غير متاح لحسابك. راجع مدير النظام.»؛ حساب تغيّر بين فحص الجلسة والقراءة 403 «تغيّرت صلاحيات حسابك. سجّل الدخول من جديد.» (سطر «actor» في الاستعلام نفسه كما في GSCO)؛ `GET` فقط وبلا تخزين. قراءة فقط: لا ينشئ زيارة ولا مسارًا ولا سجلًا.
- **التطبيق (`NearbyRules` و`NearbyCustomers` و`NearbyApi`):** يعمل على قراءات الموقع التي يسجّلها تتبع المسار المستمر أصلًا (من 6 صباحًا إلى 6 مساءً بتوقيت الرياض، عدا الجمعة)، دون طلب GPS جديد ولا إذن جديد. القراءة بدقة 75 مترًا أو أفضل، وعمرها أقل من دقيقة، وليست من موقع وهمي. «قريب» = مسافة القراءة نفسها 1000 متر أو أقل (999 داخل و1001 خارج)، في قراءتين بينهما 15 ثانية على الأقل. كل العملاء المؤكدين في القراءة نفسها في إشعار واحد، الأقرب أولًا، وبين إشعارين 30 ثانية على الأقل. من نُبِّه عنه يُحفظ على الهاتف لكل حساب (المعرّفات واليوم فقط) قبل ظهور الإشعار، فلا يتكرر في اليوم نفسه ولو أُعيد تشغيل التطبيق، ويعود في يوم جديد.
- **القائمة على الهاتف:** تُطلب عند أول قراءة، وكل خمس دقائق ما دامت القراءات تصل، ومن جديد قبل الإشعار مباشرة إلا إذا وصلت في آخر دقيقة (فالعميل الذي زُير أو نُقل لمندوب آخر لا يُنبَّه عنه). الفشل يُعاد بعد دقيقة؛ 401 و403 و404 تُسقط القائمة وتزيل الإشعارات الظاهرة وتنتظر خمس دقائق. تسجيل الخروج أو تغيّر الحساب أو المنطقة يمسح القائمة والإشعارات؛ توقف الساعة 6 مساءً يُسقط القائمة ويُبقي من نُبِّه عنه اليوم.
- **الإشعار:** قناة «المصانع القريبة» (أهمية عادية، ويمكن كتمها من إعدادات أندرويد). العنوان «مصنع قريب منك بحاجة إلى زيارة» / «مصنعان قريبان منك…» / «3 مصانع قريبة منك…» / «11 مصنعًا قريبًا منك…»، وكل سطر «<الاسم> — على بعد 420 م · آخر زيارة قبل 75 يومًا» أو «لم تُسجَّل له زيارة». شاشة القفل تعرض «يورست: مصانع قريبة بحاجة إلى زيارة» فقط. بالإنجليزية إذا اختار المندوب الإنجليزية في صفحة CRM (يقرأ التطبيق اختيار الصفحة `yr-language` عند تحميل الصفحة وعند خروجه للخلفية). يختفي وحده بعد عشر دقائق أو عند 6 مساءً.
- **الضغط على الإشعار:** يفتح «خريطة المصانع» على أقرب عميل في الإشعار: التشغيل البارد يحمّل `#nearby=<id>`، والصفحة المفتوحة يصلها الحدث `yourrest:open-nearby-customer` (`app/crm-app.tsx`). نافذة مفتوحة لا تُستبدل (تظهر رسالة «اقتربت من مصنع بحاجة إلى زيارة…»). المعرّف تلميح فقط: يُفتح العميل إن كان في بيانات العضو؛ ومن أُخفيت عنه الخريطة تُفتح له بطاقة العميل.
- **الأذونات:** لا إذن جديد. يحتاج ما يملكه تتبع المسار المستمر أصلًا (الموقع الدقيق وطوال الوقت والإشعارات). الأجهزة المثبتة لا تمنح شيئًا جديدًا.

## 9-ث. مبيعات اليوم، وموعد إعادة التواصل، واستيراد المستهدفات والمتابعات من Excel (2026-11-16)

**الطلب (البند الثامن من قائمة GSCO):** «مبيعات اليوم قصاد مستهدف اليوم، وميعاد إعادة تواصل مع الفرصة الخسرانة، واستيراد المستهدفات والمتابعات من قوالب Excel».

- **موعد إعادة التواصل:** في نموذج المتابعة، عند «تم الفقد» فقط: «الإجراء عند إعادة التواصل» و«موعد إعادة التواصل» معًا أو لا شيء، ولا يسبق تاريخ المتابعة ولا يكون في الماضي. تُحفظ المتابعة مفقودة ومعها `recontact: true` والموعد والإجراء كخطوتها التالية، فيبقى خط متابعة العميل مفتوحًا «قادمة» ثم مستحقًا في يومه بشارة «إعادة تواصل». بدونه، وكل ما حُفظ قبل هذا الإصدار، يُغلق كما كان.
- **الاستيراد من Excel:** زر «استيراد المستهدفات من Excel» في «المستهدفات والأوزان» (لمن يعدّل المستهدفات) وزر «استيراد المتابعات من Excel» في صفحة المتابعات (لمن يسجّل متابعة). «تنزيل القالب» يعطي ملفًا معبأً بما يمكن للقارئ استيراده، ثم الرفع، ثم معاينة لا تحفظ شيئًا (حالة كل صف وسبب الرفض بصف Excel)، ثم «استيراد» مرة واحدة: الصفوف السليمة تُكتب في معاملة واحدة كلها أو لا شيء، مع سطر تدقيق للاستيراد وسطر «سجل التعديلات» لكل مستهدف و«تسجيل متابعة» لكل متابعة. إعادة الملف نفسه لا تغيّر شيئًا.

## 9-خ. مدير المبيعات خارج التقييم، وما يلزم لاكتمال التقييم (2026-11-16)

**الطلب (البند الثاني من قائمة GSCO، GSCO 2.13.76، وموافقة المالك «تمام موافق ابدأ»):** «مدير المبيعات يخرج من «مقارنة أداء المندوبين» ومن التقييم ومن مستهدفات النشاط، حتى لو له كود موظف أو تقييمات قديمة. التقييمات القديمة تفضل محفوظة.» «جنب «بيانات ناقصة» تظهر أسماء المؤشرات الناقصة وأوزانها.» «فوق الجدول مربع «المطلوب لاكتمال التقييم».» «في صفحة الموظف قايمة بكل مؤشر ناقص، والمطلوب عشان يتحسب.» «طريقة حساب الدرجة ما تتغيرش.»

- **مدير المبيعات (الدور `manager`) ليس شخصًا في التقييم** (`roleOutOfEvaluation` في `lib/targets.ts`): لا يظهر في «مقارنة أداء المناديب» ولا في «ملخص المناديب» ولا في تبويبي «التحصيل» و«عروض الأسعار» ولا في «تصدير التقييم» ولا في اختيار «المندوب» في التبويبات الثلاثة، عند أي قارئ (مدير النظام، ومدير المبيعات نفسه، والمشرف)، ولو رُبط به كود موظف في ERP أو كانت له مبيعات أو تقييمات محفوظة. يفتح الشاشة على فريقه كما كانت.
- **الخادم:** `GET /api/sales?kpis=1` لا يحسب له تقييمًا؛ `POST /api/kpis` له يرد 404 «حدد عضوًا متاحًا ضمن صلاحيتك للتقييم» كأي عضو خارج التقييم؛ `GET /api/kpi-evidence` له يرد 404 «عضو الفريق غير متاح ضمن صلاحيتك.».
- **مستهدفات العملاء والزيارات (مستهدفات النشاط):** لا صف له في جدول «مستهدفات العملاء والزيارات» ولا في «تصدير كل المستهدفات»، وبطاقته في «المستهدفات والأوزان» تقول «مدير المبيعات خارج التقييم ومستهدفات العملاء والزيارات.». حفظها له يُرفض 400 «مدير المبيعات خارج التقييم، فلا تُحدَّد له مستهدفات العملاء والزيارات.» (من الصفحة ومن استيراد Excel). **مستهدف أصنافه المحسوب من فريقه باقٍ** في «المستهدفات والأوزان» كما كان.
- **التقييمات القديمة محفوظة:** لا يُحذف ولا يُعدَّل شيء من `crm_kpi_assessments` ولا غيرها؛ فقط لا تُقرأ. الرجوع إلى الإصدار السابق يعيدها كما كانت.
- **ما يلزم لاكتمال التقييم** (`lib/kpi-gaps.ts`، يُقرأ مما يرسله الخادم أصلًا، فلا تتغير الدرجة ولا الوزن): المؤشر الناقص هو ما لا درجة له وليس «لا ينطبق» (منذ 2026-11-14 «لا ينطبق» يخرج من الوزن، فلا يُذكر هنا). مؤشرات السلوك الخمسة سطر واحد «تقييم السلوك من الإدارة (10%)» إذا نقصت كلها.
  - **بجانب «بيانات ناقصة»:** الأسماء بأوزانها في جدول المقارنة تحت الدرجة، وفي بطاقات «ملخص المناديب»، وفي «تصدير التقييم»: «بيانات ناقصة: تحقيق المستهدف البيعي (25%)، التحصيل (20%)…».
  - **فوق الجدول، مربع «المطلوب لاكتمال التقييم»:** سطر لكل إجراء: الإجراء ثم وزن المؤشرات التي يكملها، وتحته من يخصهم («كل المناديب (N)» إذا خص الجميع، وإلا أربعة أسماء و«+N»)، والأكبر وزنًا أولًا. من هو «بلا نشاط في هذا الشهر – خارج التقييم» لا يدخل فيه. لا يظهر إذا لم ينقص شيء.
  - **في صفحة الموظف:** قائمة «المؤشر (الوزن): المطلوب» تحت «المطلوب لاكتمال التقييم:».
- **الإجراءات (من وأين):** أوزان الأصناف (مدير النظام أو مدير المبيعات، زر «أوزان التقييم» في «المستهدفات والأوزان»)؛ مستهدف الأصناف («تعديل الأصناف»، وللمشرف مستهدفات كل مناديب فريقه)؛ مبيعات ERP الكاملة («استيراد مبيعات ERP» في «رفع المبيعات» مع «الملف يشمل كل مبيعات المناديب للفترة التي يغطيها») أو تأكيد اكتمال السجل في «بيانات المؤشرات»، وللحفاظ والاسترداد والنمو الأشهر المطلوب رفعها بأسمائها؛ التحصيل («استيراد كشف التحصيل من ERP» في «التحصيل» أو «بيانات المؤشرات»)؛ ملف عملاء ERP بعمود «التاريخ» («استيراد من ERP» في «العملاء») لعملاء الشهر بلا منشئ؛ تقييم المشرف للزيارات «فعالة» أو «سلبية» من «إضافة نتيجة وإجراء» في «تقرير يوم المندوب» مع عدد الزيارات المنتظرة؛ درجات السلوك (زر «تقييم الإدارة وتدقيق البيانات»)؛ ربط الفريق في «الفريق والصلاحيات» لمشرف بلا فريق. حالة غير معروفة تبقى بسبب المؤشر نفسه.

## 9-ذ. تقارير خدمة العملاء بنوع التواصل وتصديرها، وتنبيه «شكوى تنتظرك»، و«طلب مساندة» من الفرصة (2026-11-16)

**الطلب (البند الثالث من قائمة GSCO، عن GSCO 2.13.77 وأندرويد 1.4.9، وموافقة المالك «تمام موافق ابدأ»؛ النشر ينتظر «ارفع»):** أربعة أجزاء.

**أ. تقرير طلبات الخدمة «بحسب نوع التواصل».** كان تقرير يورست يجمع الطلبات بـ`data.source` («بحسب قناة التواصل»)، وهو نفسه «نوع التواصل» الذي تختاره خدمة العملاء عند تسجيل الفرصة (`registration.type`). صار العنوان «بحسب نوع التواصل»، والحقل في الإجابة `byContactType` (بدل `bySource`)، والطلب القديم بلا `source` يُحسب بنوع تسجيله، وما لا نوع له يظهر «غير محدد» بدل الكلمة الإنجليزية `unknown`. الدالة `serviceContactType` في `lib/service-report.ts`. لم يكن في يورست «سطر واحد» كما في GSCO؛ التغيير في التسمية وفي حساب الطلبات القديمة.

**ب. «تصدير Excel».** في يورست تقريران شهريان لا ثلاثة تبويبات: تقرير طلبات خدمة العملاء (في «الزيارات») وتقرير الشكاوى (في «الشكاوى»، ولمدير المبيعات في «الزيارات»). لا تقرير شهري لطلبات المساندة في يورست، فلا تبويب ثالث يُصدَّر. بجانب الشهر في كل تقرير زر «تصدير Excel» يطلب `GET /api/service-report/export?kind=requests|complaints&month=YYYY-MM&lang=ar|en` فيبني الخادم ملفًا بثلاث أوراق: «الملخص» (بطاقات الشاشة وكل جدول فيها وملاحظتها)، و«زمن المراحل» (جدول الشاشة)، و«التفاصيل» (سطر لكل طلب أو شكوى: الرقم والعميل والمدينة والمنطقة والنوع أو التصنيف والوسيلة والأهمية ومن سجّل والمسؤول الحالي والحالة ووقت كل مرحلة بتوقيت الرياض و«متأخر» لكل مرحلة والنتيجة وسبب الفقد أو نتيجة الحل والإغلاق وتقييم العميل). الأرقام خلايا أرقام والنصوص نصوص لا تُقرأ معادلات، والملف من اليمين لليسار بالعربي. القراءة بنطاق التقرير نفسه (`canReadService` و`canReadComplaint`): كل قارئ يصدّر ما يقرؤه فقط، ولا يخرج نص التسجيل ولا وصف الشكوى ولا الملاحظات. تعريف البطاقات والمراحل في `lib/service-report-view.ts` مرة واحدة تقرؤها الشاشة والملف، والكاتب `xlsxBook` في `lib/xlsx-write.ts` (أوراق متعددة وخلايا أرقام؛ `xlsxWorkbook` كما كان).
- **الأبواب بالترتيب:** بلا جلسة 401؛ نوع غير معروف أو شهر غير صالح 400؛ دور ليس التقرير له 403 بعبارة التقرير؛ الشاشة التي تعرض التقرير مخفية 404 (الطلبات «الزيارات»، والشكاوى «الشكاوى» لمن له الصفحة وإلا «الزيارات»)؛ خانة «تقارير خدمة العملاء · تصدير» مغلقة 403 «غير مسموح لك بالتصدير في تقارير خدمة العملاء. راجع مدير النظام.».
- **الخانة الجديدة في «الصلاحيات»:** صف «تقارير خدمة العملاء» فيه «تصدير» وحده (لا «استعراض» له لأنه جزء من «الزيارات» و«الشكاوى»، ويقول الصف ذلك). سقفها الأدوار التي يُفتح لها التقريران: مدير النظام ومدير المبيعات ومدير خدمة العملاء، مفتوحة افتراضيًا لهم، تقييدية كبقية الخانات، وغير ثابتة: يغلقها مدير النظام لأي حساب، ومنها حساب مدير نظام آخر. الحسابات المحفوظة قبل الإصدار لم تُكتب فيها الخانة فتبقى مفتوحة؛ لا ترحيل.

**ج. «شكوى تنتظرك» على الهاتف.** `GET /api/complaints/alerts` (`lib/complaint-alerts.ts`) يعيد للعضو الشكاوى التي تنتظره هو من قائمة صفحة الشكاوى نفسها (`complaintAwaiting`): المراجعة لمدير خدمة العملاء، والتعديل والإغلاق لمن سجّلها، والتكليف لمدير المبيعات، والتفويض للمشرف، والتواصل والحل للمكلَّف؛ ولمدير النظام حين لا يوجد غيره. عشرون بحد أقصى، الأهمية العالية أولًا ثم ترتيب الصفحة، ولكل سطر: المعرّف واسم العميل والتصنيف بالعربي والإنجليزي والأهمية والخطوة وهل فتحها المكلَّف ومتى بدأت الخطوة. لا وصف ولا طلب ولا جوال ولا مدينة ولا رقم. الأبواب: بلا جلسة 401؛ شاشة الشكاوى مخفية 404 («الشكاوى» لمن له الصفحة، و«الزيارات» لفريق المبيعات)؛ غير ذلك 200.
- **التطبيق 1.0.14 (15):** `ComplaintAlertRules` (قواعد نقية) و`ComplaintAlertFeed` (قراءة صارمة) و`ComplaintAlerts` و`ComplaintAlertApi`. إشعار لكل شكوى في قناة «شكاوى العملاء» بعنوان «شكوى تنتظرك» ونص «أهمية عالية · العميل · التصنيف — بانتظار تكليفك» (البادئة للأهمية العالية وحدها)، مجمّعة والعالية أولًا، وملخص «عدد الشكاوى التي تنتظرك: N» إذا ظهر اثنان أو أكثر؛ شاشة القفل «يورست: شكوى تنتظرك» فقط؛ بالإنجليزية إن اختارها العضو في الصفحة. تتجدد الشكوى إذا بدأت خطوتها من جديد، وتختفي إذا فتحها المكلَّف أو لم تعد تنتظره، ولا تتكرر الخطوة نفسها. الضغط يفتح الشكوى: التشغيل البارد `#complaint=<id>`، والصفحة المفتوحة يصلها `yourrest:open-complaint`.
- **الفحص في الخلفية:** `AlertCheckJob` مهمة JobScheduler دورية كل 15 دقيقة، محفوظة بعد إعادة التشغيل، بشرط شبكة، تسأل خلاصة الشكاوى وخلاصة طلبات خدمة العملاء داخل نافذة 06:00 إلى 18:00 بتوقيت الرياض فقط وليس الجمعة (`ContinuousPolicy.inWindow`)، **ولو كان تسجيل خط السير متوقفًا**. لا GPS ولا خدمة ولا إذن؛ تلغي نفسها إذا لم يكن في الهاتف جلسة، وتُلغى عند تسجيل الخروج، وتُجدول عند فتح التطبيق وعند تحميل صفحة CRM بجلسة. كل خلاصة تحافظ على إيقاعها كل عشر دقائق.
- **الأذونات:** لا إذن جديد؛ المهمة المحفوظة تستعمل `RECEIVE_BOOT_COMPLETED` وشرط الشبكة `ACCESS_NETWORK_STATE`، وكلاهما موجود. الأجهزة المثبتة لا تمنح شيئًا. **الإصدار إلزامي:** أقل نسخة مسموحة = 1.0.14 (القسم 9-ح) بعد نشرها من GitHub. انشر تحديث الموقع قبل التطبيق أو معه: تطبيق 1.0.14 على موقع قديم يتلقى 404 من المسار فلا ينبّه بشيء ولا يتعطل شيء.

**د. «طلب مساندة» من داخل الفرصة.** الفرصة في يورست هي طلب خدمة العملاء (`crm_service_cases`) كما يحمله فريق المبيعات، وتُفتح في ورقة «الاعتماد والتكليف» (`app/customer-service.tsx`)؛ و«التواصل مع العملاء» هو مسار المساندة نفسه (`lib/support.ts`) بمدده (4 ساعات للتولي ثم مراحل المراجعة والتكليف والتفويض والتواصل والإغلاق) وتصعيده لمن فوق المتأخر.
- **الزر:** «طلب مساندة» في الورقة لمدير النظام وفريق المبيعات على كل فرصة مفتوحة يقرؤها العضو (للمندوب: كل فرصه المفتوحة). يسأل أولًا `GET /api/support/opportunity?id=<الفرصة>` (`lib/support-opportunity.ts`): بلا جلسة 401؛ خدمة العملاء 403 (هي المطلوب منها)؛ «الزيارات» مخفية 404؛ فرصة لا يقرؤها 404؛ وإلا الفرصة ورقم طلبها وهل هي مفتوحة، وعميلها، وطلب المساندة المفتوح للعميل إن وجد. فرصة مغلقة: «طلب المساندة متاح للفرص المفتوحة فقط.»؛ عميل غير موجود في قائمة العملاء: رسالة توضح ذلك وكيف يُصحَّح (في يورست لا يُحذف عميل له طلب خدمة، فهذا لا يحدث إلا مع بيانات تالفة)؛ طلب مفتوح للعميل: رسالة وزر «فتح الطلب المفتوح». وإلا نموذج «سبب المساندة» و«وسيلة التواصل المفضلة» يرسل `POST /api/support` بـ`opportunityId`: يُفتح الطلب في «التواصل مع العملاء» والفرصة محفوظة عليه (`data.opportunity`: المعرّف ورقم الطلب والأصناف) وتظهر في بطاقته وورقته («من الفرصة رقم N»)، ويُرفض الطلب الثاني والفرصة المغلقة وعميل غير عميل الفرصة، ويُعاد فحص الفرصة عند الحفظ.
- **«طلب مساعدة داخلية» القديم:** هو المساندة القديمة داخل الفرصة في يورست. لا يقبل طلبات جديدة (409 بعبارة تقول أين يُفتح الطلب الجديد)، ويختفي زره؛ المفتوح منه يُكمل بـ«الرد وإغلاق طلب المساعدة»، والسابق يبقى في سجل الطلب، وتبقى «إضافة ملاحظة داخلية» وفلتر «طلبات المساعدة». تنبيه للمالك: كانت خدمة العملاء تستعمله لطلب مساعدة المبيعات، ولم يعد لها إلا الملاحظة الداخلية.

## 9-ض. مشاركة خدمة العملاء في العملية البيعية: مصدر الفرصة، والاعتماد والإحالة، وتسجيل الدور، وأداء خدمة العملاء (2026-11-16)

**الطلب (البند الخامس من قائمة GSCO، عن GSCO 2.13.78 وترحيله 0049، وموافقة المالك «تمام موافق ابدأ»؛ النشر ينتظر «ارفع»).** الفرصة التي تسجّلها خدمة العملاء في يورست هي طلب خدمة العملاء (`crm_service_cases`، «فرصة» في شاشات الخدمة)، وعرض السعر هو عرض ERP المستورد على العميل (`lib/erp-quotes.ts`) الذي تذكره فاتورة ERP في «الوصف» (`lib/quotation-refs.ts`). القواعد في `lib/service-sales.ts` (نقية)، والخادم في `lib/service-sales-server.ts`، والشاشات في `app/service-sales.tsx`.

**أ. «مصدر الفرصة».** نموذج «فرصة جديدة» لخدمة العملاء يطلب المصدر (إجباري): «من جهد خدمة العملاء» (اتصال وارد، واتساب، الموقع الإلكتروني، مواقع التواصل الاجتماعي، توصية من عميل، اتصال تسويقي، معرض أو فعالية، أخرى مع نص من 3 أحرف). لا يُسأل المصدر مع تواصل إضافي على فرصة العميل المفتوحة (يبقى مصدرها). ويملأ النظام المصدر ويقفله «من بيانات النظام» عند البدء من سجل: «بدء فرصة جديدة من هذه الفرصة» (فرصة مفقودة: «فرصة مفقودة سابقة»)، و«فرصة جديدة من هذا الطلب» (طلب في «التواصل مع العملاء»: «طلب تواصل مع العملاء»، أو زيارة مفقودة: «زيارة مفقودة»)، و«فرصة جديدة من هذه الشكوى» («شكوى»)، و«بدء فرصة جديدة لهذا العميل» (عميل منقطع 90 يومًا). الخادم يعيد قراءة السجل (يقرؤه العضو، من نوعه، لعميل الفرصة نفسه، ولم تبدأ منه فرصة)، والسجل لا يبدأ إلا فرصة جديدة (لا تواصلًا على فرصة مفتوحة: 409). الفرصة المفقودة والطلب والشكوى تبدأ كلٌّ منها فرصة واحدة؛ أما العميل المنقطع فيُبدأ له من جديد بعد إغلاق الفرصة التي بدأت منه (ويعود إلى القائمة)، ولا يُبدأ ما دامت للعميل فرصة مفتوحة. صفحة قديمة أو حفظ قديم على الجهاز بلا الحقل يبقى «غير محدد»، وكذلك كل الفرص المسجلة قبل الإصدار. قسم «مصادر الفرص» في «الفرص» (لخدمة العملاء، ولمدير النظام للقراءة) فيه «فرص مفقودة للاسترداد» (المفقودة التي لم تبدأ منها فرصة، ولا فرصة مفتوحة لعميلها، الأحدث أولًا، بالعميل وسبب الفقد؛ واسما من تولاها ومن سجّلها لمن يقرأ الفرصة نفسها فقط، `canReadService`، ولا يُبحث بهما عند غيره) و«عملاء منقطعون عن الشراء 90 يومًا» (آخر شراء من ERP أو فاتورة يدوية أقدم من 90 يومًا، بلا فرصة مفتوحة، الأقرب انقطاعًا أولًا)، كلٌّ بحدود فرع العضو ومناطقه، حتى 300 سطر مع بحث.

**ب. «اعتماد وإحالة».** في ورقة «الاعتماد والتكليف» يختار مدير خدمة العملاء (أو مدير النظام) «تمرير لمدير المبيعات» (كما كان) أو «تتولاها خدمة العملاء»، والثانية متاحة فقط إذا كان العميل غير مسجّل في ERP (بلا كود ERP؛ لا تضيف خدمة العملاء عملاء في يورست، فهذا مقابل «العميل غير مسجل» في GSCO)، أو لم يشترِ خلال 90 يومًا أو لم يشترِ من قبل، أو كان المصدر من جهد خدمة العملاء؛ تُعرض الأسباب، وتنبيه «تنبيه: للعميل فرصة مفتوحة لدى المبيعات» إذا كانت آخر زيارة أو متابعة لعضو مبيعات للعميل في مرحلة مفتوحة أو له طلب قالب مفتوح. المسؤول من خدمة العملاء: مسجّل الفرصة أولًا، ثم المدير نفسه وفريقه (ولمدير النظام أي ممثل في فرع العميل ومنطقته). الفرصة التي تتولاها خدمة العملاء حالتها «لدى خدمة العملاء» (`status='service'`)، ولا يتغير مسؤول العميل في المبيعات؛ يعمل عليها مسؤولها وحده (ومدير النظام): «تسجيل تواصل» و«مرحلة البيع» حتى «تم الفوز» أو «تم الفقد» بسبب الفقد (`action:'stage'`)، ويقرأ التقرير الشهري لطلبات خدمة العملاء وملف Excel سبب الفقد من مرحلتها (`serviceLossReason` في `lib/customer-service.ts`). أعضاء المبيعات لا يقرؤونها ولا يكتبون عليها، وزيارة المندوب لعميلها لا تُربط بها.

**ج. «تسجيل دور خدمة العملاء».** عند كسب أو خسارة فرصة شاركت فيها خدمة العملاء بعد تطبيق الترحيل تظهر مهمة في أعلى «الفرص» لمسؤولها من خدمة العملاء، وإلا لمسجّلها، وإلا لمن تولى طلب مساندة منها: يختار الدور (جلب العميل، التواصل والمتابعة، عرض السعر والتفاوض، استرداد عميل منقطع، حل شكوى، أخرى) ويكتب ملاحظة من 10 أحرف، مرة واحدة. المستهدف 24 ساعة عمل؛ بعدها «متأخر». مدير خدمة العملاء يرى مهام فريقه، ومدير النظام الكل في مناطقه. ولا تظهر مهمة ولا تُسجَّل إلا على فرصة يقرؤها القارئ (`canReadService`: المنطقة، والفرع لغير مدير النظام)، أو مهمة العضو نفسه على عميل في فرعه ومناطقه (من تولى طلب المساندة). المهام المنتظرة تُحسب من الفرص، ولا يُخزَّن إلا ما سُجّل.

**د. مبيعات خدمة العملاء.** كل فاتورة مرة واحدة في أعلى فئة. الفاتورة تبيع عرض السعر الذي تذكره في «الوصف» إذا كان تاريخها لا يسبق تاريخه، وكانت لعميله حين يدل كودها على عميل واحد (كما في «تحويل عروض الأسعار»). «مبيعات بالكامل»: عرض لعميل فرصة تتولاها خدمة العملاء، مؤرَّخ من يوم قرار «تتولاها خدمة العملاء» (`routed_at`) حتى إغلاقها، وفاتورة مؤرَّخة من ذلك اليوم واستلمها النظام بعد القرار (`created_at` لصف ERP)؛ فالقرار لا يعيد تصنيف عرض أو فاتورة قبله ولا مستندًا كان عند النظام، ولا يتغير شهر منتهٍ ولا ما أكّدته «بيانات المؤشرات» (لا يلزم رفع مراجعة المبيعات). «مبيعات بالمشاركة»: عرض لفرصة سجّلتها خدمة العملاء في أي وقت آخر كانت مفتوحة فيه (مُمرّرة للمبيعات، أو قبل القرار). «مبيعات بالمساندة» (فاتورة للعميل خلال 60 يومًا من تواصل خدمة العملاء معه في «التواصل مع العملاء» بنتيجة «مهتم» أو «يطلب زيارة»؛ المدة إعداد «مدة احتساب مبيعات المساندة (أيام)» في إعدادات «تقييم خدمة العملاء»). المرتجع في فئة عرضه بالسالب. ومرتجع ERP لا يذكر رقم العرض: مرتجع بلا عرض لعميل له مبيعات بالكامل (كودُه يدل عليه وحده)، مؤرَّخ في يوم إحداها أو بعده، يتبعها («بالكامل») كاملًا ما دامت مبيعاته بالكامل حتى يومه (بعد المرتجعات التي تبعتها) تغطيه، وما زاد يبقى حيث كان؛ فلا يُحمَّل المندوب مرتجع بيع لم يُحسب له، ولا ينزل أحد عمّا حُسب له. **المبيعات بالكامل منفصلة تمامًا:** تخرج من قائمة المبيعات التي يقرؤها كل تحقيق (`readErpSales` و`readOwnErpSales`)، فلا تدخل في تحقيق مستهدف الموظف ولا الفريق ولا الفرع ولا الشركة («تحقيق المستهدف»، «مبيعات اليوم»، «مستهدفاتي»)، ولا في التقييم (المبيعات، تحويل عروض الأسعار، العملاء، سجل الشراء، فواتير «بيانات المؤشرات»). «رفع المبيعات» يبقى بإجمالي ERP، وتحته سطر «منها مبيعات خدمة العملاء بالكامل» بالقيمة وعدد الفواتير، وتظهر فواتيرها في السجل بعلامة «خدمة العملاء بالكامل» (`serviceFullSales` في `GET /api/sales`).

**هـ. «أداء خدمة العملاء»** (قسم في «الفرص» ولمدير المبيعات في «الزيارات»): لكل عضو في الشهر الفرص المسجلة ومصادرها، وما مُرّر وما تولته الخدمة وما ينتظر القرار، وما تحول إلى عرض سعر وفاتورة وقيمتهما، والمبيعات بالكامل وبالمشاركة وبالمساندة، والعملاء الذين عادوا للشراء، ومتوسط الأيام من الفرصة إلى الفاتورة، والأدوار المسجلة والمنتظرة والمتأخرة، مع سطر الفريق. بلا مستهدف (قرار المالك). «تصدير Excel»: «الملخص» و«الفواتير» و«الفرص». يراه مدير النظام ومدير المبيعات (أرقام كل الفرق) ومدير خدمة العملاء (فريقه) والممثل (نفسه)؛ التصدير لخانة «تقارير خدمة العملاء · تصدير». اسم العميل ومن يتولاها ونص مصدرها في قائمة الفرص وملف Excel لمن يقرأ الفرصة نفسها فقط (`canReadService`: مناطقه، والفرع لغير مدير النظام، ولا أعضاء المبيعات على فرصة تتولاها خدمة العملاء)، وغيرها «غير متاح لك»؛ والأرقام لا تتغير بالقارئ.

**و. تقييم خدمة العملاء:** مؤشر جديد «نسبة الفرص المتحولة إلى مبيعات» للممثل، وزن 15، ويحتاج 3 حالات على الأقل، ومستهدف 50%: الفرص التي أُغلقت في الشهر (مسؤولها من الخدمة وإلا مسجّلها)، والمتحولة ما فازت أو ارتبطت بها فاتورة. الأوزان الأخرى 13 و13 و13 و13 و9 و8 و8 و8. الإعدادات المحفوظة بالأوزان القديمة الافتراضية تأخذ الجديدة، والتي غيّرها مدير النظام تُضبط نسبيًا إلى 85 (أعداد صحيحة)، وشهادات الأشهر المقفلة تبقى كما هي (المؤشر الجديد بوزن 0).

**الطلب.** أرسل المالك صورة شريط الفلاتر في قائمة الأوامر بتطبيق المنتجات وكتب: «ضيف الفلاتر دى فى طلبات القوالب ماعدا المصدر لان المصدر عندك واحد». فوق قائمة «كل الطلبات» لوحة فيها «الحالة» و«واقف عند» و«المندوب» و«من تاريخ» و«إلى تاريخ» و«بحث» عريض، دون «المصدر» (الـCRM هو المصدر الوحيد). التصفية كلها في المتصفح على القائمة المحمّلة؛ لا تغيير في الخادم ولا ترحيل ولا تغيير في تطبيق أندرويد.

**ما يفعله كل فلتر** (القواعد في `lib/mold-filters.ts`، وكلمات الخيارات هي كلمات البطاقة نفسها، ونُقلت كلمات البطاقة إلى هذا الملف ليقرأ منها الاثنان):

| الفلتر | الخيارات (يظهر منها ما في القائمة فقط، بهذا الترتيب، ويبقى المختار ظاهرًا ولو خلت القائمة منه بعد التحديث) | المعنى |
|---|---|---|
| «الحالة» (كل الحالات) | المفتوحة (لم تُسلَّم)، لم يصل للإنتاج بعد، بانتظار ملف عرض السعر / الـ PO، بانتظار ملف التصميم، بانتظار توقيع العميل، بانتظار تحديث تطبيق الإنتاج (عميل بلا كود يورست)، بانتظار الإرسال، رفض الإنتاج البيانات، بانتظار تحديث تطبيق المنتجات، الربط مع الإنتاج غير مفعَّل، أعادتها المالية، استلمه الإنتاج، اكتملت الاعتمادات، قيد التصنيع، تم التصنيع، تم التسليم للعميل، أُلغي في تطبيق الإنتاج، ملغى | ما تقوله البطاقة: شارة الحالة، والسطر الصغير ما دام الطلب محفوظًا في الـCRM، وشارة «أعادتها المالية»، وحالة الإنتاج. قد يطابق الطلب أكثر من خيار (طلب لدى الإنتاج وتعديله ينتظر الإرسال). «المفتوحة» كما في تطبيق المنتجات: لا مُسلَّم ولا ملغى |
| «واقف عند» (كل المراحل) | بانتظار اعتمادك، بانتظار اعتماد مدير المبيعات، بانتظار اعتماد الإنتاج، بانتظار اعتماد المالية، في التصنيع، في التصنيع · Laser Cutting ... · Paint (المرحلة السبع)، بانتظار التسليم | الخطوة التي ينتظر عندها الطلب كما يرسلها الإنتاج (`waitingStep`)، ومرحلة التصنيع التي وصل إليها (أول المراحل السبع غير المنتهية، كما تعلّمها ورقة الطلب)، و«بانتظار اعتمادك» لمدير المبيعات فيما يعتمده. المُسلَّم والملغى حالات لا خطوات، والطلب غير الواصل للإنتاج لا خطوة له |
| «المندوب» (كل المندوبين) | مقدّمو الطلبات في القائمة، كلٌّ مرة باسمه | صاحب الطلب (`memberId`). يظهر فقط إن كان في القائمة أكثر من مقدّم طلب؛ المندوب يرى طلباته وحده فلا يظهر له |
| «من تاريخ» / «إلى تاريخ» | تاريخان | يوم الطلب (`requestedAt`) بتوقيت الرياض، واليومان داخلان، والمدى المكتوب بالعكس يُقلب (والخانتان تبقيان كما كُتبتا)، وأحدهما وحده يكفي |
| «بحث» (عميل، مندوب، وصف، سريال، رقم أمر...) | نص | كل كلمة في أحد: اسم العميل، كود ERP، كود يورست (YR-C-…)، مقدّم الطلب، الوصف، رقم القالب، السريال، رقم أمر الإنتاج؛ بمطبّع بحث العملاء (`normalizeMapSearch`: صور الألف والياء والتشكيل والأرقام العربية والفارسية) |

الفلاتر تجتمع (و)، ومعها زر «أعادتها المالية» كما كان (نصه «أعادتها المالية 1» كما هو). تحت اللوحة «يظهر n من m» و«مسح الفلاتر» متى ضُبط فلتر واحد، ويمسح كل شيء ومنه «أعادتها المالية». «لا نتائج» كما كانت. تبويب «طلبات بانتظار اعتمادي» لم يتغير، والفلاتر لقائمة «كل الطلبات» وحدها.

**الشكل.** الحقول الخمسة في صف واحد على الكمبيوتر بعرض متساوٍ، والبحث بعرض اللوحة تحتها؛ على هاتف 320 و360 حقلان في الصف (والتاريخان متجاوران دائمًا)؛ على التابلت بالوضعين صف ثم البحث. ومعها إصلاحان صغيران في الصفحة نفسها: اسم العميل في البطاقة كان يُعصر حرفًا في السطر بجانب شارة طويلة على 320 (الشارة تنزل الآن تحت الاسم)، وعنوان الصفحة «طلبات تصنيع القوالب» كان يبقى عربيًا في الإنجليزية (أُضيف مفتاحه «Mold requests» إلى `lib/locales/en.json`؛ إضافة مفتاح فقط).

| الملف | الدور |
|---|---|
| `lib/mold-filters.ts` | كلمات البطاقة، ومفاتيح «الحالة» و«واقف عند» لكل طلب وكلماتها، والأيام، والبحث، والتصفية، وما تعرضه اللوحة |
| `app/mold-requests.tsx` و`app/mold-requests.css` | `MoldFilterPanel`، والبطاقة تقرأ شارتها وسطرها من الملف أعلاه |
| `lib/locales/en.json` | «طلبات تصنيع القوالب» = «Mold requests» |

**الاختبارات:** `tests/mold-filters.mjs` (البوابة الافتراضية: 169 فحصًا بلا بناء)، و`tests/mold-filters-browser.mjs` (بوابة المتصفح على النسخة المبنية بثمانية طلبات مصطنعة: الكمبيوتر بالعربية والإنجليزية، ثم 320 و360 والتابلت بالوضعين والكمبيوتر بكل لغة، والمندوب على 360؛ فحص الاسم المعصور فشل قبل إصلاحه). أُضيفا إلى منطقة `mold-requests` في `tests/test-areas.json` (ومعهما `lib/customer-map-search.ts` و`lib/daily-target.ts` اللذان تقرؤهما الفلاتر) وإلى `tests/check-manifest.json` و`tests/CHECKS.md`.


## 9-أأ. مسؤول التسويق وتصنيفات العميل (2026-11-18)

بعد 9-غ، آخر حروف الترتيب الأبجدي، تبدأ أقسام هذا الفصل دورة ثانية: 9-أأ ثم 9-أب ثم 9-أج وهكذا.

**الطلب.** كتب المالك: «فيه وظيفة جديدة مسؤول تسويق، الموظف مهمته الاساسية تحديث بيانات العملاء، بيضيف التصنيفات دى ... بالاضافة بيشتغل زى المندوب»، ثم وافق على المقترح: «تمام دوس».

**الدور.** مفتاحه `marketing` في `crm_members.role` («مسؤول تسويق» / Marketing officer). لا ترحيل: العمود نص بلا قيد CHECK، والدور يُضاف من «الفريق والصلاحيات» ويُختار له مشرف كالمندوب. مسؤول التسويق مندوب في كل شيء: الصفحات نفسها (العملاء والخريطة والزيارات والمتابعات وطلبات القوالب و«أهدافي» و«المحذوفات» مع «حذف»)، وفريق المشرف ومدير المبيعات، وإلزام التتبع وتطبيق أندرويد، ومستهدفاته وتقييمه وربطه في استيراد مبيعات ERP وعروضه وتحصيله، وطلبات القوالب بتوقيع العميل، وقائمة المندوبين المرسلة لتطبيق المنتجات، والمساندة والشكاوى وطلبات خدمة العملاء، وقاعدة مكان الزيارة. القواعد كلها تقرأ `isFieldRole` و`FIELD_ROLES_SQL` من `lib/roles.ts`، فلا يُكتب `'rep'` وحده في قاعدة جديدة (يمنعه حارس `tests/marketing-role.mjs`).

**الفرق الوحيد.** يعدّل بيانات **كل** عملاء فرعه في مناطقه مباشرةً، دون طلب الموافقة الذي ينتظر فيه تعديل المندوب (9-ق)، ويُسجَّل التعديل في سجل العميل باسمه ووقته كأي تعديل. لا يعدّل عميل فرع آخر («يعدّل مسؤول التسويق بيانات عملاء فرعه فقط.») ولا عميلًا خارج مناطقه، ولا يغيّر المندوب المسؤول ولا الفرع، ولا يحذف عميلًا أبدًا: خلية «حذف عميل» غير موجودة لدوره ولا تُحفظ له ولو أُرسلت، والخادم يرفضه أيضًا. ماكينات العميل لعملائه هو فقط كالمندوب.

**التصنيفات الثلاثة** (في بيانات العميل JSON، بلا ترحيل؛ «تصنيف العميل» `customerType` كما هو):

| الحقل | القيم | ملاحظة |
|---|---|---|
| «تصنيف الفرصة» `opportunityGrade` | A مرتفعة، B متوسطة، C ضعيفة، D مستبعدة | مع وصف كل قيمة كما أرسله المالك |
| «ملاحظات التصنيف» `gradeNotes` | نص حتى 1000 حرف | بالإملاء الصوتي |
| «حجم المصنع» `factorySize` | A كبير، B متوسط، C صغير، D متوقف | يقترح النظام A (5 ماكينات أو أكثر) وB (3 إلى 4) وC (1 إلى 2) من عدد ماكينات العميل المسجلة؛ القيمة المحفوظة تغلب دائمًا؛ «متوقف» يدويًا فقط؛ «اعتماد المقترح» يحفظ المقترح |
| «اهتمام العميل» `customerInterest` | `technical` فني، `price` سعري، `service` خدمي، `trust` الثقة | اختيار واحد |

عدد الماكينات المسجلة: مجموع «العدد» في سجلات الماكينات تحت العميل؛ ماكينة بلا عدد تُحسب واحدة، ومجموعة من الشيت بلا عدد لا تُحسب. جدول المالك قال «أكثر من 5» لكبير، وحُسبت الخمسة كبيرًا وسُئل المالك ليؤكد (`suggestedFactorySize` في `lib/customer-classification.ts`).

**من يحدد التصنيفات** (`canClassifyCustomer` في `lib/access.ts`، ويفرضها `POST /api/crm`): مسؤول التسويق لعملاء فرعه، والمشرف لعملاء فريقه (يمر تغييره في طلب تعديله إلى مدير المبيعات كأي تعديل له)، ومدير المبيعات ومدير النظام مباشرة، كلٌّ في مناطقه. المندوب يراها على عملائه هو فقط للقراءة (لا يرسل الخادم تصنيفات عملاء غيره)، وخدمة العملاء للقراءة؛ وأي حفظ منهما يغيّرها يُرفض («تصنيفات العميل يحددها مسؤول التسويق ...»)، فلا يحملها طلب تعديل المندوب. الحفظ الذي لا يحمل الحقول (صفحة قديمة) يبقيها، والقيمة المجهولة تُرفض برسالتها.

**في «العملاء».** النموذج («تصنيفات التسويق» بعد «تصنيف العميل» وما معه)، وصفحة العميل، وعلامات صغيرة في صف العميل وبطاقته، وفلتر لكل تصنيف (حجم المصنع بالقيمة التي يظهر بها: المحفوظة وإلا المقترحة)، وأربعة أعمدة في تصدير العملاء (CSV). استيراد العملاء من ERP لم يتغير: ملف ERP لا يحمل هذه الأعمدة.

**تطبيق أندرويد.** التطبيق المثبت (1.0.14) يعرف العضو الميداني بالدور `rep` فقط، فيرسل الخادم لمسؤول التسويق `memberRole: "rep"` في `/api/mobile-route` و`/api/nearby-customers` (`trackingRole`)، وتقارنه الصفحة بالقيمة نفسها؛ لا حاجة لنسخة جديدة من التطبيق. حساب يتحول من مندوب إلى مسؤول تسويق يُعاد دخوله كأي تغيير دور (يتغير `auth_version`).

| الملف | الدور |
|---|---|
| `lib/roles.ts` | `MARKETING_ROLE` و`isFieldRole` و`isMarketingRole` و`FIELD_ROLES_SQL` و`trackingRole` |
| `lib/customer-classification.ts` | القوائم وكلماتها، الحقول في المخطط، الاقتراح، الحفظ والتغيير، الفلاتر |
| `lib/access.ts`، `lib/crm-server.ts`، `app/api/crm/route.ts` | من يعدّل ومن يصنّف، وحارس الفرع عند الحفظ، ورفض الحذف، وفحص التصنيفات |
| `lib/crm.ts` | اسم الدور، والحقول في مخطط العميل، وما يُرسل لكل قارئ (`_classificationReadOnly`) |
| `lib/permissions.ts` | الدور في جدول الصلاحيات (خلايا المندوب عدا «حذف عميل») ومذكرة «تحرير» العملاء |
| `app/customer-classification-fields.tsx` و`.css` | الحقول والملخص والعلامات |
| `app/crm-app.tsx` | النموذج والفلاتر والتصدير وصفحة العميل، وكل موضع للمندوب |

**الاختبارات:** `tests/marketing-role.mjs` و`tests/customer-classification.mjs` (البوابة الافتراضية)، و`tests/marketing-role-http.mjs` (بعد البناء)، و`tests/marketing-role-browser.mjs` (المتصفح: 320 و360 والتابلت بالوضعين والكمبيوتر، بالعربية والإنجليزية). لا ترحيل: الترحيلات 22 كما هي، والرجوع إلى الإصدار السابق يترك الحقول في بيانات العملاء دون قراءة، ويعامل الإصدار السابق عضوًا بدور `marketing` كدور غير معروف (لا صفحات)، فيُغيَّر دوره قبل الرجوع.

## 10-ب. مندوب محجوب أو بلا بيانات تتبع

1. افتح «الفريق والصلاحيات» ← عمود «التتبع»، أو «تقرير يوم المندوب» ← اختر المندوب: اللوحة تقول هل لم يُفعَّل التتبع قط، أم لم تصل نقاط اليوم، وما آخر ما أبلغ به الهاتف.
2. «لم يصل أي تقرير من الهاتف»: لم يفتح النظام بعد التحديث. اطلب منه فتح تطبيق أندرويد.
3. «متصفح»: يستخدم المتصفح؛ لا حل إلا تطبيق أندرويد.
4. «أذونات ناقصة»: يفتح إعدادات الهاتف ← التطبيقات ← يورست ← الأذونات ← الموقع: «السماح طوال الوقت» مع الموقع الدقيق، والإشعارات.
5. «يوم العمل مرتبط بجهاز آخر»: بدّل هاتفه في منتصف اليوم؛ يُحل في اليوم التالي.
