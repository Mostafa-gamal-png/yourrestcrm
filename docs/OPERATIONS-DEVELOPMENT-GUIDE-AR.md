# دليل التشغيل والتطوير والتحديث — Yourrest CRM

هذا الدليل للمطوّر ومسؤول الاستضافة. يشرح تشغيل المشروع محليًا، واختباره، وبناءه، وتحديثه على الاستضافة مع الحفاظ على البيانات والإعدادات. لا تنشر شيئًا على الموقع الفعلي إلا بعد تجربة النسخة محليًا وأخذ نسخة احتياطية.

## 1. المتطلبات

| العنصر | الإصدار |
|---|---|
| Node.js | 22.16 أو أحدث (التطبيق يستخدم `node:sqlite` المدمج) |
| pnpm | 11 (`corepack enable` ثم `pnpm --version`) |
| Chromium + Playwright | اختياري، لاختبارات المتصفح فقط |
| Python 3 و`unzip` | اختياري، لسكربتات التغليف واختبارات الحزم |

لا توجد قاعدة بيانات خارجية: التطبيق يحفظ كل شيء في ملف SQLite ومجلد مرفقات خاصين.

## 2. أول تشغيل للتطوير

```bash
pnpm install --frozen-lockfile   # تثبيت الاعتمادات المقفلة
pnpm typecheck                   # فحص الأنواع
pnpm lint                        # ESLint
pnpm check                       # الأنواع + كل الاختبارات الافتراضية (نحو 6 دقائق)
pnpm build                       # البناء إلى dist/standalone
```

ملاحظات:
- إذا رفض pnpm تثبيت إصدار حديث بسبب `minimumReleaseAge` في `pnpm-workspace.yaml`، فهذه سياسة أمان مقصودة. لا تعطّلها في المشروع؛ استخدم الإصدارات المقفلة في `pnpm-lock.yaml`.
- كل الاختبارات تستخدم بيانات اصطناعية وقواعد SQLite مؤقتة. لا تحتاج إعدادات إنتاج ولا تلمس بيانات حقيقية.
- `pnpm check` ينفّذ الأنواع ثم كل ملف في `tests/` ما عدا الاستثناءات الموثقة في `tests/check-manifest.json`. إضافة ملف اختبار `.mjs` جديد لا تحتاج تسجيله.

## 3. تجربة التطبيق محليًا

بعد `pnpm build`:

```bash
pnpm demo
```

يشغّل النسخة المبنية ببيانات اصطناعية (ستة حسابات بأدوار مختلفة وثلاثة عملاء) على عنوان مثل `https://crm.yourrest.org:8443` بشهادة موقعة ذاتيًا. رموز الدخول تظهر في الطرفية عند طلبها ولا يُرسل أي بريد حقيقي. عند الإيقاف بـ Ctrl+C تُحذف بيانات التجربة.

لأن التطبيق يشترط أصل HTTPS، افتح العنوان بإحدى طريقتين:

1. Chrome بملف تعريف مؤقت (الأنظف):
   ```bash
   chrome --user-data-dir=/tmp/yr-demo --ignore-certificate-errors \
     --host-resolver-rules="MAP crm.yourrest.org 127.0.0.1" https://crm.yourrest.org:8443
   ```
2. أو إضافة السطر `127.0.0.1 crm.yourrest.org` إلى ملف hosts أثناء التجربة فقط، وحذفه بعدها.

لتغيير المنفذ: `DEMO_PORT=9443 pnpm demo`. الحسابات: `owner` و`admin` و`manager` و`supervisor` و`rep.east` و`rep.west` و`service` بنطاق `@yourrest.org`.

لتجربة الهاتف: في أدوات المطور اختر شاشة 390 بكسل أو جهازًا محمولًا. الوضع الليلي من المفتاح في الشريط العلوي.

## 4. الإعدادات والأسرار

- الإعدادات الحقيقية في ملف `settings.cjs` **خارج** مجلد الإصدار وخارج `public_html`، بصلاحية خاصة (600).
- `node setup.cjs` عند أول تثبيت على الاستضافة ينشئ `settings.cjs` بسرّ عشوائي جديد ومجلدات البيانات الخاصة. لا تشغّله على تثبيت قائم.
- القالب الخالي من الأسرار: `settings.example.cjs`. ومتغيرات البيئة النموذجية: `.env.example`.
- المفاتيح: `YR_APP_ORIGIN` و`YR_AUTH_SECRET` (64 خانة سداسية عشرية أو أكثر) و`YR_DATABASE_PATH` و`YR_OBJECTS_PATH` و`YR_MAIL_TRANSPORT` و`YR_MAIL_FROM` و`YR_SENDMAIL_PATH`، واختياريًا `YR_NATIONAL_ADDRESS_API_KEY`.
- تغيير `YR_AUTH_SECRET` يسجّل خروج كل المستخدمين. لا تضع السر في المستودع أو في السجلات.
- عند وجود `settings.cjs` يرفض التطبيق أي قيمة `YR_*` مختلفة في متغيرات البيئة.
- مفتاح توقيع أندرويد يُسلّم منفصلًا ولا يُنشر ولا يدخل المستودع.

| المسار | المحتوى |

| `app/` | الصفحات والمكونات ومسارات API (`app/api/*`) |
| `lib/` | القواعد الأساسية: الصلاحيات (`access.ts`)، المستهدفات (`targets.ts`)، أوزان التقييم (`kpis.ts`)، المبيعات، استيراد ERP، المزامنة دون شبكة |
| `db/` و`drizzle/` | المخطط وترحيلات SQL التراكمية (16 ملفًا؛ آخرها `0015_member_devices.sql`) |
| `portable/` | طبقة الاستضافة: التشغيل والإعداد والنسخ الاحتياطي والاسترجاع والترقية |
| `scripts/` | البناء والتغليف والتجربة المحلية؛ `scripts/lib/built-app.mjs` يشغّل النسخة المبنية للاختبارات |
| `tests/` | اختبارات الانحدار والأمان والمتصفح والإصدار |
| `mobile/android` | مصدر أندرويد (لا يُبنى هنا) |

## 6. قواعد التطوير الآمن

1. **الصلاحيات على الخادم دائمًا.** إخفاء زر في الواجهة ليس حماية. أي مسار جديد في `app/api` يتحقق من الجلسة ثم الدور ثم نطاق السجل، ويُضاف إلى `tests/server-authorization.mjs`.
2. **لا تعدّل المعادلات** (أوزان التقييم، تجميع المشرف ومدير المبيعات، المستهدفات الممتدة بالتواريخ) إلا بقرار أعمال، ومع اختبارات تثبّت الأرقام.
3. **الترحيلات تراكمية فقط.** لا تعدّل ملفًا في `drizzle/` طُبّق من قبل؛ أضف ملفًا جديدًا. التثبيت القائم يأخذ نسخة من المخطط قبل أي ترحيل.
4. **التواريخ بتوقيت الرياض.** استخدم `today()` من `lib/crm.ts` ولا تستخدم تاريخ جهاز المستخدم أو `toISOString()` على اللحظة الحالية.
5. **أنواع دقيقة بلا `any`** ولا `eslint-disable`. أخطاء lint المتبقية موثقة في تقرير المراجعة.
6. **استيراد جديد بين الوحدات** قد يكسر اختبارات تحقن التبعيات بأسماء محددة (مثل `tests/journey-ui.mjs`). استخدم `import type` للأنواع، وحدّث الاختبار إذا أضفت استيرادًا فعليًا.
7. **ملفات يولّدها البناء** (`public/offline-app/**` و`public/sw.js` و`public/offline-shell-manifest.json`) تتغير عند تغيير كود الواجهة. شغّل `pnpm build` وثبّتها في commit منفصل.
8. اختبارات المتصفح تكتب أدلة في `docs/`؛ وجّه مخرجاتها إلى مجلد مؤقت بمتغيرات `YR_*_SCREENSHOT_DIR` و`YR_*_REPORT` كي لا تتغير الأدلة المحفوظة.

## 8. البناء والتغليف

```bash
pnpm build        # ينشئ dist/standalone (التطبيق + مجلد operations + الترحيلات + manifest)
```

حزمة الاستضافة التراكمية تُنشأ بسكربتات `scripts/package-*.py` (مثل `package-namecheap.py`)، وهي تنسخ `dist/standalone` ومعها التعليمات والأدلة. هذه السكربتات تاريخية ومرتبطة باختبارات `tests/*-update-package.py`؛ لا تحذفها قبل توحيدها بقرار منفصل.

## 9. التحديث على الاستضافة مع الحفاظ على البيانات

البيانات والإعدادات خارج مجلد الإصدار، لذلك استبدال `release` لا يمسها. اتّبع الترتيب بدقة:

1. **نسخة احتياطية قبل أي تحديث** (يمكن أخذها والتطبيق يعمل):
   ```bash
   node /home/ACCOUNT/yourrest-crm/release/operations/backup-scheduled.mjs /home/ACCOUNT/yourrest-crm-backups 14
   ```
   تأكد أن الناتج `ok:true` وأن `status.json` يظهر `state: ok`. التفاصيل واستعادة نسخة: `docs/PRODUCTION-BACKUP-AR.md`.
2. من cPanel > **Setup Node.js App** اختر التطبيق ثم **Stop App**.
3. فكّ الحزمة داخل مجلد التطبيق مع **استبدال `release` فقط**. لا تستبدل `settings.cjs`، ولا مجلد البيانات `yourrest-crm-data`، ولا ملف قاعدة البيانات.
4. **لا تشغّل** `setup.cjs` ولا `npm install` على تثبيت قائم.
5. **Start App.** عند الإقلاع يطبّق التطبيق الترحيلات الجديدة فقط على قاعدة معروفة، بعد نسخة خاصة من المخطط. إذا توقف الإقلاع فراجع سجل التطبيق ولا تحذف قاعدة البيانات.
6. افتح الموقع وسجّل الدخول وتحقق من: الدخول، قائمة العملاء، تسجيل زيارة، صفحة المستهدفات. افتح التطبيق مرة أثناء الاتصال ثم أغلقه وافتحه لتفعيل واجهة الوضع دون اتصال.
7. تطبيق أندرويد لا يتحدث تلقائيًا برفع السيرفر؛ ثبّت APK الجديد (نفس التوقيع) فوق القديم دون حذفه إذا تغيّر إصدار الأندرويد.

**التراجع:** أوقف التطبيق وأعد `release` السابق. إذا لزم استرجاع البيانات فاستعدها إلى **مجلد خاص جديد** (الأداة ترفض الكتابة فوق مجلد قائم):

```bash
node /home/ACCOUNT/yourrest-crm/release/operations/restore.mjs verify  /home/ACCOUNT/yourrest-crm-backups/BACKUP_NAME
node /home/ACCOUNT/yourrest-crm/release/operations/restore.mjs restore /home/ACCOUNT/yourrest-crm-backups/BACKUP_NAME /home/ACCOUNT/yourrest-crm-restored
```

ثم وجّه `YR_DATABASE_PATH` و`YR_OBJECTS_PATH` في `settings.cjs` إلى المجلد المسترجع وشغّل التطبيق. لا تحذف قاعدة البيانات الأصلية قبل التأكد من سلامة المسترجعة.

## 9-ب. بناء حزمة التحديث وبروفتها قبل الرفع

حزمة الاستضافة التي تُرفع على cPanel تُبنى من `dist/standalone` بسكربت التغليف الذي يثبّت بصمة كل ملف داخل مُفعِّل مستقل. لا تُرفع حزمة السورس نفسها.

```bash
pnpm install --frozen-lockfile && pnpm build
python3 scripts/package-ui-refresh-update.py \
  --release dist/standalone --output /مسار/خارج/المستودع/Yourrest-CRM-Update-YYYYMMDD.zip \
  --release-name update --release-date YYYYMMDD \
  --stage-name yourrest-crm-update-YYYYMMDD --helper-name yourrest-activate-update.cjs \
  --guide docs/UPDATE-YYYYMMDD-AR.txt
```

الدليل يجب أن يذكر اسم مجلد الرفع واسم المُفعِّل وإلا يرفض السكربت.

**ترحيل جديد داخل الحزمة:** القاعدة الحية يجب أن تكون على الخط الأساسي (15 ترحيلًا). أي ترحيل بعده تُعلنه صراحة عند التغليف، وتشترط الحزمة أن يحمل البناء الترحيلات الأساسية + المعلنة بالضبط وإلا ترفض:

```bash
python3 scripts/package-ui-refresh-update.py ... \
  --new-migration 0015_member_devices.sql --verify-route /api/device-status=401
```

- `--new-migration` (يتكرر): اسم الترحيل بالضبط كما في `drizzle/`.
- `--verify-route PATH=STATUS` (يتكرر): مسار جديد يفحصه `--verify` بلا جلسة (المتوقع هنا 401).
- المُفعِّل لا يكتب في القاعدة ولا يشغّل الترحيل. `--check` يعلن التغيير، والتطبيق يطبّقه عند أول Start بعد نسخة خاصة في `yourrest-crm-data/schema-backups`، و`--verify` يرفض بسبب واضح (`MIGRATION_NOT_APPLIED_START_APP_FIRST`) إن لم يبدأ التطبيق، ثم يتأكد من 16 ترحيلًا ومن بقاء كل معرفات السجلات.
- **لا رجعة بسيطة بعد الترحيل:** الإصدار القديم يرفض قاعدة فيها ترحيل أحدث. التراجع بعد نجاح الترحيل = استعادة نسخة `schema-backups` + إعادة `old-release` (دليل التحديث يشرحه، وأي بيانات بعد التشغيل تضيع). قبل الترحيل لا خسارة.
- اختبار هذا المسار كاملًا: `node tests/schema-update-activation.mjs` (الحزمة الحقيقية والمُفعِّل الحقيقي وروتين الإقلاع الحقيقي على SQLite).

**بروفة كاملة قبل الرفع** (ببيانات اصطناعية، دون أي اتصال بالاستضافة): ابنِ الإصدار المثبّت حاليًا في مجلد منفصل ثم نفّذ بحساب غير مميز كما على الاستضافة:

```bash
node scripts/rehearse-update.mjs --old-release /مسار/dist/standalone-القديم --package /مسار/Yourrest-CRM-Update-YYYYMMDD.zip --out report.json
```

تُنشئ البروفة موقعًا مثبّتًا كالاستضافة، وتشغّل الإصدار القديم وتنشئ بيانات عبر واجهته، ثم تتبع خطوات الدليل: `--check` والتطبيق يعمل، رفض التبديل والتطبيق يعمل، الإيقاف والتبديل، التشغيل و`--verify`، ثم تثبت أن كل جدول ومرفق والإعدادات والواجهات لكل دور متطابقة، وأن حزمة معطوبة تُرفض دون لمس شيء. المُفعِّل يشترط أصل الموقع `https://crm.yourrest.org` تمامًا، لذلك تحتاج البروفة المنفذ 443 (صلاحية ربط المنافذ المنخفضة فقط).

عند إعلان ترحيل جديد تجرّب البروفة أيضًا طريقي التراجع بالخطوات نفسها المكتوبة في دليل التحديث: (أ) العودة قبل أول تشغيل للإصدار الجديد بإعادة `old-release`، و(ب) العودة بعد الترحيل. في (ب) تثبت أن الإصدار القديم يرفض القاعدة المرحَّلة، وأن استعادة نسخة `schema-backups` مع المجلد القديم تعيد كل جدول وكل واجهة إلى حالتها قبل التحديث. **ملفا `database.sqlite-wal` و`database.sqlite-shm` يبقيان بعد إيقاف التطبيق** ويجب إزاحتهما مع `database.sqlite` قبل نسخ النسخة الخاصة، وإلا اختلطا بالقاعدة المستعادة.

## 9-ج. إلزام تتبع المسار وحالة هاتف المندوب

**القاعدة:** المندوب (الدور `rep` فقط) لا يرى مساحة العمل إلا من تطبيق أندرويد وبعد اكتمال: الموافقة، الموقع الدقيق، الإشعارات، الموقع طوال الوقت، خدمة الموقع في الهاتف، وتسجيل الهاتف على حسابه. غير ذلك شاشة حجب كاملة تسمّي الناقص وتعرض الإجراء. الحجب في الواجهة فقط (السيرفر لا يمنع المندوب من قراءة بياناته إن عدّل المتصفح)، لذلك التقرير يكشف بدوره غياب النقاط.

| الملف | الدور |
|---|---|
| `lib/tracking-gate.ts` | قرار الحجب (دالة نقية) وجدول الحالات؛ اختباره `tests/tracking-gate.mjs` |
| `app/tracking-gate.tsx` | شاشة الحجب؛ تحيط مساحة العمل في `app/crm-app.tsx`. الأدوار الأخرى تمر دون تغيير |
| `lib/device-status.ts` + `app/device-status-reporter.tsx` | إرسال حالة الهاتف: عند التغيّر (60 ثانية كحد أدنى بين تقريرين) وكل 15 دقيقة، مع إعادة محاولة متصاعدة؛ ولا يُرسل أثناء «جارٍ التحقق» |
| `app/api/device-status/route.ts` + `lib/device-status-server.ts` | `POST` للمندوب وحده (حد 30 ثانية لكل جهاز ونص منقّى وزمن من السيرفر)، و`GET` لمن يرى تقرير المندوب ضمن نطاقه ومنطقته |
| `drizzle/0015_member_devices.sql` | جدول `crm_member_devices` (صف لكل مندوب ولكل منصة: `android-app` أو `browser`) |
| `lib/tracking-coverage.ts` و`lib/tracking-coverage-text.ts` | تصنيف يوم بلا GPS وصياغته: متتبَّع / فُتح يوم بلا نقاط / لا نقاط اليوم / لم يُفعَّل قط، والجمعة وما قبل 6 صباحًا ليسا فشلًا |
| `scripts/lib/native-bridge.mjs` | محاكي جسر أندرويد لاختبارات المتصفح (انظر `tests/CHECKS.md`) |

حالة الهاتف **للتشخيص فقط**: لا تدخل في حركة ولا زيارة ولا مستهدف ولا تقييم. لا تُضف إليها قرارًا تجاريًا.

عند كتابة اختبار متصفح يدخل بحساب مندوب: ثبّت المحاكي قبل `goto` (`installNativeBridge(page, {memberId, regionScope})`) وإلا يظهر الحجب بدل التطبيق.

## 10. حل المشكلات الشائعة

| العَرَض | السبب والحل |
|---|---|
| `Active all-region system owner is missing` عند الإقلاع | يلزم عضو `owner` فعّال بدور admin ونطاق كل المناطق في قاعدة البيانات |
| لا يصل رمز الدخول | تحقق من `YR_MAIL_FROM` (نطاق `@yourrest.org`) و`YR_SENDMAIL_PATH`؛ حد معدل الطلبات لكل عنوان قد يمنع الإرسال مؤقتًا |
| `Conflicting YR_*` | أزل متغير البيئة المخالف أو عدّل `settings.cjs` ليطابقه |
| رفض الكتابة بـ 403 | الطلب بلا أصل صحيح أو بلا الصلاحية؛ تحقق من `YR_APP_ORIGIN` وعنوان الموقع |
| اختبار متصفح ينقطع الاتصال | عطّل متغيرات الوكيل كما في القسم 7 |

## 10-ب. مندوب محجوب أو بلا بيانات تتبع

1. افتح «الفريق والصلاحيات» ← عمود «التتبع»، أو «تقرير يوم المندوب» ← اختر المندوب: اللوحة تقول هل لم يُفعَّل التتبع قط، أم لم تصل نقاط اليوم، وما آخر ما أبلغ به الهاتف.
2. «لم يصل أي تقرير من الهاتف»: لم يفتح النظام بعد التحديث. اطلب منه فتح تطبيق أندرويد.
3. «متصفح»: يستخدم المتصفح؛ لا حل إلا تطبيق أندرويد.
4. «أذونات ناقصة»: يفتح إعدادات الهاتف ← التطبيقات ← يورست ← الأذونات ← الموقع: «السماح طوال الوقت» مع الموقع الدقيق، والإشعارات.
5. «يوم العمل مرتبط بجهاز آخر»: بدّل هاتفه في منتصف اليوم؛ يُحل في اليوم التالي.
