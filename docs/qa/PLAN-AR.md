## 1. ما وجدته في الفحص الأولي (حالة البداية)

### بنية المشروع
| العنصر | الحالة |
|---|---|
| الإطار | Next 16.3.6 يعمل عبر `vinext 1.0.0-beta.5` + Vite 8، React 19.2، TypeScript 5.9 strict |
| قاعدة البيانات | SQLite عبر `node:sqlite` (Node ≥ 22.16) خلف طبقة Drizzle بواجهة D1، 13 ملف migration في `drizzle/` |
| الاستضافة | Namecheap cPanel + Passenger، التشغيل من `dist/standalone/app.cjs`، الإعدادات في `settings.cjs` بمتغيرات `YR_*` |
| المصادقة | بريد + OTP (`lib/email-auth.ts`, `portable/local-mail.mjs`) |
| الأدوار | `admin`, `manager`, `supervisor`, `rep`, `customer_service`, `customer_service_manager` — المنطق في `lib/access.ts` |
| الواجهة | 40 ملف صفحة/مكوّن في `app/`، مكوّنات shadcn مُضمّنة في `components/ui/` (لا تُعدَّل) |
| API | 19 مسار في `app/api/` |
| الاختبارات | ~130 ملف `.mjs` في `tests/` بحزّان (harness) خاص: ترجمة TS بالذاكرة + SQLite في الذاكرة. بوابة `npm run check` تشغّل `tsc` + كل الاختبارات الافتراضية |
| البوابات المستثناة | `browser` (تحتاج بناء + Chromium)، `release-build`، `release-artifact` (اختبارات Python لحزم الإصدار)، `erp-workbook` (تحتاج ملف ERP الأصلي) |
| Lint | إعداد ESLint 9 موجود لكن **لا يوجد سكربت `lint`** في `package.json` |
| Android | مصدر `mobile/android` خارج نطاق هذه المهمة (لا JDK/SDK هنا) |

### معادلات يجب الحفاظ عليها حرفيًا
- **أوزان التقييم:** `lib/kpis.ts` — 18 مؤشرًا بأوزان ثابتة (تحقيق المستهدف 25، التحصيل 20، ...) و6 محاور.
- **المستهدفات:** `lib/targets.ts` — `effectiveSet` (آخر مجموعة محفوظة في الشهر أو قبله)، `withManagerTargets` (تجميع المشرف/مدير المبيعات من فريقه)، `quantityAttainment` (التحقق الكمي الموزون).
- **نطاق الصلاحيات:** `salesScopeMemberIds` و`salesRecordAccess` في `lib/access.ts`.
- **الملخص الأعلى:** `lib/targets-performance-summary.ts`.

### ملاحظات أولية على جودة الكود (قبل أي تشغيل)
- الأسلوب مكثّف جدًا (أسطر طويلة شبه مضغوطة). إعادة التنسيق الشاملة ستُفسد قابلية مراجعة الفروقات، لذلك **لن أعيد تنسيق الملفات كاملة**؛ سأستخرج دوالًا وأفصل المسؤوليات بخطوات صغيرة فقط.
- 11 موضعًا فيها `as any` أو `eslint-disable` في `app/` و`lib/` (مثل `app/api/followups/route.ts`، `lib/crm-context-records.ts`، `app/crm-app.tsx`).
- أكبر الملفات: `app/crm-app.tsx` (444 سطرًا)، `lib/erp-sales.ts` (389)، `app/journey-tracker.tsx` (374).
- `README.md` فيه فقرات مكررة 3 مرات (Competitors workspace) وتاريخ تحديثات متراكم.
- 30+ سكربت `scripts/package-*-update.py` تاريخية لحزم إصدارات قديمة، مرتبطة باختبارات Python في بوابة `release-artifact`.
- الاعتمادات: `pnpm-workspace.yaml` فيه `minimumReleaseAge: 10080` و`trustLockfile: false` — قد يبطّئ التثبيت أو يرفض إصدارات؛ يُسجَّل كمخاطرة.

## 2. القرارات والافتراضات (أعمل بها ما لم تُصحَّح)

1. **المستودع يحتوي ZIP فقط.** سأفك الضغط إلى جذر المستودع (مجلد `Yourrest-CRM/` يصبح الجذر) وأُثبّت commit "خط الأساس" بدون أي تعديل، ثم تبدأ التغييرات فوقه كي تظهر الفروقات بوضوح. ملف ZIP الأصلي يبقى في تاريخ git ويُحذف من الشجرة.
2. **لا نشر على الإنتاج** ولا اتصال بأي بيانات حقيقية. كل التجارب على SQLite مؤقت وحسابات مصطنعة.
3. **لا تغيير في مخطط قاعدة البيانات** (لا migration جديد) إلا إذا أثبت الفحص خطأً يستلزم ذلك، وعندها يكون append-only مع ذكره في التقرير.
4. **لا إضافة مكتبات** إلا لحاجة واضحة. Playwright موجود في البيئة (Chromium في `/opt/pw-browsers`) ولن يُضاف للاعتمادات.
5. **Android وGSCO وموقع يورست جروب وبوابة المنتجات خارج النطاق**؛ لا يُلمس `mobile/`.
6. **السكربتات التاريخية `package-*.py`** لن تُحذف في هذه الجولة لأنها مربوطة ببوابة اختبار موثّقة؛ سأقترح توحيدها في التقرير فقط.

## 3. مراحل التنفيذ

### المرحلة 0 — تجهيز المستودع (نصف ساعة)
- فك الـ ZIP إلى جذر المستودع، إضافة `.gitignore` للمخرجات (`output/`, `.sites-runtime/`, `dist/`, `node_modules/`).
- Commit: `baseline: import Yourrest CRM source 2026-10-08 unchanged`.

### المرحلة 1 — خط الأساس قبل التعديل
- `pnpm install --frozen-lockfile` وتسجيل أي فشل.
- إضافة سكربت `lint` (`eslint .`) و`typecheck` (`tsc --noEmit`) إلى `package.json` دون تغيير القواعد.
- تشغيل: `pnpm typecheck` → `pnpm lint` → `npm run check` (البوابة الافتراضية) → `npm run build`.
- حفظ النتائج في `docs/qa/BASELINE-2026-10-10.json` مع تصنيف كل فشل: **موجود مسبقًا** / **بيئي** / **غير قابل للتشغيل هنا**.
- بعد البناء: `node tests/namecheap-http.mjs` و`node tests/app-update-release.mjs` (بوابة `release-build`).

### المرحلة 2 — بيئة تجريبية معزولة
- إنشاء `settings.example.cjs` و`.env.example` نموذجيين بلا أسرار (كل متغيرات `YR_*` المكتشفة: `YR_APP_ORIGIN`, `YR_AUTH_SECRET`, `YR_DATABASE_PATH`, `YR_OBJECTS_PATH`, `YR_MAIL_*`, `YR_NATIONAL_ADDRESS_API_KEY`).
- سكربت `scripts/seed-dev.mjs`: قاعدة SQLite مؤقتة عبر `portable/initialize.mjs`، حساب لكل دور (admin، مدير مبيعات، مشرف، مندوبان في منطقتين، خدمة عملاء)، عملاء وزيارات ومتابعات ومبيعات حديثة وقديمة ومستهدفات وأوزان.
- تشغيل `dist/standalone` محليًا مع بريد OTP محلي (ملفات) لقراءة رمز الدخول.

### المرحلة 3 — اختبار الوظائف الفعلية
**أ. آليًا على الخادم (HTTP مباشر):**
- مصفوفة الصلاحيات: كل دور × كل مسار API (19 مسارًا) × GET/POST، والتأكد أن الرفض يحدث على الخادم لا في الواجهة فقط.
- تسجيل الدخول: OTP صحيح/خاطئ/منتهٍ، حدود المحاولات (`auth_limits`)، إبطال الجلسة عند تغيير `auth_version`.
- العملاء: إنشاء/تعديل/حذف حسب الدور، أكواد العملاء والأسماء المستعارة، الاستيراد (`customers/import`, `machines/import`).
- الزيارات والمتابعات: الإنشاء، المرفقات (`visit-files`) وحدود الحجم، منع تعديل المندوب للسجلات القديمة.
- المبيعات: الاستيراد اليدوي و ERP (ملف XLSX اصطناعي)، السجلات القديمة، فلاتر التاريخ عبر حدود الشهور والمنطقة الزمنية Asia/Riyadh، المرتجعات.
- المستهدفات والتقييم: حالات **اختبار توصيفية (characterization)** تُثبّت الأرقام الحالية لـ `quantityAttainment` و`withManagerTargets` و`kpiSummary` قبل أي refactor.

**ب. بالمتصفح الفعلي (Playwright + Chromium، سطح مكتب 1366px وهاتف 390px):**
- الدخول، التنقل بالأدوار، النماذج والأزرار، رفع الملفات ومؤشر التقدم، الفلاتر والعدادات، الوضع الليلي، لغة الواجهة، القوائم على الهاتف.
- لقطات شاشة قبل/بعد في `docs/qa/screenshots/`.

### المرحلة 4 — إصلاح الأخطاء
- لكل خطأ مُثبَت: السبب الجذري → إصلاح أصغر ما يمكن → اختبار تراجعي باسم واضح → commit مستقل.
- ملاحظات `tsc` و`eslint` و`react-hooks` تُعالج حسب الأثر الفعلي: استبدال `as any` بأنواع دقيقة، إصلاح اعتماديات الـ hooks بدل تعطيل القاعدة، بلا إضعاف أي تحقق (zod، origin، حدود الحجم).
- الأولوية: أمان/صلاحيات → صحة الحسابات (مستهدفات/KPI/تواريخ) → فقدان بيانات أو حفظ خاطئ → واجهة الهاتف → تحسينات.

### المرحلة 5 — إعادة تنظيم الكود (خطوات صغيرة قابلة للمراجعة)
1. توحيد أنماط مسارات API المتكررة (`checkOrigin` + `readJsonBody` + حدود الحجم + تحويل `CRMError` إلى استجابة) في مساعد واحد.
2. تقسيم `app/crm-app.tsx` إلى: تحميل الجلسة، التنقل، تسجيل أدوات السياق.
3. فصل تحليل ملف ERP عن قواعد الأعمال في `lib/erp-sales.ts`.
4. توحيد مساعدي الوقت والتواريخ (Asia/Riyadh) في موضع واحد.
5. تحسين الأسماء ومعالجة الأخطاء في الطبقات التي يثبت الفحص أنها غامضة.
6. تنظيف `README.md` (إزالة التكرار، نقل التاريخ إلى `docs/CHANGELOG-AR.md`).
7. حذف الكود غير المستخدم فقط بعد إثبات عدم الاستخدام (بحث مرجعي + نجاح البوابة).
- كل خطوة: البوابة خضراء قبلها وبعدها، سلوك الواجهة والـ API لا يتغير، التوافق مع `dist/standalone` وPassenger محفوظ.

### المرحلة 6 — التحقق النهائي
- إعادة `typecheck` + `lint` + `npm run check` + `build` + اختبارات `release-build` + اختبارات المتصفح.
- مقارنة قبل/بعد: عدد الاختبارات، الفشل المسبق (بأسمائه وأسبابه)، أي فشل جديد وتحقيقه.
- تجربة الهاتف والوضع الليلي مرة أخيرة بلقطات.

### المرحلة 7 — التسليم
- **ZIP** بالسورس الكامل المعدّل (بدون `node_modules`/`dist`/مخرجات) + `settings.example.cjs` + `.env.example`.
- **دليل عربي** `docs/دليل-التشغيل-والتطوير-AR.md`: المتطلبات، التثبيت، التشغيل محليًا، البناء، التحديث على الاستضافة مع الحفاظ على البيانات (نسخة احتياطية → رفع الإصدار → `portable/upgrade.mjs` → التحقق → الاسترجاع عند الفشل).
- **تقرير** `docs/qa/REPORT-AR.md`: التغييرات، النتائج قبل/بعد، الأخطاء المُصلحة وأسبابها، المشكلات المتبقية، ما تعذّر اختباره.
- Commit وPush على الفرع المحدد فقط. **لا نشر على الموقع.**

## 4. ما أتوقع تعذّر اختباره هنا (سيُذكر بوضوح في التقرير)
- بوابة `erp-workbook`: تحتاج ملف ERP الأصلي غير المرفق؛ سأستخدم ملفًا اصطناعيًا للمنطق فقط.
- تطبيق Android وGPS في الخلفية وتسليم البريد الفعلي عبر sendmail على Namecheap.
- الأداء الحقيقي على استضافة Namecheap (اختبار الحمل هنا على بيانات اصطناعية فقط).
- اختبارات حزم الإصدار (Python) إلا إذا أعدت توليد حزمة بالسكربتات الموجودة.

## 5. المخاطر
- فشل `pnpm install` بسبب سياسة `minimumReleaseAge` أو الشبكة → سأحاول `--config.minimumReleaseAge=0` مؤقتًا في البيئة فقط دون تعديل سياسة المشروع، وأسجّل ذلك.
- `vinext` نسخة beta: أي فشل بناء غير مرتبط بالكود يُصنَّف بيئيًا ويُوثَّق.
- الأسلوب المكثّف يرفع احتمال كسر السلوك عند الاستخراج → الاعتماد على اختبارات التوصيف قبل كل خطوة.
