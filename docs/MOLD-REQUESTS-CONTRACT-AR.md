# عقد الواجهة: طلبات القوالب بين yourrestcrm وyourrest-products (الإصدار 1)

يربط هذا العقد برنامجين مستقلين لا يدخل مستخدمو أحدهما الآخر:

- **yourrestcrm** (Namecheap، Node/SQLite): يدخل فيه **المندوب** طلب القالب ويرى حالته. هو **المالك** لبيانات الطلب.
- **yourrest-products** (cPanel، PHP/MySQL، `https://yourrest.org/products/`): يعمل فيه **موظفو الإنتاج** على الطلب. هو **المالك** لبيانات الإنتاج والتسليم.

الـ CRM هو من يتصل بتطبيق المنتجات دائمًا (يرسل الطلب ويسحب الحالة). تطبيق المنتجات لا يتصل بالـ CRM إطلاقًا.

## 1) العنوان والمصادقة

العنوان: `https://yourrest.org/products/crm-api.php?route=<route>` والمسارات: `requests` و`status` و`cancel`. كلها `POST` بجسم JSON بترميز UTF-8 وترويسة `Content-Type: application/json; charset=utf-8`. HTTPS فقط.

لا توجد جلسات ولا كوكيز. كل طلب يُوقَّع بمفتاح سري مشترك (32 حرفًا عشوائيًا على الأقل، يُحفظ خارج الكود في إعداد كل طرف ولا يصل للمتصفح أبدًا):

- `X-YR-Timestamp`: ثواني Unix (UTC) وقت الإرسال. يُرفض الطلب إن زاد الفرق عن الخادم على 300 ثانية.
- `X-YR-Signature`: HMAC-SHA256 بحروف hex صغيرة للنص التالي، بالمفتاح السري:

```
<timestamp>\n<METHOD>\n<route>\n<sha256-hex(جسم الطلب كما أُرسل بالضبط)>
```

مثال: `1767225600\nPOST\nrequests\n<sha256>`. المسار `route` هو اسم المسار فقط دون `?route=`. جسم فارغ يعني sha256 للنص الفارغ.

**متجه اختبار** (يجب أن يطابقه التنفيذان):

- المفتاح: `test-secret-for-contract-vector-0123456789abcdef`
- الوقت: `1767225600`، الطريقة `POST`، المسار `requests`
- الجسم (UTF-8 بالضبط): `{"crmRequestId":"rec-1","specs":{"notes":"طلب تجريبي"}}`
- sha256 للجسم: `c7f373832a49548ba96241f5284c065765fb871add3a3c32adbf9be6e8d2b19a`
- التوقيع المتوقع: `d52d43c3f895c07a5a1c8ffddebc6a1a3e7f819df32b6c06c8cf3f104777a3f1`

## 2) المسارات

### `requests` — إنشاء أو تعديل أو ربط طلب (آمن للتكرار)

الجسم:

```json
{
  "crmRequestId": "rec-9f3a",
  "legacyOrderNo": 12,
  "requestedAt": "2026-10-29T10:15:00+03:00",
  "customer": { "crmNumber": 27, "name": "مصنع زايد للطابوق", "address": "الدمام", "city": "Damam - الدمام" },
  "salesman": { "crmMemberId": "mem-1", "name": "أحمد عبد العزيز", "email": "name@yourrest.org" },
  "specs": {
    "description": "200*400*27.5TH MM OPEN",
    "core": "open", "vibrators": 2, "model": "old", "halfBlock": "none",
    "moldWidth": 1380, "gelbaSize": 795, "moldNo": "YR099-9",
    "quantity": 1, "designUrl": "https://drive.google.com/...", "notes": ""
  }
}
```

- `crmRequestId` (إلزامي): معرّف الطلب في الـ CRM، حروف وأرقام و`_` و`-` حتى 64. هو مفتاح عدم التكرار.
- `legacyOrderNo` (اختياري): للطلبات التاريخية فقط (الفقرة 5).
- `requestedAt`: ISO مع إزاحة المنطقة. `salesman.email` اختياري. `designUrl` اختياري ويجب أن يبدأ بـ `https://`.
- حدود الحروف: `notes` حتى 2000، `address` حتى 300، `description` حتى 200، `moldNo` حتى 40، بقية النصوص حتى 160، `designUrl` حتى 1000.

القيم المسموحة (نفس القوائم في كلا الطرفين):

| الحقل | القيم | التسمية العربية |
|---|---|---|
| `core` | `open` / `closed` | مفتوح / مغلق |
| `vibrators` | `2` / `3` / `4` | عدد الرجاجات |
| `model` | `old` / `gelba_new` / `new` | موديل قديم / جلبة موديل جديد / موديل جديد |
| `halfBlock` | `none` / `one` / `two` / `three` | كما في الشيت: No H.B / 1 H.B / 2 H.B / 3 H.B |
| `moldWidth` | عدد صحيح 1000 إلى 2000 (مم). المعتاد 1380 و1375 | عرض القالب |
| `gelbaSize` | عدد صحيح 500 إلى 1200. المعتاد 795 و800 | مقاس الجلب |
| `quantity` | عدد صحيح 1 إلى 100 | الكمية |

السلوك:

- طلب جديد: يُنشأ بحالة `received` ويُعطى `orderNo` تسلسليًا. الرد `201` و`created: true`.
- الطلب موجود وما زال `editable`: تُستبدل حقول الطلب (لا حقول الإنتاج). الرد `200` و`created: false`. إن تطابقت البيانات فلا أثر.
- الطلب موجود وغير `editable`: `409` برمز `request_locked`، وفي `error.details.request` الحالة الحالية.

الرد:

```json
{ "request": <كائن الحالة>, "created": true, "linked": false }
```

### `status` — سحب الحالة

الجسم: `{ "ids": ["rec-9f3a", "rec-2b"] }` (حتى 200). الرد:

```json
{ "requests": [ <كائن الحالة> ], "unknown": ["معرّفات غير موجودة"] }
```

### `cancel` — إلغاء طلب

الجسم: `{ "crmRequestId": "rec-9f3a", "reason": "..." }`. يُنفَّذ فقط إن كان الطلب `editable`، وإلا `409 request_locked`. تكراره على طلب ملغى يرجع `200` بحالته.

### `pending` — الطلبات التي تنتظر اعتماد مدير المبيعات

مدير المبيعات يعمل على الـ CRM فقط، ويعتمد **كل** الطلبات من هناك: الواردة من الـ CRM، والمسجلة مباشرة في تطبيق المنتجات. يستدعي الـ CRM هذا المسار (مثلًا كل بضع دقائق) ويعرض النتيجة لمدير المبيعات.

- الجسم: `{}`.
- الرد: `{ "requests": [ ... ] }`، والأقدم انتظارًا أولًا (حتى 500 طلب).
- كل عنصر فيه:
  - `orderNo` و`revision`.
  - `crmRequestId`: قيمته `null` للطلب المسجل في المنتجات.
  - `source`: إما `crm` أو `manual`.
  - `requestedAt` و`waitingSince`.
  - `enteredBy`: مَن سجّله في المنتجات، للطلب `manual` فقط.
  - `customer` و`salesman` و`specs` بنفس حقول طلب الـ CRM.
- لا يحمل أي بيانات إنتاج.

### `customers` — قائمة عملاء الـ CRM

الطلبات المسجلة مباشرة في تطبيق المنتجات تختار العميل من قائمة عملاء الـ CRM فقط، ويُملأ منها كود يورست والعنوان والمدينة. يرسل الـ CRM القائمة كاملة مرة أولى، ثم كلما أُضيف عميل أو عُدّل أو حُذف (أو مرة يوميًا على الأقل).

```json
{ "mode": "full", "customers": [ { "crmNumber": 27, "name": "مصنع زايد", "address": "الدمام", "city": "Damam - الدمام", "erpCode": "146", "active": true } ] }
```

الحقول:
- `crmNumber`: كود يورست الرقمي (`crm_customer_numbers.number`)، إلزامي.
- `name`: إلزامي، حتى 200 حرف.
- `address`: اختياري، حتى 300 حرف.
- `city`: اختياري، حتى 100 حرف. يُفضَّل بصيغة الشيت مثل `Damam - الدمام` حتى تُملأ المدينة تلقائيًا.
- `active`: اختياري، والافتراضي `true`.
- `erpCode` (إضافة 2026-11-02): كود العميل في ERP، وهو «رقم العميل» في ملف عملاء ERP. نص حتى 50 حرف، والأرقام فيه أرقام إنجليزية (146 مش ١٤٦). الـ CRM يرسله مع كل عميل في القائمة، و`""` لما العميل ملوش كود (أو كوده أطول من 50 حرف)؛ لما يوصل فاضي امسح الكود المحفوظ عندك. العميل المحذوف بيتبعت `active: false` من غير الحقل ده، ولما الحقل مش موجود سيب الكود اللي عندك زي ما هو. يُعرض في اختيار العميل ويُبحث به، لكن ربط الطلب بالعميل يفضل بـ `crmNumber` (كود يورست). تطبيق المنتجات يتجاهل الحقل لحد ما يدعمه، فإرساله لا يكسر شيئًا.

الوضع `mode`:
- `upsert`: يضيف أو يحدّث العملاء المرسلين فقط.
- `full`: يفعل ذلك، ويوقف كل عميل غير موجود في القائمة. لا يُحذف، لأن الطلبات تشير إليه.

للقوائم الكبيرة: أرسلها على دفعات بـ `upsert`، ثم أرسل نداءً أخيرًا بـ `full` يحمل كل العملاء.

حد هذا المسار 2MB (بقية المسارات 64KB)، وحتى 20000 عميل في النداء. ولأن القائمة الكاملة أكبر، ينتظر الـ CRM رد هذا المسار حتى 60 ثانية (بقية المسارات 10 ثوانٍ).

العميل المحذوف أو الموقوف في الـ CRM يُرسَل بـ `upsert` و`"active": false` وقت حذفه، فلا يعتمد إيقافه على نداء `full` التالي.

الرد: `{ "received", "inserted", "updated", "deactivated", "activeCustomers" }`.

### `approval` — اعتماد مدير المبيعات أو سحبه (آمن للتكرار)

مدير المبيعات يعتمد من الـ CRM، وهذا المسار يبلّغ تطبيق المنتجات بذلك. الـ CRM هو من يقرر مَن يحق له الاعتماد. لا يمكن إعطاء هذا الاعتماد من تطبيق المنتجات. اعتمادا الإنتاج ومدير النظام يتمان في تطبيق المنتجات.

الجسم:

```json
{ "crmRequestId": "rec-9f3a", "action": "approve", "by": { "name": "اسم مدير المبيعات", "email": "manager@yourrest.org" } }
```

- الطلب يُحدَّد بـ `crmRequestId` إن جاء من الـ CRM، أو بـ `orderNo` إن سُجّل في المنتجات. أحدهما فقط.
- `action`: إما `approve` أو `withdraw`.
- `by.name`: إلزامي.
- `by.email`: اختياري.

الرد `200`: `{ "request": <كائن الحالة> }`.

قواعد المسار:
- `approve` على طلب معتمد من مدير المبيعات يرجع `200` دون تغيير.
- `withdraw` على طلب غير معتمد يرجع `200` دون تغيير.
- `withdraw` بعد اعتماد الإنتاج يرجع `409 request_locked`.
- الطلب الملغى يرجع `409 request_locked`.
- طلب الشيت التاريخي يرجع `409 request_locked`، لأنه معتمد أصلًا.
- المعرّف غير الموجود يرجع `404 not_found`.
- أي تعديل لاحق للطلب من الـ CRM يلغي الاعتمادات، ويلزم الاعتماد من جديد.

كل رد `409 request_locked` من هذا المسار يحمل كائن الحالة في `error.details.request`، ومنه يُعرف السبب:
- `status` = `cancelled`: الطلب ملغى (من المندوب، أو حُذف في تطبيق المنتجات).
- `approvals.required` = `false`: طلب تاريخي من الشيت لا يحتاج اعتمادًا.
- `approvals.production` ليس `null`: الإنتاج اعتمد، فلا يُسحب اعتماد مدير المبيعات.

## 3) كائن الحالة (يملكه تطبيق المنتجات)

```json
{
  "crmRequestId": "rec-9f3a",
  "orderNo": 92,
  "status": "in_production",
  "editable": false,
  "moldSerial": "093",
  "productionDate": "2026-10-30",
  "stages": {
    "laserCutting":  { "done": true,  "at": "2026-10-30" },
    "box":           { "done": true,  "at": "2026-10-31" },
    "coreConnector": { "done": false, "at": null },
    "lowerMold":     { "done": false, "at": null },
    "tempershoe":    { "done": false, "at": null },
    "alignment":     { "done": false, "at": null },
    "paint":         { "done": false, "at": null }
  },
  "stagesDone": 2,
  "stagesTotal": 7,
  "delivered": false,
  "deliveryDate": null,
  "waitingStep": "manufacturing",
  "waitingSince": "2026-10-30T11:20:00+03:00",
  "approvals": {
    "required": true,
    "sales": { "at": "2026-10-29T12:00:00+03:00", "by": "manager@yourrest.org (اسم مدير المبيعات)" },
    "production": { "at": "2026-10-29T15:30:00+03:00" },
    "admin": { "at": "2026-10-30T09:10:00+03:00" }
  },
  "updatedAt": "2026-10-31T09:00:00+03:00",
  "revision": 5
}
```

ترتيب المراحل ثابت: `laserCutting` ثم `box` ثم `coreConnector` ثم `lowerMold` ثم `tempershoe` ثم `alignment` ثم `paint`. تُعرض بأسمائها الإنجليزية كما في الشيت: Laser Cutting، BOX، Core and Connector، Lower Mold، Tempershoe، Alignment، Paint. `at` تاريخ إتمام المرحلة إن عُرف وإلا `null` (الطلبات التاريخية لا تاريخ لمراحلها).

`status` يحسبه تطبيق المنتجات بهذا الترتيب: `cancelled` ثم `delivered` (سُلّم) ثم `produced` (المراحل السبع كلها منتهية ولم يُسلَّم) ثم `in_production` (مرحلة منتهية أو تاريخ إنتاج) ثم `confirmed` ثم `received`. و`editable` تساوي `true` فقط حين تكون الحالة `received`.

**الاعتمادات:** كل طلب جديد يحتاج ثلاثة اعتمادات بالترتيب في تطبيق المنتجات: مدير المبيعات، ثم الإنتاج، ثم مدير النظام. `confirmed` تعني اكتمال الثلاثة، ولا يبدأ الإنتاج قبلها. أثناء الاعتمادات تبقى الحالة `received`، فيظل المندوب قادرًا على التعديل والإلغاء. **أي تعديل من الـ CRM أثناء الاعتمادات يلغي ما تم منها**، ويعود الطلب لمدير المبيعات.

`waitingStep` يوضح أين ينتظر الطلب الآن (حقل إضافي، يمكن للـ CRM عرضه للمندوب أو تجاهله):
- `sales`: بانتظار اعتماد مدير المبيعات.
- `production`: بانتظار اعتماد الإنتاج.
- `admin`: بانتظار اعتماد مدير النظام.
- `manufacturing`: في التصنيع.
- `delivery`: بانتظار التسليم.
- `done`: تم التسليم.
- `cancelled`: ملغى.

`waitingSince` وقت دخوله هذه الخطوة بتوقيت الرياض.

`approvals` يوضح وقت كل اعتماد، وقيمته `null` إن لم يتم بعد:
- اسم المعتمد (`by`) يُرجَع لاعتماد مدير المبيعات الذي جاء من الـ CRM فقط.
- `required: false` تعني طلبًا تاريخيًا لا يحتاج اعتمادًا.

إن حُذف طلب في تطبيق المنتجات يُرجَع بالحالة `cancelled`.

**تصحيح الطلب في تطبيق المنتجات:** كائن الحالة لا يحمل بيانات الطلب، فالتصحيح لا يصل إلى الـ CRM، ويبقى الـ CRM يعرض البيانات كما أرسلها. لذلك لا يُصحَّح طلب الـ CRM في تطبيق المنتجات ما دام `editable` (أثناء الاعتمادات)، حتى لا يمسح تعديلٌ من المندوب تصحيحًا لم يره. بعد اكتمال الاعتمادات يمكن تصحيحه هناك.

**لا يُرجع تطبيق المنتجات أبدًا**: ملاحظات الإنتاج الداخلية، العمال، المشرفين، أي بيانات إنتاج أخرى.
**لا يرسل الـ CRM أبدًا** غير الحقول المذكورة أعلاه: لا هواتف ولا بريد العميل ولا بيانات زيارات ولا مبيعات.

## 4) الأخطاء

أي خطأ: `{ "error": { "code": "...", "message": "...", "fields": [...]?, "details": {...}? } }`

| الرمز | HTTP | المعنى |
|---|---|---|
| `invalid_signature` | 401 | توقيع خاطئ أو ترويسات ناقصة |
| `stale_timestamp` | 401 | فرق الوقت أكبر من 300 ثانية |
| `not_configured` | 503 | المفتاح السري غير مضبوط في تطبيق المنتجات |
| `invalid_payload` | 400 | بيانات غير صحيحة، و`fields` تسمي الحقول |
| `request_locked` | 409 | الإنتاج قبل الطلب فلا تعديل ولا إلغاء |
| `not_found` | 404 | طلب غير موجود (في `cancel`) |
| `payload_too_large` | 413 | الجسم أكبر من 64 كيلوبايت |
| `method_not_allowed` | 405 | غير POST |

## 5) الطلبات التاريخية (91 طلبًا في الشيت)

ملف `mold-requests-source.json` فيه الطلبات الـ 91 بصيغ موحّدة (`legacyOrderNo` من 1 إلى 91). يستورد تطبيق المنتجات بيانات الإنتاج والتسليم والمراحل منه. ثم يُنشئ الـ CRM سجلاته للطلبات نفسها (العميل بـ `customer.crmNumber`، والمندوب باسمه) ويرسل كل طلب إلى `requests` بـ `crmRequestId` الجديد و`legacyOrderNo`: عندها **يربط** تطبيق المنتجات الصف المستورد بالمعرّف (`linked: true`) دون المساس ببيانات الإنتاج، وتكراره بلا أثر.

حقل `dataIssues` في كل صف يصف أخطاء الشيت الأصلية (مثل تاريخ إنتاج قبل تاريخ الطلب). لا تُصحَّح تلقائيًا بل تُعرض في تقرير.

## 6) السلوك المطلوب من الـ CRM عند تعذر الاتصال

- إرسال الطلب أو تعديله أو إلغاؤه: يُحفظ في الـ CRM أولًا ثم يُرسل. عند الفشل يبقى «بانتظار الإرسال» ويُعاد بتباعد متزايد (دقيقة ثم 5 دقائق ثم 30 دقيقة ثم ساعتان ثم كل ساعتين حتى 24 ساعة) وبزر «إعادة الإرسال» للمندوب. التكرار آمن لأن `requests` idempotent.
- سحب الحالة: بلا إعادة محاولة. يُعرض آخر ما عُرف مع «آخر تحديث» ويُحدَّث عند الفتح التالي.
- مهلة كل طلب 10 ثوانٍ، و60 ثانية لـ `customers`.

## إضافة: ملفات التصميم (2026-11-02)

تطبيق المنتجات أضاف ملفات تصميم القوالب (PDF وصور وملفات هندسية) وطباعة «أمر العمل» بالتصميم. هذه الإضافة على عقد الإصدار 1، بنفس التوقيع ونفس العنوان (القسم 1). النص كما أرسله المالك.

### `design-files` — إرفاق ملف بالطلب (آمن للتكرار)

- الجسم مش JSON: سطر واحد JSON، ثم `\n`، ثم بايتات الملف كما هي. والترويسة `Content-Type: application/octet-stream`.
  مثال: `{"crmRequestId":"rec-9f3a","crmFileId":"f-71c2","name":"رسم القالب 1380.pdf"}\n<بايتات>`
- التوقيع المعتاد: HMAC على `"ts\nPOST\ndesign-files\nsha256(الجسم كله: سطر JSON + \n + الملف)"`. وقّع نفس البايتات المرسلة بالظبط.
- `crmRequestId`: لازم الطلب يكون اتقبل في `requests` الأول. لو اتبعت قبله يرجع 404.
- `crmFileId`: معرّف ثابت للملف عندكم، بالنمط `^[A-Za-z0-9_-]{1,64}$`، ومايتكررش لملف تاني أبدًا.
- `name`: الاسم الأصلي، لحد 200 حرف، من غير مسارات ولا `\ / < > : " | ? *` ولا رموز تحكم. الامتداد لازم يكون واحد من دول:
  - pdf
  - png وjpg وjpeg وwebp وgif
  - dwg وdxf وstep وstp وigs وiges وstl وsldprt وsldasm وslddrw وnc1 وdstv وai وeps وcdr وpsd وsvg وzip وrar و7z
- الحدود: 25 ميجابايت للملف، و10 ملفات للطلب. الصورة لحد 80 مليون نقطة، والـ PDF لازم يكون PDF فعلًا.
- الردود:
  - 201 `{created:true, file, request}`
  - 200 `{created:false,...}`: لو نفس `crmFileId` بنفس البايتات اتبعت قبل كده.
  - 409 `request_locked` (مع كائن الحالة): الطلب مبقاش `editable`، أي إن الاعتمادات اكتملت.
  - 404 `not_found`: الطلب مش موجود عند الإنتاج لسه.
  - 400 `invalid_payload`: `fields` فيها `name` أو `crmFileId` أو `file`. ومع `file` فيه `details.reason`، وقيمته واحدة من: `empty` أو `not_pdf` أو `bad_image` أو `too_many_pixels`.
  - 413 `payload_too_large`: الملف أكبر من 25 ميجابايت.
- مهم: إرفاق ملف أو حذفه بيتحسب تعديل للطلب، وبيلغي الاعتمادات ويرجّع الطلب لمدير المبيعات، زي أي تعديل من `requests`. لازم المندوب يتحذّر قبلها.

### `design-file-delete` — حذف ملف بعته الـ CRM (آمن للتكرار)

- الجسم `{crmRequestId, crmFileId}`، والرد 200 `{request}`.
- لو الطلب مش `editable` يرجع 409 `request_locked`، ولو `crmFileId` مش موجود يرجع 404. الحذف بيلغي الاعتمادات زي الإرفاق.
- الـ CRM بيحذف ملفاته هو بس. الملفات اللي أرفقها الإنتاج بيديرها الإنتاج.

### `design-file` — تنزيل ملف

- الجسم `{fileId}`. الـ `fileId` بييجي من `designFiles`.
- الرد 200 هو بايتات الملف، و`Content-Type` إما `application/pdf` أو نوع الصورة أو `application/octet-stream`. والاسم في `Content-Disposition` (`filename*` بـ UTF-8).
- لو الملف مش موجود يرجع 404 بصيغة JSON المعتادة.

### `designFiles` في كائن الحالة (`status` وكل الردود) وفي عناصر `pending`

كل عنصر فيه: `fileId`، `crmFileId` (قيمته `null` للي أرفقه الإنتاج)، `name`، `kind` (`pdf` أو `image` أو `other`)، `size`، `source` (`crm` أو `production`)، `uploadedAt`.

### المهلات وإعادة المحاولة

- المهلة 120 ثانية لـ `design-files` ولـ `design-file`، ومهلات باقي المسارات زي ما هي.
- الملف يتحفظ في الـ CRM الأول، ويتبعت بعد ما الطلب نفسه يتقبل في `requests`، وبيتعاد بنفس جدول إعادة المحاولة (القسم 6).
- 400 و404 و413 نهائية، فمتعيدهاش لوحدها. اعرض للمندوب السبب.
- 409 `request_locked`: اعرض الحالة، والملف ميتبعتش.

### ما يفعله الـ CRM (للمراجعة مع تطبيق المنتجات)

- `crmFileId` في الـ CRM هو `mdf-` ثم UUID، ثابت للملف ولا يُعطى لغيره، حتى بعد حذفه.
- يفحص الـ CRM الاسم والامتداد والحجم والـ PDF والصورة (حتى 80 مليون نقطة من ترويسة الصورة) والعشرة ملفات (ملفاته وملفات الإنتاج كما في آخر حالة) قبل الحفظ، فأغلب الرفض يحدث عنده قبل الإرسال.
- العقد لا يذكر الرد على الملف الحادي عشر إن وصل؛ الـ CRM يعامل أي 400 كرفض نهائي ويعرض السبب كما جاء (`details.reason`).
- ملف لم يصل للإنتاج أبدًا (لم يُرسل، أو رُفض رفضًا نهائيًا) يُحذف في الـ CRM وحده دون نداء `design-file-delete`.
