# Yourrest CRM Android 1.0.11 (versionCode 12)

## Updates inside the app

The CRM shows an Arabic/English update banner at login and throughout the app.
It checks on opening, returning and reconnecting. Existing older APKs start their
first update through the banner and their existing browser download handler;
administrators do not distribute APK files to individual users. Version 1.0.10
adds private native downloads with progress, retry and Android installation
confirmation. It verifies size, SHA-256, package name, increasing version code
and the original installed signing certificate before opening PackageInstaller.
Android may request permission to install updates from Yourrest. Installation
requires user confirmation; this is not silent installation. Save any open form
before installing. Existing saved records, offline outboxes and login remain in
place because the signed package updates the existing app without uninstalling.

Public update metadata is generated from the verified APK build report using
`scripts/publish-android-release.mjs`, then served without caching at
`/api/app-update`. Do not change the APK without regenerating this metadata.

Native Android 8+ container for `https://crm.yourrest.org`, targeting API 35. Install the matching CRM server update before this APK. The Android package and signing identity remain unchanged from earlier releases.

## Customer-service request notifications in 1.0.11

Version 1.0.11 tells a representative when customer service assigns a request to them, even while Yourrest is closed or the phone is locked. The tracking foreground service (working hours: 06:00 to 18:00 Asia/Riyadh, never Friday) asks `GET /api/service-queue/alerts` every ten minutes through the signed-in session; opening or returning to the app asks at most once a minute. The server answers with the requests that wait for that member personally: identifier, customer name, a one-line need, what is expected (first contact, assign, delegate or approve), whether it was already opened and when it began waiting. No registration text, attachment, note, phone number or location is part of the answer, and the session cookie never leaves native memory.

A request is announced once per start (`id@since`); a re-assignment is a new start. Announced keys are kept per member in private preferences for 30 days (at most 300) and another member signing in on the same phone starts clean. `ServiceAlertPolicy` also skips requests already opened, skips announcing while the person is looking at the app (the page already shows the request) and folds more than three new requests into one summary. The lock screen shows only a generic title; the customer and need appear after unlocking. The channel is "طلبات خدمة العملاء" (high importance); on Android 13+ the notification permission is the one the tracking setup already asks for. Tapping a notification opens that request in the CRM: a running page receives `yourrest:open-service-case`, a cold start loads `#service-case=ID`, and a screen with unsaved work is never replaced.

Managers and supervisors, who do not run the tracking service, see the same requests in the Visits badge, panel and banner when they open the app or the website; this release has no background polling for them. Installed apps older than 1.0.11 keep working and receive requests in the page without the phone notification.

Not verified here: delivery on a real phone, Doze and battery-optimisation behaviour, and notification permission prompts on Android 13+. Test on company phones before relying on it.

## Offline route recovery in 1.0.9

Update both the server and each phone APK. The website update alone cannot repair native offline collection. Pending point timestamps, owner identity, day and selected-customer binding remain the original captured values, including after delayed delivery. Server replay accepts authorized historical observations without a fixed age cutoff, while keeping account-creation, schedule, ownership, current scope, device and timestamp checks. Do not uninstall the app or clear its storage while data is pending: either action deletes Android app-private storage.

## User-initiated dictation

Version 1.0.8 adds speech-to-text through an installed Android speech recognition activity, separately from location setup. Tap a field microphone, speak Arabic or English, review the inserted text and save the visit normally. No audio is archived by CRM. An available device speech service is required; if unavailable, use the keyboard microphone or type. The website exposes a clear message on a microphone attempt in an older APK rather than silently invoking an unsupported WebView API.

The trusted bridge advertises `speechProtocol:1` and `speechSupported`. `speechStart({sessionId,language})` returns `{sessionId,text,cancelled}`. `speechCancel({sessionId})` invalidates that exact session, including while the external recognition activity is in front. Recognition is bounded to 75 seconds and 5,000 text characters. Navigation, logout, a changed authenticated-session fingerprint, a changed field/customer, or a disabled/closed form prevents late text from entering another context. No microphone or foreground-service permission is added to CRM for this external recognition flow.

Use the in-app update banner to install the same-signed current APK over Yourrest. Publishing an update makes it discoverable; Android still asks the user to confirm installation. Actual microphone recognition still needs physical-device acceptance testing; browser mocks and native session checks are not that test.

## Representative continuous mode

The authenticated representative activates this mode through the visible setup button. `prepare({continuous:true})` shows a new, explicit Arabic disclosure: location, movement and stops are collected only from **06:00 inclusive to 18:00 exclusive in Asia/Riyadh, Saturday through Thursday (no Friday collection)**, with the screen locked or another app open during that period. Device timezone changes do not change the permitted hours. Existing broader consent remains valid for this reduced collection period. It asks for precise location and notifications, then separately explains Android's **Allow all the time** location setting. Earlier visit-only consent does not activate this policy.

`enroll({memberId})` verifies the actual signed-in server member, representative role, region scope and device before persisting enrollment and starting the location foreground service. No selected customer is required. A visible Android notification describes the 06:00–18:00 collection period excluding Friday, and explicitly says collection is paused outside that period. The representative has no app-provided End workday action in this mode; Android's own permission and stop controls remain effective. Logout disables enrollment and the cached offline authorization immediately. Pending points and gaps retain their original owner on the serialized worker; they can be uploaded only after that same account authenticates online again. An empty old-account store can be released for a different account. Pending evidence is never transferred to another account.

The native receiver handles `BOOT_COMPLETED` and `MY_PACKAGE_REPLACED` with stored enrollment, explicit consent, precise/background location and notifications. Time/timezone changes and a single ordinary inexact boundary alarm re-evaluate the schedule for an existing service; these alarms never start an otherwise stopped service or bypass Android foreground-start restrictions. The service attempts current server authentication before collecting on a restart and after an overnight pause. A successful authenticated response grants a local seven-day collection lease bound to the same member, representative role and region scope. A retryable connection failure or temporary server response can use the still-valid lease with current consent and OS permissions; first activation always needs the server. Explicit authentication/scope rejection (including HTTP 401, 403 and 409) and TLS failure never authorize this fallback. An expired or absent lease waits for successful online verification. This is a bounded permission to collect locally, not permission to upload under stale server credentials. The server always checks current authorization when data is uploaded.

Android can suspend or stop an app, remove permissions, restrict its battery use, or shut down the device. System Force stop is respected. On supported versions the next process checks `ApplicationExitInfo.REASON_USER_REQUESTED` and blocks automatic restart after an explicit system stop until the user reactivates enrollment. There are no stealth collection mechanisms, accessibility services, device-owner mechanisms or exact-alarm restart loops. The visible foreground service remains alive during scheduled pauses to support permitted resumption without new alarm permissions. Its location subscriptions are removed while paused, including the whole of Friday. Thursday at 18:00 schedules the next collection window for Saturday at 06:00. A main-thread boundary timer and an ordinary inexact wakeup alarm re-evaluate the schedule; callback guards independently reject every out-of-window fix even if Android delays delivery of a timer or alarm.

## Collection and storage

During the permitted hours, GPS and network updates are requested every 15 seconds with a zero-distance threshold in continuous mode, so stationary observations remain real samples. Android decides the actual delivery cadence. Each valid callback is saved directly in app-private SQLite before upload work, retaining its real timestamp, accuracy, UUID and customer binding captured at that callback. Network failures cannot hold accepted samples only in a worker's RAM queue.

Continuous data is partitioned by Riyadh date in a separate private outbox, with stable begin keys per day and a 100,000-pending-point capacity. There is no automatic age-based deletion or 48-hour upload deadline. At capacity, the store preserves all pending samples, records a buffer_full gap where possible and refuses new samples until capacity is available; storage or device failures cannot be treated as successful recording. Points and gap events upload chronologically in batches of at most 50 points. Acknowledgments are checked against the requested day, member and device, and only acknowledged sent IDs are removed. HTTP work is coalesced; each scheduled pass and the enrolled app-resume sync upload at most one chronological batch or gap before yielding the serialized worker to foreground actions. Explicit bridge flush and authorization retain their existing larger budgets. Concurrent inserts do not confuse upload acknowledgment counts. Territory changes or revoked authentication disable collection and preserve pending evidence for authorized resolution; they never silently clear it. Other rejected/conflicting data remains visible for review instead of being silently lost. Benign same-account conflicts receive at most three status-verified retries.

At 18:00 collection pauses without fabricating a GPS exit, visit duration, gap or day-end event. No new location is subscribed to or persisted outside the permitted window. Pre-upgrade Friday points and gaps remain unmodified in the private outbox as quarantined evidence without automatic age deletion and still counted toward capacity; they do not enter upload selectors or block a later permitted date. Queued totals still protect account identity and storage limits; pending upload counts include only eligible dates. A separate informational `quarantineNotice` and `quarantinedCount`/`quarantinedGapCount` report these rows, without setting a collection error or `syncError`. Already queued in-window points can upload at any time, including after 18:00 and on Friday; the restriction is on when locations are captured, not the later delivery time. The following eligible 06:00 window attempts authenticated verification before subscribing again, with the bounded offline lease fallback described above. Each new Saudi date clears yesterday's customer binding. Historical queued points and gaps are uploaded before the new date is opened when possible; the backend also preserves valid late evidence around a system midnight closure. New day boundaries never fabricate movement, customer arrival or departure. The reports derive stops from actual verified fixes and show gaps when evidence is missing.

Legacy visit-mode outbox data is migrated after verifying the same representative. IDs and dates remain unchanged, and data is copied durably before its legacy acknowledgment/removal. Managers and supervisors retain the existing optional visit/day tracking behavior; they are never automatically enrolled in background collection. Their optional collector also removes provider subscriptions and rejects captures outside the same working-hours window.

## Web bridge and navigation

The user agent contains `YourrestCRM-Android/1`. The website must suppress its browser collector as soon as this marker is present. A trusted main-page load injects `window.__yourrestNative.request(method,payload)` and emits `yourrest:native-ready`; state changes emit `yourrest:native-state` with the state as `detail`.

Methods:

- `prepare({continuous?:boolean})`: informed consent and Android permission setup only.
- `enroll({memberId})`: verify and activate/resume representative continuous mode.
- `start({memberId,stopId})`: bind the selected authenticated customer after verifying the current server member, scope, device and active stop. It does not drain unrelated queued observations first; their original captured customer bindings remain unchanged. Collection remains active between visits during the working-hours window.
- `status({})`, `flush({})`, `logout({})`.
- `stop({})`: legacy day mode only; rejects while continuous enrollment is active.
- `directions({memberId,stopId,latitude,longitude})`: requires a trusted foreground page, the bound member and stop, running tracking (or scheduled pause with valid enrollment), and exact coordinates from the server's customer snapshot. After that preflight, opens a fixed `google.navigation:q=latitude,longitude&mode=d` intent pinned to `com.google.android.apps.maps`, without the BROWSABLE category. If Maps is unavailable or the OS rejects it, attempts the canonical HTTPS Google Maps directions URL once. It does not use `resolveActivity`, which can misreport installed apps under package visibility rules. If both launches fail, a native dialog explains the failure and the bridge returns `maps_launch_failed:` with that human-readable message; binding/permission/coordinate failures retain their original error and never get this marker.

Successful requests return `{tracking,permission,pendingCount,pendingGapCount,lastFixAt,accuracy,error,dayId,date,stopId,memberId,directionsSupported,mapsLaunchSupported,appVersion,continuousSupported,enrolled,backgroundPermission,workHoursSupported,fridayExclusionSupported,workWeekSupported,workingDays,workingHoursTimeZone,trackingWindowActive,trackingWindowStart,trackingWindowEnd,trackingTimeZone,nextTrackingWindowAt}`. `appVersion` comes from the installed Android package metadata; `mapsLaunchSupported:true` identifies the explicit Maps launcher. Both pending counts are integers from the durable store: point count and gap-event count. A points-only zero does not prove the outbox is empty; the website must preserve its preselection sync barrier when gaps remain or the legacy gap count is unknown. A day ID may be null before the first permitted window or during an offline rollover. Outside working hours, valid enrollment returns `enrolled:true,tracking:false,error:null`. The `workHoursSupported:true` capability identifies this APK policy so the website can distinguish older 24-hour clients and prompt an update. `fridayExclusionSupported:true` and `workWeekSupported:true` identify this Friday-excluding version; `workingDays:[0,1,2,3,4,6]` uses JavaScript weekday numbers (Friday is 5), and `workingHoursTimeZone` is `Asia/Riyadh`. Earlier APKs omit the capability flags; the website must check them before invoking new commands. Except for cancellation of a matching speech session and the existing bounded Maps handoff, a valid trusted bridge request received while the activity is hidden rejects immediately with an instruction to open the app, rather than waiting for the 90-second bridge timeout. Nonce and trusted-origin checks still run before any reply.

Async ordinary directions links (including outside tracking hours) can use the same launcher from the currently trusted CRM main frame. This exception accepts only HTTPS `www.google.com/maps/dir/` URLs with `api=1`, one finite in-range coordinate pair, `travelmode=driving` and `dir_action=navigate`, with no extra or duplicate parameters, userinfo, arbitrary port or fragment. It requires a genuine gesture or the current nonempty injected navigation nonce, while the activity is resumed. This preserves the legitimate handoff when WebView no longer reports a gesture after an awaited CRM request. Subframes and other external URLs retain the ordinary gesture requirement. The adapter constructs both intents from validated coordinates; it never launches a supplied arbitrary intent or custom scheme.

WebView authentication stays in the cookie jar. Native requests obtain current HttpOnly cookies directly through `CookieManager`; cookies never enter JavaScript or the outbox. The low-level bridge requires a per-main-navigation nonce and exact trusted HTTPS page. Mixed HTTP, file URLs, SSL bypass, third-party cookies and WebView debugging are disabled. Ordinary external navigation still requires a user gesture. File uploads use Android's document picker; browser-generated blob downloads currently instruct the user to use the browser.

## Verification and builds

The code has compiled against the Android 35 API classes. JVM checks cover the actual rules and scheduling helpers: 37 route rules, 138 chronological-outbox checks, 27 directions checks and 30,472 continuous-policy checks (Saudi boundaries, every minute of a full week, Friday exclusion, Thursday-to-Saturday scheduling, calendar transitions, cached fixes and independent device timezones). The trip-start regression adds 178 source guards and actual-outbox-scheduler checks for authenticated binding without unrelated backlog drains, single-operation background/resume passes, retained retry data, gap-only queues and foreground-required replies for trusted hidden requests. These are **not** physical phone, battery, GPS, reboot, lock-screen or Maps-launch acceptance tests.

The Maps launcher has 120 executable parser/transport and integration-source checks. They exercise installed/missing/denied Maps, HTTPS fallback, failure of both handlers, malformed destinations, arbitrary schemes and hosts, frame/origin/nonce/gesture guards, authenticated-bound preflight, package/category selection and installed-version capability. OS responses are simulated; actual Google Maps launch on a phone remains unverified.

Before rollout, verify on actual representative devices: first consent and permissions; start a selected customer's trip with a queued GPS backlog; launch installed Google Maps during and outside tracking hours; test HTTPS fallback with Maps disabled and a clear error if no browser is enabled; return to the CRM after Maps while sync is active; foreground/background transitions during a start request; collection while locked and using Maps; stationary stops; lost GPS and internet; 06:00 start and 18:00 pause while locked; Thursday-to-Saturday scheduling and no Friday GPS subscriptions; timezone/clock changes; offline reconnect after 18:00; reboot/package update; system stop; permission removal; logout/account switching; same-account recovery of queued data after logout; offline reboot/new-workday recovery with a valid lease; rejection and lease-expiry cases; queues older than 48 hours; storage-full behavior; and scoped supervisor reports. OEM battery settings may affect restart reliability.

Standard build: AGP 8.9.2, Gradle 8.13, JDK 17, SDK 35. Debug builds have `.dev` appended to the package. The alternative pinned open-source build is described in `tools/README.md`; it does not auto-accept an Android SDK license. Keep the private signing key outside the source package and use the same certificate for all APK updates. A signed APK is not evidence of store review or device testing.

The notification rules have their own check (`ServiceAlertCheck`, 75 checks: cadence, validity of what the server sends, news and de-duplication, retention, wording, summary, and source guards for the fixed origin, bounded answer, private lock screen and the single-top activity). With a plain JDK: `javac -d out RouteRules.java ServiceAlertPolicy.java ServiceAlertCheck.java`, then `java -cp out org.yourrest.crm.ServiceAlertCheck <main Java source directory>`.

Run pure Java checks with JDK 17, compiling `RouteRules.java`, `OutboxDrain.java`, `ContinuousPolicy.java`, `MapsLauncher.java` and their corresponding test classes in `app/src/test/java/org/yourrest/crm`, then run `RouteRulesCheck`, `OutboxDrainCheck`, `DirectionsCheck`, `ContinuousPolicyCheck`, `TripStartCheck` and `MapsLaunchCheck`. For the last two checks, pass the main Java source directory as their first argument when running outside the CRM project root. The full source compile additionally requires an Android 35 API classpath and generated Android resources.
